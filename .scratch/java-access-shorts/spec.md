# 스펙: 자바 입문 열여섯 번째 — 접근 제어자

Status: resolved

## Problem Statement

15편 "패키지"에서 시청자는 다른 패키지의 클래스를 쓰려면 `public`이 필요하다는 것만 배웠다. 그 장면은 "자세한 건 다음 편 접근 제어자에서 다룰게요"라고 예고했다. 그런데 실제 코드에는 `private`·`protected`, 그리고 아무것도 안 붙인 멤버가 섞여 있고, 입문자는 이것들이 각각 어디까지 열려 있는지 모른다.

입문자가 접근 제어자에서 특히 자주 헷갈리는 점은 다음과 같다.

- 네 가지(`private`·기본 접근·`protected`·`public`)가 각각 어디까지 쓸 수 있게 해 주는지
- 아무것도 안 붙인 기본 접근을 `default`라고 적는 것으로 오해하는 것(13편의 `default` 메소드와 혼동)
- 자식 클래스라도 부모의 `private` 멤버는 쓸 수 없다는 것
- `protected`가 "자식 전용"이 아니라 "같은 패키지 + 다른 패키지의 자식"이라는 것
- 최상위 클래스에는 `public`과 기본 접근만 붙일 수 있다는 것
- 필드를 왜 `private`으로 숨기는지(캡슐화)
- 13편에서 인터페이스 메소드를 구현할 때 왜 `public`이 필수였는지

3분 이하 세로 쇼츠 한 편으로, 실제 여러 파일을 컴파일해 나오는 오류로 각 단계의 경계를 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열여섯 번째 영상 "접근 제어자"를 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 예시 클래스: 15편의 `school` 패키지(`Person`·`Student` 민수·`Teacher` 서준)와 `app` 패키지(`Main`)를 이어 쓰고, `app` 패키지에 `Person`을 상속한 `Tutor`(지우)를 추가한다
- 흐름: 좁은 것부터 넓은 것으로 private → 기본 접근 → protected → public → 네 단계 표 → 클래스의 접근 제어자 → 캡슐화 → 오버라이딩과 접근 범위

장면 구성은 아래와 같다.

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | – | 자바 입문 열여섯 번째, 접근 제어자. `public`·`protected`·기본·`private` 네 칩 |
| priv | 1. private | 1 | `Person`의 `private String pw;`. `Person` 안의 `check()`에서는 됨(`true`), 같은 패키지의 자식 `Student`에서 `pw`를 쓰면 오류 `pw has private access in Person`. 칩: 같은 클래스만 |
| dflt | 2. 기본 접근 | 2 | `String phone;`(아무것도 안 붙임). `school.Student`에서는 됨, `app.Main`에서 `s.phone`은 오류 `phone is not public in Person; cannot be accessed from outside package`. 메모: `default`라고 적는 게 아님(적으면 오류) |
| prot | 3. protected | 3 | `protected int age;`. `app.Tutor`(다른 패키지의 자식) 안에서는 됨, `app.Main`에서 `s.age`는 오류 `age has protected access in Person`. 같은 패키지에서도 됨 |
| pub | 4. public | 4 | `public String name;`. `app.Main`에서 `s.name` → `민수`. 15편에서 클래스·생성자·메소드에 붙였던 그 `public` |
| table | 4-1. 한눈에 표 | 4 | 4×4 표(행: public·protected·기본·private / 열: 같은 클래스·같은 패키지·다른 패키지의 자식·다른 패키지 전체), ✅/❌ |
| cls | 4-2. 클래스에는 둘만 | 4 | 최상위 클래스에는 `public`과 기본 접근만. `private class Club` → 오류 `modifier private not allowed here` |
| enc | 5. 캡슐화 | 5 | `Student`의 `private int score;` + `getScore()`·`setScore()`(0~100만 받음). `s.setScore(-5)` 후 `getScore()` → `85`. `s.score = -5`는 오류 `score has private access in Student` |
| ovr | 5-1. 오버라이딩과 접근 범위 | 5 | `Teacher`의 `hello()`에서 `public`을 빼면 오류 `hello() in Teacher cannot override hello() in Person` / `attempting to assign weaker access privileges; was public`. 메모: 그래서 13편에서 인터페이스 메소드 구현에 `public`이 필수 |
| outro | 정리 | – | 목록 전체 → 나레이션에 맞춰 줄 강조 → 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열여섯 번째, 접근 제어자"라는 주제를 바로 알고 싶다. 15편이 예고한 그 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 `public`·`protected`·기본·`private` 네 가지를 칩으로 먼저 보고 싶다. 이번 편에서 다룰 대상을 한눈에 알 수 있기 때문이다.
3. 시청자로서, 15편의 `school`·`app` 패키지와 민수·서준이 다시 나오길 바란다. 새 예제를 익히는 부담 없이 접근 범위에만 집중할 수 있기 때문이다.
4. 시청자로서, `Person`의 필드 네 개가 접근 제어자만 다르다는 것을 보고 싶다. 비교 대상이 하나로 고정되어 차이가 분명해지기 때문이다.
5. 시청자로서, 가장 좁은 `private`부터 가장 넓은 `public`까지 순서대로 배우고 싶다. 범위가 한 칸씩 넓어지는 흐름으로 기억할 수 있기 때문이다.
6. 시청자로서, `private` 필드가 같은 클래스 안의 메소드에서는 문제없이 쓰이는 것을 보고 싶다. `private`이 "아무도 못 쓰는 것"이 아니라는 것을 알 수 있기 때문이다.
7. 시청자로서, 자식 클래스 `Student`조차 부모의 `private` 필드를 쓰면 오류가 나는 것을 보고 싶다. 상속하면 다 쓸 수 있다는 오해를 바로잡을 수 있기 때문이다.
8. 시청자로서, 실제 오류 문구 `has private access`를 화면에서 보고 싶다. 직접 같은 오류를 만났을 때 알아볼 수 있기 때문이다.
9. 시청자로서, 아무것도 안 붙인 필드가 같은 패키지에서는 쓰이고 다른 패키지에서는 오류가 나는 것을 보고 싶다. 기본 접근의 경계가 패키지라는 것을 알 수 있기 때문이다.
10. 시청자로서, 기본 접근에 "(아무것도 안 붙임 = 같은 패키지 전용)"이 함께 적혀 있길 바란다. 용어와 뜻을 함께 기억할 수 있기 때문이다.
11. 시청자로서, 기본 접근을 `default`라고 적는 게 아니라는 메모를 보고 싶다. 13편의 `default` 메소드와 헷갈리지 않기 때문이다.
12. 시청자로서, 15편에서 본 `is not public in ...; cannot be accessed from outside package` 오류가 필드에서도 나는 것을 보고 싶다. 지난 편과 이어서 이해할 수 있기 때문이다.
13. 시청자로서, 다른 패키지의 자식 클래스 `Tutor`가 `protected` 필드를 쓰는 것을 보고 싶다. `protected`가 자식에게 열어 주는 범위를 결과로 확인할 수 있기 때문이다.
14. 시청자로서, 같은 `app` 패키지의 `Main`에서는 `protected` 필드가 오류(`has protected access`)인 것을 보고 싶다. 자식이 아니면 다른 패키지에서는 못 쓴다는 것을 알 수 있기 때문이다.
15. 시청자로서, `protected`는 같은 패키지에서도 쓸 수 있다는 설명을 듣고 싶다. "자식 전용"이라는 오해를 피할 수 있기 때문이다.
16. 시청자로서, `public` 필드는 다른 패키지의 `Main`에서도 쓰여 `민수`가 나오는 것을 보고 싶다. 가장 넓은 범위를 결과로 확인할 수 있기 때문이다.
17. 시청자로서, 단계마다 그 단계가 어디까지 열리는지 칩으로 보고 싶다. 코드와 오류를 보면서도 범위를 놓치지 않기 때문이다.
18. 시청자로서, 네 단계를 4×4 표로 한 번에 정리해서 보고 싶다. 캡처해 두고 복습할 수 있기 때문이다.
19. 시청자로서, 표의 각 행이 단계 장면의 칩과 같은 색·같은 ✅/❌로 나오길 바란다. 앞에서 본 내용과 바로 연결되기 때문이다.
20. 시청자로서, 최상위 클래스에는 `public`과 기본 접근만 붙일 수 있다는 것을 보고 싶다. 클래스에 `private`을 붙이는 실수를 피할 수 있기 때문이다.
21. 시청자로서, `private class`의 실제 오류 문구 `modifier private not allowed here`를 보고 싶다. 같은 오류를 알아볼 수 있기 때문이다.
22. 시청자로서, 필드를 `private`으로 숨기고 getter·setter로 다루는 예를 보고 싶다. 실무 코드에서 가장 흔한 모양을 알아볼 수 있기 때문이다.
23. 시청자로서, `setScore(-5)`를 불러도 점수가 85로 지켜지는 것을 보고 싶다. 숨기는 이유가 "잘못된 값을 막기 위해서"라는 것을 결과로 이해할 수 있기 때문이다.
24. 시청자로서, `s.score = -5`처럼 직접 바꾸려 하면 오류가 나는 것을 보고 싶다. 숨긴 필드는 setter를 거쳐야만 바뀐다는 것을 알 수 있기 때문이다.
25. 시청자로서, 이것을 "캡슐화"라고 부른다는 것을 듣고 싶다. 앞으로 자주 들을 용어를 알 수 있기 때문이다.
26. 시청자로서, 오버라이딩할 때 `public`을 빼면 오류가 나는 것을 보고 싶다. 접근 범위를 좁힐 수 없다는 규칙을 알 수 있기 때문이다.
27. 시청자로서, 13편에서 인터페이스 메소드 구현에 `public`이 필수였던 이유가 이 규칙이라는 것을 듣고 싶다. 따로 외웠던 규칙이 하나로 연결되기 때문이다.
28. 시청자로서, 정리 장면에서 핵심을 목록으로 한꺼번에 보고, 나레이션이 말하는 줄이 강조되길 바란다. 복습하면서 따라 읽을 수 있기 때문이다.
29. 시청자로서, 모든 자막이 나레이션과 단어 단위로 맞길 바란다. 소리 없이 보더라도 내용을 따라갈 수 있기 때문이다.
30. 시청자로서, 휴대폰 화면에서도 표와 코드가 읽히길 바란다. 쇼츠는 대부분 휴대폰으로 보기 때문이다.
31. 제작자로서, 화면의 모든 예제가 실제 폴더 구조로 여러 파일을 컴파일·실행해서 대본의 결과와 같은지 빌드가 확인하길 바란다. 접근 범위는 패키지 경계에서만 드러나기 때문이다.
32. 제작자로서, 화면에 나오는 컴파일 오류 문구도 빌드가 실제 javac 결과와 대조하길 바란다. 틀린 오류 문구를 올리는 일을 막을 수 있기 때문이다.
33. 제작자로서, 4×4 표의 ✅/❌도 실제 컴파일 결과로 확인되길 바란다. 표 한 칸이 틀리면 영상 전체의 신뢰가 깨지기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-access-shorts`. 15편(패키지)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 입문 접근 제어자 정리", "접근 제어자"는 주황 강조. 진행 표시는 5칸이다. 4-1·4-2는 4번째 칸, 5-1은 5번째 칸에 속한다.
- **용어** (GLOSSARY): 접근 제어자, 기본 접근, 캡슐화, getter / setter. "접근 제한자", "접근 지정자", "default 접근"은 쓰지 않는다. 기본 접근은 화면에 처음 한 번 "(아무것도 안 붙임 = 같은 패키지 전용)"을 덧붙인다. 표의 행 이름과 칩은 "기본"으로 쓴다.
- **예시 데이터** (영상 전체에서 하나로 통일)
  - `school` 패키지
    - `Person` (k1): `public abstract class`. 필드 네 개 `public String name` · `protected int age` · `String phone` · `private String pw`. `public` 생성자, `pw`를 쓰는 `public` 메소드 `check(String)`, `public abstract void hello()`
    - `Student` (k2): `public class Student extends Person`. 민수, 나이 17, 점수 85. `phone`을 쓰는 메소드(기본 접근 장면용), enc 장면에서는 `private int score` + `getScore()`·`setScore()`(0~100만 받음)
    - `Teacher` (k3): `public class Teacher extends Person`. 서준. `public void hello()` → ovr 장면에서만 `public`을 뺀다
  - `app` 패키지
    - `Tutor` (k3 이외의 색이 필요하면 `--violet`): `public class Tutor extends Person`. 지우, 나이 20. `age`를 쓰는 `hello()`
    - `Main`: 다른 패키지에서 접근하는 문장은 모두 이 클래스의 `main` 안에서 실행된다
  - 생성자 매개변수가 늘어나 화면이 길어지면 생성자는 `{ ... }`로 줄여 보여 준다(실제 컴파일 소스는 완전한 코드)
- **장면별 기대 결과** (기획 단계에서 로컬 javac/java로 확인함, 대조 기준)
  - 출력: priv `true`(`s.check("1234")`), dflt `010-1234`(Student 안에서 phone), prot `튜터 지우 20살`, pub `민수`, enc `85`
  - 컴파일 오류(첫 오류 줄)
    - priv: `pw has private access in Person`
    - dflt: `phone is not public in Person; cannot be accessed from outside package`
    - prot: `age has protected access in Person`
    - cls: `modifier private not allowed here`
    - dflt 메모(`default int x;`): `modifier default not allowed here` — 화면에 문구는 안 보여 줘도 되지만 빌드가 확인한다
    - enc: `score has private access in Student`
    - ovr: `hello() in Teacher cannot override hello() in Person` (둘째 줄 `attempting to assign weaker access privileges; was public`). 화면에는 둘째 줄을 보여 주므로 대조 헬퍼가 오류의 다음 줄까지 볼 수 있어야 한다
- **표 검증**: 4×4 표의 16칸을 실제 컴파일로 확인한다. 각 접근 제어자의 필드를 네 위치(같은 클래스 `Person`, 같은 패키지 `school`의 다른 클래스, 다른 패키지의 자식 `app.Tutor`, 다른 패키지의 일반 클래스 `app.Main`)에서 접근해 보고, 성공·실패가 표의 ✅/❌와 같은지 대조한다. 표는 이 결과로 그린다(직접 적지 않는다). "같은 패키지" 열은 자식이 아닌 클래스로 확인해 `protected`의 같은 패키지 허용을 보인다.
- **여러 파일 컴파일 헬퍼**: 15편의 파일 묶음 컴파일 헬퍼를 그대로 쓴다. 장면마다 기본 묶음(`school` 3개 + `app.Tutor` + `app.Main`)에서 바뀐 파일만 넘긴다. 오류 대조에 "다음 줄"까지 포함하는 확장만 필요하다.
- **사실 표현 주의**
  - `protected`는 "자식만"이라고 말하지 않는다. "같은 패키지, 그리고 다른 패키지의 자식"으로 말한다. 다른 패키지의 자식이 부모 타입 변수로 접근하면 안 되는 미묘한 규칙은 다루지 않으므로 "자식 클래스 안에서"처럼 말한다.
  - 클래스 규칙은 "최상위 클래스"에 한정한다(중첩 클래스는 `private` 가능). 나레이션은 "파일에 바로 쓰는 클래스에는"처럼 쉽게 쓴다.
  - 오버라이딩 규칙은 "범위를 좁힐 수 없다(넓히는 건 된다)"로 말한다.
- **장면 구성 요소**
  - 단계 장면(priv·dflt·prot·pub)은 같은 모양으로 배치한다: `head` → 필드 선언 한 줄(`mark`) → 되는 코드와 결과 → 안 되는 코드와 오류 문구(`.warn`) → 범위 칩(네 위치 ✅/❌)
  - table은 기존 `table()` 헬퍼로 그리고, ❌ 칸은 기존 빨간 표시를 재사용한다. 새 디자인 토큰은 추가하지 않는다
  - enc는 `setScore` 안의 범위 검사 줄을 `mark`로 강조한다
  - ovr는 `.note`로 13편과 연결한다
  - 코드 한 줄은 33자 이하로 쓴다
- **대본**
  - 영어 키워드는 한글 발음으로 쓴다(퍼블릭, 프로텍티드, 프라이빗, 패키지, 스쿨, 앱, 퍼슨, 스튜던트, 티처, 튜터, 메인, 체크, 게터, 세터, 겟스코어, 셋스코어, 헬로).
  - 기본 접근을 처음 말할 때는 "아무것도 안 붙이면"을 함께 말한다(기본 생성자·기본값과 혼동 방지).
  - 길이는 대본 전체를 먼저 써서 확인하고, 3분을 넘으면 음성 생성 전에 줄인다.
- **정리 장면** (6줄 안팎, 대본 작성 때 확정)
  1. `private`: 같은 클래스 안에서만
  2. 기본(아무것도 안 붙임): 같은 패키지까지
  3. `protected`: 같은 패키지 + 다른 패키지의 자식
  4. `public`: 어디서나
  5. 필드는 `private` + getter·setter(캡슐화)
  6. 오버라이딩은 범위를 좁힐 수 없다
- **README**: 제목은 "자바 입문: 접근 제어자 (private · 기본 · protected · public · 클래스 접근 · 캡슐화 · 오버라이딩)". YouTube URL은 업로드 후 넣는다.
- **유튜브 제목**: "자바 입문 16편: 접근 제어자 | public · protected · 기본 · private".

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 실제 폴더 구조로 컴파일·실행한 예제의 출력, javac의 실제 오류 문구, 표의 ✅/❌가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 15편 빌드의 파일 묶음 컴파일·실행 검증을 그대로 쓴다. 새 테스트 지점은 만들지 않는다. 표 16칸 확인도 같은 지점을 반복 호출한다.
- **대조 항목**
  - 출력 대조(5건): priv, dflt, prot, pub, enc
  - 컴파일 오류 대조(7건): priv, dflt, dflt 메모(`default`), prot, cls, enc, ovr
  - 표 대조(16칸)
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다.
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(table 또는 단계 장면)을 390px 폭으로 줄여 모바일 가독성을 확인한다.
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다.
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재.
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "점수는 그대로 팔십오예요"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 15편 빌드의 파일 묶음 컴파일·오류 대조 헬퍼, 13편의 `public` 필수 컴파일 오류 장면.

## Out of Scope

- `protected`의 세부 규칙(다른 패키지의 자식이 부모 타입 변수나 다른 객체를 통해 접근하면 오류)
- 중첩 클래스·내부 클래스의 접근 제어자
- `private` 생성자, 싱글턴
- 모듈(`module-info.java`)의 `exports`에 따른 접근 제한
- 리플렉션으로 `private` 접근하기
- 인터페이스 멤버의 암묵적 `public`, `private` 인터페이스 메소드
- 디자인·템포·제작 도구의 변경

## Further Notes

- 시리즈 순서: … → 인터페이스(13) → 다형성(14) → 패키지(15) → 접근 제어자(16). 15편 `pub` 장면이 "다음 편 접근 제어자"를 예고했다.
- 15편의 `Person.name`은 기본 접근이었다. 이번 편에서는 `public`으로 바꾸고, 대신 `phone`이 기본 접근 역할을 맡는다.
- 용어 4개(접근 제어자, 기본 접근, 캡슐화, getter / setter)는 기획 단계에서 GLOSSARY에 등록했다. 처음에 "default 접근"으로 정했다가 13편의 `default` 메소드와 헷갈려 "기본 접근"으로 바꿨다.
- 기획 중 확인한 javac 오류 문구는 로컬 javac(영문 로케일 `-J-Duser.language=en`) 기준이다.
- 커밋·푸시는 사용자가 요청할 때만 한다.
