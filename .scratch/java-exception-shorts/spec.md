# 스펙: 자바 입문 스무 번째 — 예외

Status: ready-for-agent

## Problem Statement

시청자는 지난 편들에서 "실행 중 오류"를 여러 번 봤다. 다운캐스팅이 실패할 때(14편), 같은 스트림을 두 번 쓸 때(19편)가 그 예다. 하지만 그것이 무엇인지, 어떻게 막는지는 아직 배우지 않았다. 다음 편(21편 텍스트 파일 읽기·쓰기)은 `IOException` 처리가 필수라서, 예외를 모르면 첫 줄부터 컴파일 오류를 만난다.

입문자가 예외를 처음 배울 때 특히 막히는 점은 다음과 같다.

- 예외가 나면 왜 프로그램이 그 자리에서 멈추고 다음 줄이 실행되지 않는지
- `try-catch`로 잡으면 무엇이 달라지는지, `catch` 괄호 안의 예외 타입은 무엇인지
- 예외 종류가 여러 개일 때 `catch`를 여러 개 쓰는 법과 그 순서
- `finally`가 언제 실행되는지
- `throw`와 `throws`의 차이(한 글자 차이라 헷갈림)
- 어떤 예외는 처리하지 않으면 컴파일조차 안 되는 이유(체크 예외 / 언체크 예외)
- 예외 클래스를 왜, 어떻게 직접 만드는지(커스텀 예외)

3분 이하 세로 쇼츠 한 편으로, 실제로 실행한 결과·예외·컴파일 오류로 이 내용을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 스무 번째 영상 "예외"를 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 흐름: 예외로 프로그램이 멈추는 모습에서 출발해, 잡고(try-catch) → 종류별로 잡고(여러 catch) → 항상 실행하고(finally) → 직접 던지고(throw) → 처리를 넘기고(throws) → 직접 만든다(커스텀 예외)
- 예시 데이터: 시리즈와 같은 이름 민수·서준·지우, 점수 85·92·78. 잘못된 점수의 예는 `120`
- 하나의 `checkScore` 메소드가 STEP 4~5에 걸쳐 발전한다: `IllegalArgumentException` 던지기 → `Exception`으로 바꾸면 컴파일 오류 → `throws` 추가 → `ScoreException`으로 교체

장면 구성은 아래와 같다. 진행 표시가 5칸이라 기획 때의 STEP 6개를 5칸에 맞췄다(throw와 throws를 STEP 4 한 칸에 묶음).

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "예외" 제목. `10 / 0` 다음 줄 출력이 실행되지 않고 `ArithmeticException`으로 멈춤. "지난 편들의 '실행 중 오류'가 바로 예외" |
| trycatch | 1. try-catch | 1 | 같은 코드를 `try`에 넣고 `catch (ArithmeticException e)`로 잡으면 "0으로 나눌 수 없어요" 출력 뒤 "끝"까지 실행 |
| kinds | 2. 여러 catch | 2 | `Integer.parseInt("abc")` → `NumberFormatException`, 배열 `a[3]` → `ArrayIndexOutOfBoundsException`. `e.getMessage()`로 실제 메시지 출력 |
| order | 2-1. catch 순서 함정 | 2 | `catch (Exception e)`를 먼저 쓰면 아래 `catch`는 실행될 일이 없어 컴파일 오류. 구체적인 예외부터 위에 |
| finally | 3. finally | 3 | `"85"`와 `"abc"`를 각각 변환. 예외가 나든 안 나든 `finally`의 "끝" 출력 |
| throw | 4. throw | 4 | `checkScore(120)` → `if`문에서 `throw new IllegalArgumentException(...)`. 언체크 예외라 `throws` 없이 컴파일됨 |
| throws | 4-1. throws · 체크 예외 | 4 | `Exception`을 던지게 바꾸면 컴파일 오류(`unreported exception`). 메소드에 `throws`를 붙이면 부르는 쪽이 `try-catch`로 처리. 체크 예외(처리 강제) / 언체크 예외(처리 선택) `.vs` 카드 |
| custom | 5. 커스텀 예외 | 5 | `class ScoreException extends Exception` + 생성자에서 `super(message)`. `checkScore`가 `ScoreException`을 던지고 `catch (ScoreException e)`로 잡아 메시지 출력 |
| outro | 정리 | — | 목록 전체 → 나레이션에 맞춰 줄 강조. `RuntimeException`을 물려받으면 처리 강제 없음 한 줄 포함. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 스무 번째, 예외"라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 `10 / 0` 다음 줄이 실행되지 않고 프로그램이 멈추는 모습을 실제 실행 결과로 보고 싶다. 예외가 왜 문제인지 바로 느낄 수 있기 때문이다.
3. 시청자로서, 실행 결과에 `ArithmeticException`과 `/ by zero`가 찍힌 것을 보고 싶다. 실제 개발 중에 만날 화면에 익숙해지기 때문이다.
4. 시청자로서, 지난 편들의 "실행 중 오류"가 바로 예외였다는 연결을 듣고 싶다. 이미 본 장면과 새 용어가 이어지기 때문이다.
5. 시청자로서, 예외는 실행 중에 생겨 처리할 수 있는 것이고, 컴파일 오류는 실행 전에 막히는 것이라는 구분을 듣고 싶다. 두 말을 섞어 쓰지 않게 되기 때문이다.
6. 시청자로서, 같은 코드를 `try`에 넣고 `catch`로 잡으면 "끝"까지 실행되는 것을 보고 싶다. `try-catch`의 효과를 결과로 확인할 수 있기 때문이다.
7. 시청자로서, `catch` 괄호 안의 예외 타입이 "어떤 예외를 잡을지"를 정한다는 것을 보고 싶다. 괄호 안을 어떻게 쓰는지 알 수 있기 때문이다.
8. 시청자로서, `try` 안에서 예외가 난 줄 아래는 건너뛰고 `catch`로 바로 넘어간다는 것을 보고 싶다. 실행 순서를 정확히 알 수 있기 때문이다.
9. 시청자로서, 숫자가 아닌 글자를 `Integer.parseInt`로 바꿀 때 `NumberFormatException`이 난다는 것을 보고 싶다. 자주 만나는 예외를 알 수 있기 때문이다.
10. 시청자로서, 배열 범위를 넘으면 `ArrayIndexOutOfBoundsException`이 난다는 것을 보고 싶다. 배열 편에서 배운 인덱스와 연결되기 때문이다.
11. 시청자로서, 예외 종류마다 `catch`를 따로 써서 다르게 처리하는 모습을 보고 싶다. 여러 예외를 다루는 법을 알 수 있기 때문이다.
12. 시청자로서, `e.getMessage()`가 예외의 설명 문구를 돌려준다는 것을 실제 출력으로 보고 싶다. 무엇이 잘못됐는지 알아내는 법을 알 수 있기 때문이다.
13. 시청자로서, `catch (Exception e)`를 위에 먼저 쓰면 아래 `catch`가 컴파일 오류가 되는 함정을 보고 싶다. 같은 실수를 피할 수 있기 때문이다.
14. 시청자로서, 그 이유가 `Exception`이 모든 예외의 부모 클래스라서 먼저 다 잡아 버리기 때문이라는 설명을 듣고 싶다. 상속 편에서 배운 부모·자식 관계와 연결되기 때문이다.
15. 시청자로서, "구체적인 예외부터 위에 쓴다"는 규칙을 한 줄로 받고 싶다. 외우기 쉽기 때문이다.
16. 시청자로서, 예외가 날 때와 안 날 때 모두 `finally`가 실행되는 것을 두 실행 결과로 비교해 보고 싶다. `finally`의 의미를 결과로 확인할 수 있기 때문이다.
17. 시청자로서, `throw new 예외클래스("메시지")`로 예외를 직접 던질 수 있다는 것을 보고 싶다. 잘못된 값을 내 코드에서 막는 방법을 알 수 있기 때문이다.
18. 시청자로서, 점수 120처럼 문법은 맞지만 말이 안 되는 값을 `checkScore`가 막는 예제를 보고 싶다. 직접 던지는 이유를 이해할 수 있기 때문이다.
19. 시청자로서, `IllegalArgumentException`은 `throws` 없이도 컴파일된다는 것을 보고 싶다. 언체크 예외의 성질을 먼저 경험할 수 있기 때문이다.
20. 시청자로서, 같은 메소드가 `Exception`을 던지게 바꾸면 `unreported exception` 컴파일 오류가 나는 것을 보고 싶다. 체크 예외가 처리를 강제한다는 것을 결과로 확인할 수 있기 때문이다.
21. 시청자로서, 메소드 선언에 `throws`를 붙이면 "부르는 쪽이 처리하라"는 뜻이라는 것을 보고 싶다. `throws`의 역할을 알 수 있기 때문이다.
22. 시청자로서, `throw`와 `throws`가 화면에서 `s` 한 글자로 구분되어 강조된 것을 보고 싶다. 헷갈리기 쉬운 두 키워드를 구분할 수 있기 때문이다.
23. 시청자로서, 체크 예외(처리 강제)와 언체크 예외(처리 선택)를 나란히 비교한 카드를 보고 싶다. 두 종류를 한눈에 구분할 수 있기 때문이다.
24. 시청자로서, `IOException`이 체크 예외의 대표라는 것을 듣고 싶다. 다음 편 파일 읽기·쓰기에서 왜 처리가 필수인지 미리 알 수 있기 때문이다.
25. 시청자로서, `class ScoreException extends Exception`으로 예외 클래스를 직접 만드는 코드를 보고 싶다. 커스텀 예외를 만드는 법을 알 수 있기 때문이다.
26. 시청자로서, 생성자에서 `super(message)`로 메시지를 부모에게 넘긴다는 것을 보고 싶다. `getMessage()`가 그 메시지를 돌려주는 이유를 알 수 있기 때문이다.
27. 시청자로서, `checkScore`가 `ScoreException`을 던지고 `catch (ScoreException e)`로 잡아 "점수 오류: 120"이 출력되는 것을 보고 싶다. 직접 만든 예외가 실제로 동작하는 것을 확인할 수 있기 때문이다.
28. 시청자로서, 예외 이름만 봐도 무슨 문제인지 알 수 있다는 커스텀 예외의 장점을 듣고 싶다. 왜 직접 만드는지 이해할 수 있기 때문이다.
29. 시청자로서, 처리를 강제하고 싶지 않으면 `RuntimeException`을 물려받는다는 한 줄을 보고 싶다. 두 가지 선택지를 알 수 있기 때문이다.
30. 시청자로서, 정리 장면에서 오늘 배운 키워드를 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
31. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
32. 시청자로서, 모바일 화면에서 코드와 출력이 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
33. 시청자로서, 화면에 나온 코드를 그대로 따라 쳐도 같은 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
34. 제작자로서, 화면의 모든 예제가 빌드 중에 실제로 컴파일·실행되어 대본의 기대 결과와 다르면 빌드가 멈추길 원한다. 틀린 내용을 올리지 않기 위해서다.
35. 제작자로서, 예외 문구와 컴파일 오류 문구가 실제 실행 결과로 그려지길 원한다. 화면에 손으로 적은 문구가 실제와 달라지지 않기 위해서다.
36. 제작자로서, 영상에 나온 예제 프로그램 전체가 예제 기록 파일로 남길 원한다. 시청자 질문에 같은 코드로 답할 수 있기 때문이다.
37. 제작자로서, 디자인·템포·자막 방식이 19편과 같길 원한다. 시리즈의 일관성을 지키기 위해서다.
38. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고 싶다. 시리즈 기록을 유지하기 위해서다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-exception-shorts`. 19편(스트림)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(`SPEED = 1.2`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 입문 <em>예외</em> 정리". 진행 표시는 5칸이다. 2-1은 2번째 칸, 4-1은 4번째 칸에 속한다.
- **용어** (GLOSSARY, 기획 단계에서 등록함): 예외, 컴파일 오류, try-catch, finally, throw, throws, 체크 예외, 언체크 예외, 커스텀 예외. 기존 용어 부모 클래스·자식 클래스·static 메소드를 그대로 쓴다.
  - 체크 예외에는 화면에 처음 한 번 "(처리 강제)", 언체크 예외에는 "(처리 선택)", 커스텀 예외에는 "(직접 만든 예외 클래스)"를 덧붙인다
  - "에러", "익셉션"(단독), "검사 예외", "사용자 정의 예외"는 쓰지 않는다
  - `Error`(메모리 부족 등)는 다루지 않는다
- **읽는 법** (대본은 한글 발음): 트라이 캐치, 파이널리, 쓰로우, 쓰로우즈, 익셉션 클래스 이름은 짧게(어리스메틱 익셉션, 넘버 포맷 익셉션 등). 화면에서 `throws`의 `s`를 주황으로 강조한다.
- **예시 데이터**: 민수 85(k1), 서준 92(k2), 지우 78(k3). 잘못된 점수는 `120`. 변환 예제의 정상 문자열은 `"85"`, 잘못된 문자열은 `"abc"`. 배열 예제는 `int[] scores = {85, 92, 78}`에 `scores[3]`.
- **checkScore의 발전** (한 메소드를 장면마다 바꿔 보여 줌)
  - throw: `static void checkScore(int score)` 안에서 0 미만·100 초과면 `IllegalArgumentException("점수 오류: " + score)`
  - throws: `Exception`으로 바꾸면 컴파일 오류 → 선언에 `throws Exception` 추가 → 부르는 쪽에 `try-catch`
  - custom: `Exception`을 `ScoreException`으로 교체
  - 33자 제한 때문에 선언 줄은 `throws` 앞에서 줄을 바꾼다
- **장면별 기대 결과** (기획 단계에서 로컬 OpenJDK 25, 영문 로케일로 확인한 문구. 대조 기준)
  - 실행 중 예외: hook — 출력 없이 `java.lang.ArithmeticException: / by zero` (다음 줄 출력 없음)
  - 출력: trycatch — 처리 문구 + "끝" / kinds — `For input string: "abc"`, `Index 3 out of bounds for length 3` / finally — 두 실행 모두 "끝" 포함 / throw·throws·custom — `점수 오류: 120`
  - 컴파일 오류: order — `exception ArithmeticException has already been caught` / throws — `unreported exception Exception; must be caught or declared to be thrown`
- **컴파일·실행 헬퍼**: 19편의 출력 대조, 실행 중 오류 대조, 컴파일 오류 대조 헬퍼를 그대로 쓴다. 확장은 하나: `checkScore` 같은 `static` 메소드를 `Main` 클래스 안(`main` 바깥)에 둘 수 있게 한다. `ScoreException`처럼 `Main` 바깥 클래스는 지금처럼 클래스 위쪽에 넣는다. 화면에 선언을 보여 줄지 숨길지는 장면마다 정한다.
- **화면의 출력·오류 상자**: 헬퍼가 얻은 실제 결과로 그린다. 실행 중 예외 상자는 예외 이름과 메시지를 줄을 나눠 보여 준다(19편 방식).
- **사실 표현 주의**
  - "`Exception`은 모든 예외의 부모"는 이 영상 범위(`Error` 제외)에서만 맞으므로 "예외 클래스들의 부모"처럼 말한다
  - `finally`는 "예외가 나든 안 나든 실행"까지만 말하고, `System.exit` 같은 예외 상황은 다루지 않는다
  - 체크 예외 처리는 "try-catch로 잡거나 throws로 넘긴다" 두 가지를 함께 말한다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 실제로 컴파일·실행한 예제의 출력, 실행 중 예외 문구, 컴파일 오류 문구가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 빌드 자체. 19편 빌드의 대조 헬퍼를 그대로 쓰고 새 테스트 지점은 만들지 않는다. `static` 메소드 지원은 기존 헬퍼의 확장이다.
- **대조 항목**
  - 실행 중 예외 대조(1건): hook(앞선 출력 없음 포함)
  - 출력 대조: trycatch, kinds, finally(두 실행), throw, throws(처리 뒤), custom
  - 컴파일 오류 대조(2건): order, throws(처리 전)
  - 기대와 다르면 빌드를 멈춘다
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(throws 또는 custom)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "끝까지 실행돼요", "점수 오류 백이십"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 19편 once 장면(실행 중 오류 대조), 14편 다형성의 다운캐스팅 오류 장면, 컴파일 오류 대조를 쓴 접근 제어자·추상 클래스 편.

## Out of Scope

- `Error`와 `Throwable`, 예외 클래스 계층도 전체
- 멀티 catch(`catch (A | B e)`)
- try-with-resources (21편에서 처음 소개)
- `e.printStackTrace()`와 스택 트레이스 읽는 법
- 예외 다시 던지기, 예외 감싸기(cause)
- `NullPointerException`, `ClassCastException` 같은 다른 예외 종류의 자세한 소개
- `finally`가 실행되지 않는 예외 상황(`System.exit` 등)
- 파일 입출력 예제(21편)
- 디자인·템포·제작 도구의 변경

## Further Notes

- 시리즈 순서: … → 람다식(18) → 스트림(19) → 예외(20) → 텍스트 파일 읽기·쓰기(21). 21편은 이 편의 체크 예외와 `throws`를 이어서 쓴다.
- 기획 때 STEP 6개(try-catch, 여러 catch, finally, throw, throws·체크 예외, 커스텀 예외)로 합의했으나, 진행 표시가 5칸이라 throw와 throws를 STEP 4 한 칸에 묶었다. 장면 순서는 합의한 그대로다.
- 기획 중 확인한 출력과 오류 문구는 로컬 OpenJDK 25.0.4(영문 로케일) 기준이다.
- 유튜브 제목 형식: "자바 입문 20편: 예외 | try-catch · finally · throw · throws · 커스텀 예외" (꺾쇠 금지).
- 커밋·푸시는 사용자가 요청할 때만 한다.
