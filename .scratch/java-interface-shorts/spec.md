# 스펙: 자바 입문 열세 번째 — 인터페이스

Status: resolved

## Problem Statement

자바 입문 시리즈 시청자는 상속 편에서 `extends`로 부모 클래스를 **하나만** 물려받을 수 있다는 것(단일 상속)을 배웠고, 지난 편에서는 추상 메소드로 자식 클래스에게 오버라이딩을 강제하는 법을 배웠다. 그런데 "선생님은 가르치기도 하고 공부도 한다"처럼 한 클래스가 여러 능력을 약속해야 할 때는 부모 클래스를 둘 둘 수 없어 막힌다.

입문자가 인터페이스에서 특히 자주 헷갈리는 점은 다음과 같다.

- 인터페이스를 왜 쓰는지, 추상 클래스와 무엇이 다른지
- `implements`의 문법, 그리고 `extends`와 함께 쓰는 순서
- 인터페이스 메소드를 구현할 때 `public`을 빼면 왜 컴파일 오류가 나는지(가장 흔한 오류)
- 인터페이스에 적은 필드가 왜 바꿀 수 없는 상수가 되는지
- 몸체가 있는 `default` 메소드가 인터페이스 안에 있어도 되는지

3분 이하 세로 쇼츠 한 편으로, 실제로 컴파일·실행되는 예제를 써서 이 개념들을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열세 번째 영상 "인터페이스"를 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 예시 클래스: 12편의 추상 클래스 `Person` → `Student`(민수·85) / `Teacher`(서준)를 그대로 이어 쓰고, 인터페이스 `Studyable`·`Teachable`을 새로 만든다.
- 흐름: 단일 상속의 한계 → 인터페이스 선언 → 구현과 강제 → 여러 개 구현 → 상수와 new 불가 → default 메소드 → 추상 클래스와 비교
- 부모·인터페이스 타입 변수에 객체를 담는 것(`Studyable x = new Student(...)`)은 다음 편(다형성)에서 다루므로, 이번 편 예제는 모두 자기 클래스 타입 변수만 쓴다.

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열세 번째, 인터페이스"라는 주제를 바로 알고 싶다. 따라오던 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 12편의 `Person`·`Student`·`Teacher`, 민수·서준이 다시 나오길 바란다. 앞에서 배운 코드 위에 새 개념을 쌓을 수 있기 때문이다.
3. 시청자로서, 서준이 "가르치기"와 "공부하기" 두 능력을 가져야 하는 상황을 보고 싶다. 인터페이스가 필요한 이유를 구체적인 장면으로 이해할 수 있기 때문이다.
4. 시청자로서, 능력마다 부모 클래스를 두려 해도 `extends`는 하나만 된다는 것을 다시 확인하고 싶다. 상속 편의 단일 상속 규칙과 이번 편이 연결되기 때문이다.
5. 시청자로서, `interface Studyable { void study(); }`의 모양을 보고 싶다. 클래스 선언과 무엇이 다른지 한눈에 알 수 있기 때문이다.
6. 시청자로서, 인터페이스를 "구현 클래스가 갖출 메소드를 적은 약속 목록"으로 설명 듣고 싶다. 문법보다 역할을 먼저 이해할 수 있기 때문이다.
7. 시청자로서, 인터페이스 메소드는 따로 적지 않아도 `public abstract`라는 것을 알고 싶다. 뒤에 나오는 `public` 필수 규칙의 이유가 되기 때문이다.
8. 시청자로서, `class Student extends Person implements Studyable`처럼 `extends` 뒤에 `implements`가 온다는 순서를 보고 싶다. 두 키워드를 함께 쓸 때 헷갈리지 않기 때문이다.
9. 시청자로서, Student가 `study()`를 구현해 `민수 공부 중`이 출력되는 것을 보고 싶다. 인터페이스 메소드가 구현 클래스에서 완성되는 모습을 결과로 볼 수 있기 때문이다.
10. 시청자로서, 구현한 메소드에도 `@Override`가 붙어 있길 바란다. 앞 편들에서 배운 표기와 이어지기 때문이다.
11. 시청자로서, Student가 `study()`를 빠뜨리면 컴파일 오류가 나는 것을 보고 싶다. 인터페이스도 추상 메소드처럼 구현을 강제한다는 것을 확인할 수 있기 때문이다.
12. 시청자로서, 구현 메소드에서 `public`을 빼면 컴파일 오류가 나는 것을 보고 싶다. 실제로 가장 많이 겪는 오류를 미리 알 수 있기 때문이다.
13. 시청자로서, 그 오류의 이유를 "인터페이스 메소드는 원래 public이라 더 좁힐 수 없다"로 듣고 싶다. 규칙을 외우지 않고 이유로 이해할 수 있기 때문이다.
14. 시청자로서, Teacher가 `implements Teachable, Studyable`로 인터페이스 두 개를 쉼표로 구현하는 것을 보고 싶다. 여러 능력을 한 클래스에 갖추는 방법을 알 수 있기 때문이다.
15. 시청자로서, Teacher가 `서준 수업 중`과 `서준 공부 중`을 모두 출력하는 것을 보고 싶다. 두 인터페이스가 모두 구현되었음을 결과로 확인할 수 있기 때문이다.
16. 시청자로서, "클래스 상속은 하나, 인터페이스 구현은 여러 개"라는 대비를 듣고 싶다. why 장면의 문제가 해결되었음을 알 수 있기 때문이다.
17. 시청자로서, 인터페이스에 적은 `int MAX_HOURS = 8;`이 자동으로 `public static final` 상수가 된다는 것을 알고 싶다. 인터페이스에 필드를 둘 때 생기는 일을 정확히 알 수 있기 때문이다.
18. 시청자로서, `Studyable.MAX_HOURS`로 값 `8`을 읽는 것을 보고 싶다. 상수를 인터페이스 이름으로 쓴다는 것을 알 수 있기 때문이다.
19. 시청자로서, `Studyable.MAX_HOURS = 9;`가 컴파일 오류라는 것을 보고 싶다. 11편의 `static final` 상수와 같은 규칙임을 연결할 수 있기 때문이다.
20. 시청자로서, `new Studyable()`이 컴파일 오류라는 것을 보고 싶다. 인터페이스도 추상 클래스처럼 객체를 만들 수 없음을 확인할 수 있기 때문이다.
21. 시청자로서, `default` 메소드로 인터페이스 안에 몸체 있는 메소드를 둘 수 있다는 것을 보고 싶다. "인터페이스는 몸체 없는 메소드만"이라는 오해를 풀 수 있기 때문이다.
22. 시청자로서, Student가 `rest()`를 구현하지 않아도 `s.rest()`로 `쉬는 중`이 출력되는 것을 보고 싶다. default 메소드는 구현이 강제되지 않고 그대로 물려받는다는 것을 알 수 있기 때문이다.
23. 시청자로서, 추상 클래스와 인터페이스를 나란히 비교한 카드를 보고 싶다. 둘 중 무엇을 언제 쓰는지 정리할 수 있기 때문이다.
24. 시청자로서, 비교 카드에서 "extends 하나 vs implements 여럿", "필드·생성자 vs 상수만", "일반 메소드 vs default 메소드" 세 가지 차이를 보고 싶다. 핵심 차이만 짧게 기억할 수 있기 때문이다.
25. 시청자로서, 정리 장면에서 여섯 가지 핵심을 목록으로 한꺼번에 보고, 나레이션이 말하는 줄이 강조되길 바란다. 복습하면서 따라 읽을 수 있기 때문이다.
26. 시청자로서, 모든 자막이 나레이션과 단어 단위로 맞길 바란다. 소리 없이 보더라도 내용을 따라갈 수 있기 때문이다.
27. 시청자로서, 휴대폰 화면에서도 코드가 읽히길 바란다. 쇼츠는 대부분 휴대폰으로 보기 때문이다.
28. 제작자로서, 화면의 모든 예제가 실제로 컴파일·실행되어 대본의 결과와 같은지 빌드가 확인하길 바란다. 틀린 코드를 올리는 일을 막을 수 있기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-interface-shorts`. 직전 영상(추상 메소드와 추상 클래스)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 출력 대조·컴파일 오류 대조·컴파일 성공 확인 헬퍼를 그대로 쓴다. 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 입문 인터페이스 정리", "인터페이스"는 주황 강조. 진행 표시 5칸, 2-1·2-2는 2번째 칸, 5-1은 5번째 칸에 속한다.
- **예시 데이터** (영상 전체에서 하나로 통일)
  - `Person` (k1): 12편 그대로의 추상 클래스. 필드 `String name`, 생성자 `Person(String name)`, 추상 메소드 `hello()`, 일반 메소드 `bye()`. 이번 편에서는 화면에 거의 보이지 않고, 숨김 줄로 완전한 프로그램을 만든다.
  - `Student` (k2): `extends Person implements Studyable`, 필드 `int score`, `hello()` → `"학생 " + name + " 안녕"`, `public void study()` → `name + " 공부 중"`. 객체는 민수·85.
  - `Teacher` (k3): `extends Person implements Teachable, Studyable`, `hello()` → `name + " 선생님 안녕"`, `public void teach()` → `name + " 수업 중"`, `public void study()` → `name + " 공부 중"`. 객체는 서준.
  - `Studyable` (인터페이스): 상수 `int MAX_HOURS = 8;`, 메소드 `void study();`, `default void rest()` → `"쉬는 중"`. decl 장면에서는 `study()`만, rules 장면에서 상수, dflt 장면에서 `rest()`를 보여 준다(앞 장면에서는 숨김).
  - `Teachable` (인터페이스): 메소드 `void teach();`.
  - 인터페이스는 k1~k3과 겹치지 않는 표시(파란 테두리)를 쓴다. Studyable과 Teachable은 같은 표시를 쓰고 이름으로 구분한다.
- **장면별 기대 결과**
  - impl: `민수 공부 중`
  - multi: `서준 수업 중`, `서준 공부 중` 두 줄
  - rules: `8`
  - dflt: `쉬는 중`
  - 컴파일 오류 예제와 javac 오류 문구(대조 기준, 기획 단계에서 로컬 javac 25로 확인함):
    - miss: `Student is not abstract and does not override abstract method study() in Studyable`
    - pub: `study() in Student cannot implement study() in Studyable` (다음 줄: `attempting to assign weaker access privileges; was public`)
    - rules(재대입): `cannot assign a value to static final variable MAX_HOURS` — 11편의 `final variable` 문구와 다르다는 점에 주의
    - rules(new): `Studyable is abstract; cannot be instantiated`
- **장면 구성 요소**
  - why는 코드 없이 보여 준다. Teacher에서 "가르치기"·"공부하기" 두 부모로 가는 그림에 ✗ 표시, `extends는 하나만` 경고로 구성한다. (`extends Person, Worker`의 javac 오류는 `'{' expected`라 설명에 도움이 되지 않아 쓰지 않는다.)
  - pub는 오류 예제 아래에 "인터페이스 메소드 = 자동 public" 메모를 둔다.
  - multi는 "extends 하나 · implements 여럿" 칩을 함께 보여 준다.
  - rules는 두 오류(재대입, `new`)를 한 장면에 담으므로 코드를 짧게 줄인다. 공간이 부족하면 결과 칩으로 대체한다.
  - vs는 두 개념 비교 카드(`.vs`)를 세 줄로 쓴다.
- **대본**
  - 영어 키워드는 한글 발음으로 쓴다(인터페이스, 임플리먼츠, 익스텐즈, 스터디어블, 티처블, 스터디, 티치, 레스트, 퍼블릭, 디폴트, 뉴, 맥스 아워즈, 앱스트랙트, 퍼슨, 스튜던트, 티처).
  - 용어는 GLOSSARY를 따른다. 인터페이스 메소드는 "구현한다"로 말하고 "오버라이딩한다"고 하지 않는다. Student·Teacher는 인터페이스의 "구현 클래스"이지 "자식 클래스"가 아니다.
  - 길이는 대본 전체를 먼저 써서 확인하고, 3분을 넘으면 음성 생성 전에 줄인다.
- **정리 장면 6줄**
  1. 인터페이스 → 갖출 메소드의 약속 목록
  2. `implements`로 구현, 빠뜨리면 오류
  3. 구현 메소드는 `public` 필수
  4. 인터페이스는 여러 개 구현 가능
  5. 필드는 상수, `new` 불가
  6. `default`로 몸체 있는 메소드

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 예제의 실제 출력, 실제 컴파일 오류가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 기존 빌드 과정의 Java 예제 검증을 그대로 쓴다. 빌드는 장면마다 예제를 실제 JDK로 컴파일·실행하고, 기대와 다르면 멈춘다. 새 테스트 지점은 만들지 않는다.
- **대조 항목**
  - 출력 대조(4건): impl `민수 공부 중`, multi 두 줄, rules `8`, dflt `쉬는 중`
  - 컴파일 오류 대조(4건): `study()` 빠뜨림, `public` 누락, 상수 재대입, 인터페이스 `new`
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다.
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(multi 또는 rules)을 390px 폭으로 줄여 모바일 가독성을 확인한다.
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다.
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재.
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "서준 수업 중, 서준 공부 중이 나와요"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 12편의 추상 메소드 강제 오류(omiss)와 `new` 불가(anew) 장면, 11편의 상수 재대입 오류 장면.

## Out of Scope

- 인터페이스 타입 변수에 객체 담기(`Studyable x = new Student(...)`), 업캐스팅, 다형성 — 14편에서 다룬다. 이번 편에서는 예고도 하지 않는다
- 인터페이스의 `static` 메소드·`private` 메소드
- 인터페이스끼리 `extends`
- 함수형 인터페이스와 람다
- 두 인터페이스의 `default` 메소드 이름이 겹칠 때의 규칙
- 접근 제어자 전반(`public` 외 `protected`·`private`)
- 디자인·템포·제작 도구의 변경
