# 스펙: 자바 입문 열여덟 번째 — 람다식

Status: resolved

## Problem Statement

시청자는 13편에서 인터페이스와 `implements`를, 17편에서 `List`를 배웠다. 하지만 "80점 이상인지 검사하는 기능" 하나를 넘기려 해도 인터페이스를 구현한 클래스를 따로 만들고, 객체를 `new`로 만들어야 한다. 실무 코드와 자바 라이브러리에는 `s -> s >= 80` 같은 람다식이 계속 나오는데, 시리즈에서는 아직 한 번도 다루지 않았다.

입문자가 람다식을 처음 볼 때 특히 막히는 점은 다음과 같다.

- `->`가 무엇이고, 람다식의 어디가 매개변수이고 어디가 몸체인지
- 괄호·타입·`{ return ; }`을 언제 생략할 수 있는지. 매개변수가 0개나 2개면 괄호를 꼭 써야 한다는 것
- 아무 인터페이스에나 람다식을 담을 수 없고, 추상 메소드가 하나뿐인 함수형 인터페이스여야 한다는 것
- `Predicate`처럼 자바가 미리 만들어 둔 함수형 인터페이스가 있다는 것
- `forEach`·`removeIf`·`sort`에 람다식을 넘겨 리스트를 다루는 방법
- 람다식 안에서 쓰는 바깥 지역 변수의 값을 바꾸면 컴파일 오류가 난다는 것(사실상 final)
- `System.out::println` 같은 메소드 참조가 무엇인지

3분 이하 세로 쇼츠 한 편으로, 실제로 컴파일·실행한 결과와 오류로 이 내용을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열여덟 번째 영상 "람다식"을 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 흐름: 13편 방식(구현 클래스)에서 출발해 람다식 한 줄로 줄이고, 문법·규칙을 배운 뒤, 17편의 리스트에 람다식을 써 본다
- 익명 클래스는 거치지 않는다. 구현 클래스에서 람다식으로 바로 넘어간다
- 예시 데이터: 17편과 같은 이름 민수·서준·지우, 점수 85·92·78

장면 구성은 아래와 같다.

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | – | 자바 입문 열여덟 번째, 람다식. 큰 제목 `s -> s >= 80`(`->` 주황) |
| why | 1. 왜 필요한가 | 1 | `interface Checker { boolean check(int s); }`를 구현 클래스(`implements`)로 만든 여러 줄 코드 → `Checker c = s -> s >= 80;` 한 줄. `c.check(85)` → `true`, `c.check(78)` → `false` |
| syntax | 2. 문법 | 2 | `(int s) -> { return s >= 80; }`를 매개변수 · 화살표 · 몸체로 나눠 표시. 6편 화살표 switch의 `->`와 같은 기호, 다른 뜻(`.note`) |
| short | 2-1. 줄여 쓰기 | 2 | 타입 생략 `(s) -> { return s >= 80; }` → 괄호 생략 `s -> { … }` → 식 하나면 `{ return ; }` 생략 `s -> s >= 80`. 매개변수가 0개 `() -> …`나 2개 `(a, b) -> …`면 괄호를 꼭 쓴다 |
| fi | 3. 함수형 인터페이스 | 3 | `Checker`에 추상 메소드를 하나 더 넣으면 람다식에 담을 때 컴파일 오류(`.warn`). 추상 메소드가 딱 하나인 인터페이스 = 함수형 인터페이스. `@FunctionalInterface`를 붙이면 인터페이스 쪽에서 바로 오류로 알려 준다 |
| pred | 3-1. Predicate | 3 | 자바가 미리 만들어 둔 함수형 인터페이스 `Predicate<Integer>`(`import java.util.function.Predicate;`). `Checker`를 직접 만들지 않아도 된다. `p.test(85)` → `true` |
| each | 4. forEach | 4 | `names`에 `add` 세 번(민수·서준·지우) → `names.forEach(n -> System.out.println(n));` → 민수·서준·지우 세 줄 |
| rmif | 4-1. removeIf | 4 | `scores`에 `add` 세 번(85·92·78) → `scores.removeIf(s -> s < 80);` → `[85, 92]`. 78이 빠진다 |
| sort | 4-2. sort | 4 | 새 `scores`(85·92·78) → `scores.sort((a, b) -> b - a);` → `[92, 85, 78]`. 빼기 결과로 순서를 정한다(오름차순은 `a - b`) |
| final | 5. 사실상 final | 5 | `int pass = 80; pass = 90;` 뒤에 람다식에서 `pass`를 쓰면 컴파일 오류(`.warn`). 람다식 안에서 쓰는 바깥 지역 변수는 값을 바꾸면 안 된다 |
| ref | 5-1. 메소드 참조 맛보기 | 5 | `names.forEach(n -> System.out.println(n));`와 `names.forEach(System.out::println);`를 나란히 보여 주고, 결과가 같다(민수·서준·지우) |
| outro | 정리 | – | 목록 전체 → 나레이션에 맞춰 줄 강조 → 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열여덟 번째, 람다식"이라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 `s -> s >= 80` 같은 람다식의 생김새를 먼저 보고 싶다. 오늘 무엇을 읽을 수 있게 되는지 알 수 있기 때문이다.
3. 시청자로서, 13편에서 배운 방식(인터페이스 + 구현 클래스 + `new`)으로 같은 기능을 만든 코드를 보고 싶다. 람다식이 무엇을 줄여 주는지 비교할 수 있기 때문이다.
4. 시청자로서, 여러 줄의 구현 클래스 코드가 `Checker c = s -> s >= 80;` 한 줄로 바뀌는 것을 보고 싶다. 람다식이 왜 필요한지 납득할 수 있기 때문이다.
5. 시청자로서, 람다식으로 만든 `c`도 `c.check(85)`처럼 똑같이 호출하고 `true`·`false`가 나오는 것을 보고 싶다. 람다식도 인터페이스를 구현한 객체라는 것을 결과로 확인할 수 있기 때문이다.
6. 시청자로서, 람다식이 매개변수 · 화살표 · 몸체 세 부분으로 나뉜다는 것을 색으로 구분해 보고 싶다. 처음 보는 문법을 읽는 순서를 알 수 있기 때문이다.
7. 시청자로서, `->`를 "화살표"라고 부른다는 것을 듣고 싶다. 코드를 말로 읽을 수 있기 때문이다.
8. 시청자로서, 6편 화살표 switch의 `->`와 같은 기호지만 뜻이 다르다는 메모를 보고 싶다. 두 문법을 헷갈리지 않기 때문이다.
9. 시청자로서, 매개변수 타입을 생략해도 된다는 것을 단계별로 보고 싶다. 실무 코드에 타입이 없어도 당황하지 않기 때문이다.
10. 시청자로서, 매개변수가 하나면 괄호를 생략할 수 있다는 것을 보고 싶다. `s ->`와 `(s) ->`가 같다는 것을 알 수 있기 때문이다.
11. 시청자로서, 몸체가 식 하나면 `{ return ; }`을 생략할 수 있다는 것을 보고 싶다. 가장 짧은 형태가 어떻게 나왔는지 이해할 수 있기 때문이다.
12. 시청자로서, 매개변수가 0개나 2개면 괄호를 꼭 써야 한다는 것을 보고 싶다. 괄호를 언제나 생략할 수 있다고 오해하지 않기 때문이다.
13. 시청자로서, 추상 메소드가 두 개인 인터페이스에 람다식을 담으면 컴파일 오류가 나는 것을 실제 오류 문구로 보고 싶다. 람다식에 규칙이 있다는 것을 알 수 있기 때문이다.
14. 시청자로서, 추상 메소드가 하나뿐인 인터페이스를 함수형 인터페이스라고 부른다는 것을 듣고 싶다. 용어와 조건을 함께 기억할 수 있기 때문이다.
15. 시청자로서, `@FunctionalInterface`를 붙이면 인터페이스 쪽에서 바로 오류를 알려 준다는 것을 보고 싶다. 실수를 일찍 잡는 방법을 알 수 있기 때문이다.
16. 시청자로서, 자바가 `Predicate`라는 함수형 인터페이스를 미리 만들어 뒀다는 것을 보고 싶다. `Checker`를 매번 직접 만들 필요가 없다는 것을 알 수 있기 때문이다.
17. 시청자로서, `Predicate`를 쓰려면 `import java.util.function.Predicate;`가 필요하다는 것을 보고 싶다. 15편 import와 이어지기 때문이다.
18. 시청자로서, `Predicate<Integer>`의 꺾쇠가 17편에서 배운 "담을 타입"과 같은 문법이라는 것을 알고 싶다. 배운 것을 연결할 수 있기 때문이다.
19. 시청자로서, `p.test(85)`가 `true`를 돌려주는 것을 보고 싶다. `Checker`의 `check` 대신 `test`를 부른다는 것을 알 수 있기 때문이다.
20. 시청자로서, 17편처럼 `add`로 이름을 넣는 줄을 화면에서 보고 싶다. 리스트가 어떻게 만들어졌는지 알고 따라 칠 수 있기 때문이다.
21. 시청자로서, `forEach`에 람다식을 넘겨 이름이 한 줄씩 출력되는 것을 보고 싶다. 향상된 for 없이도 리스트를 돌 수 있다는 것을 알 수 있기 때문이다.
22. 시청자로서, `removeIf(s -> s < 80)`이 78을 지워 `[85, 92]`가 되는 것을 보고 싶다. 조건으로 지우는 방법을 결과로 확인할 수 있기 때문이다.
23. 시청자로서, `removeIf`의 람다식이 "지울 조건"이라는 것을 듣고 싶다. 남길 조건으로 착각하지 않기 때문이다.
24. 시청자로서, `sort((a, b) -> b - a)`가 `[92, 85, 78]`로 정렬하는 것을 보고 싶다. 람다식으로 정렬 순서를 정할 수 있다는 것을 알 수 있기 때문이다.
25. 시청자로서, 오름차순은 `a - b`라는 것을 함께 보고 싶다. 반대 순서도 바로 쓸 수 있기 때문이다.
26. 시청자로서, 매개변수가 두 개인 `sort`의 람다식에서 괄호가 꼭 필요하다는 것을 다시 보고 싶다. 앞에서 배운 규칙을 실제 예로 확인할 수 있기 때문이다.
27. 시청자로서, 람다식에서 쓰는 바깥 지역 변수의 값을 바꾸면 컴파일 오류가 나는 것을 실제 오류 문구로 보고 싶다. 직접 같은 오류를 만났을 때 원인을 알 수 있기 때문이다.
28. 시청자로서, 값을 바꾸지 않으면 `final`을 안 붙여도 된다는 것("사실상 final")을 듣고 싶다. 꼭 `final`을 붙여야 한다고 오해하지 않기 때문이다.
29. 시청자로서, `System.out::println`이 `n -> System.out.println(n)`과 같은 결과라는 것을 나란히 보고 싶다. 실무 코드의 `::`를 처음 봐도 읽을 수 있기 때문이다.
30. 시청자로서, 같은 학생·점수는 모든 장면에서 같은 색으로 보고 싶다. 리스트가 바뀔 때 무엇이 빠지고 움직였는지 따라갈 수 있기 때문이다.
31. 시청자로서, 정리 장면에서 오늘 배운 내용을 한 화면에 보고 싶다. 영상을 다시 보지 않아도 복습할 수 있기 때문이다.
32. 시청자로서, 나레이션이 말하는 순간 정리 항목이 강조되길 바란다. 어디를 읽어야 할지 따라갈 수 있기 때문이다.
33. 시청자로서, 화면의 모든 출력과 오류가 실제로 실행한 결과이길 바란다. 직접 따라 쳤을 때 같은 결과가 나와야 믿을 수 있기 때문이다.
34. 시청자로서, 휴대폰 화면에서도 코드를 읽을 수 있길 바란다. 쇼츠는 주로 휴대폰으로 보기 때문이다.
35. 시청자로서, 나레이션과 단어 단위로 맞는 한국어 자막을 보고 싶다. 소리 없이 봐도 이해할 수 있기 때문이다.
36. 제작자로서, 화면의 결과나 오류가 대본과 다르면 빌드가 멈추길 바란다. 틀린 내용을 올리는 실수를 막을 수 있기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-lambda-shorts`. 17편(래퍼 클래스와 List)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 <em>람다식</em> 정리" 형태로 "람다식"을 주황으로 강조한다. 진행 표시는 5칸이다. 2-1은 2번째 칸, 3-1은 3번째 칸, 4-1·4-2는 4번째 칸, 5-1은 5번째 칸에 속한다.
- **용어** (GLOSSARY): 람다식, 화살표, 함수형 인터페이스(기획 단계에서 등록함). 기존 용어 인터페이스·구현 클래스·구현·리스트·ArrayList·담을 타입·import를 그대로 쓴다.
  - "람다 함수", "익명 함수", "람다 연산자", "SAM 타입"은 쓰지 않는다
  - "사실상 final"과 "메소드 참조"는 이번 편에서 한 장면씩만 쓰므로 GLOSSARY에 올리지 않는다. 화면에는 "사실상 final(값을 안 바꾸는 변수)"처럼 처음 한 번 풀어 쓴다
- **예시 데이터** (영상 전체에서 하나로 통일)
  - 인터페이스: `interface Checker { boolean check(int s); }`, 기준은 80점 이상
  - 이름: 민수(k1), 서준(k2), 지우(k3). `names` 리스트의 순서도 이 순서다
  - 점수: 85, 92, 78. `scores` 리스트의 순서도 이 순서다. 점수 색은 사람을 따라간다(85=k1, 92=k2, 78=k3). 정렬 뒤에도 색은 값을 따라간다
  - 리스트는 17편처럼 `List<…> x = new ArrayList<>();`와 `add` 줄을 화면에 보여 준다(한 줄에 하나). 핵심 람다식 줄만 주황으로 강조한다
  - removeIf와 sort는 각각 새 리스트 `[85, 92, 78]`에서 시작한다
- **장면별 기대 결과** (기획 단계에서 로컬 JDK 25, 영문 로케일로 확인함. 대조 기준)
  - 출력
    - why: `true false`(`c.check(85)`, `c.check(78)`)
    - pred: `true`
    - each: `민수`, `서준`, `지우` 세 줄
    - rmif: `[85, 92]`
    - sort: `[92, 85, 78]`
    - ref: `민수`, `서준`, `지우` 세 줄(람다식 버전과 같음)
  - 컴파일 오류(첫 오류와 그 아래 설명 줄)
    - fi(람다식에 담기): `incompatible types: Checker is not a functional interface`, 설명 줄 `multiple non-overriding abstract methods found in interface Checker`
    - fi(`@FunctionalInterface`): `Unexpected @FunctionalInterface annotation`, 설명 줄 `Checker is not a functional interface`. 화면 공간이 부족하면 둘 중 람다식 오류를 크게, 이 오류는 한 줄 메모로 보여 준다
    - final: `local variables referenced from a lambda expression must be final or effectively final`
- **컴파일·실행 헬퍼**: 17편의 컴파일·실행 대조 헬퍼(출력 대조)와 컴파일 오류 대조 헬퍼를 그대로 쓴다. 이번 편은 실행 중 오류 장면이 없다. 화면의 출력·오류 콘솔은 헬퍼가 얻은 실제 결과로 그린다. 모든 예제는 예제 기록 파일에 남긴다.
- **사실 표현 주의**
  - "람다식은 함수형 인터페이스를 구현한 객체를 만든다"로 말한다. "람다식은 함수다"처럼 단정하지 않는다
  - 함수형 인터페이스는 "추상 메소드가 딱 하나"로 말한다. `default` 메소드는 있어도 된다는 예외는 다루지 않지만, "메소드가 하나"라고 말하지 않는다
  - `b - a` 정렬은 "빼기 결과로 순서를 정한다"로 말한다. 음수·양수 규칙을 단정적인 공식처럼 말하지 않고, 아주 큰 수의 넘침은 다루지 않는다(점수에는 문제없음)
  - 사실상 final은 "람다식 안에서 쓰는 바깥 지역 변수는 값을 바꾸면 안 된다"로 말한다. 필드에는 해당하지 않으므로 "지역 변수"를 꼭 붙인다
  - 메소드 참조는 "람다식을 더 짧게 쓰는 방법" 정도로만 소개하고 종류(정적·인스턴스·생성자 참조)는 다루지 않는다
- **장면 구성 요소**
  - why는 위아래 두 코드 블록(구현 클래스 코드 → 람다식 한 줄) 비교, 줄 수 차이를 강조
  - syntax는 한 줄 코드를 세 부분으로 색칠하고 아래에 이름표(매개변수 · 화살표 · 몸체), 6편 연결은 `.note`
  - short는 단계별로 한 줄씩 짧아지는 코드 세 줄 + 괄호 필수 규칙 칩(`()`·`(a, b)`)
  - fi·final 오류는 `.warn`, 결과는 코드 블록 아래 콘솔
  - ref는 두 줄을 `.vs` 카드로 나란히 보여 준다
  - 코드 한 줄은 33자 이하. `List<Integer> scores = new ArrayList<>();`처럼 긴 줄은 `=` 뒤에서 줄바꿈한다. `names.forEach(n -> System.out.println(n));`도 33자를 넘으므로 화살표 뒤에서 줄바꿈한다
- **대본**
  - 영어 키워드는 한글 발음으로 쓴다(람다식, 화살표, 체커, 체크, 리턴, 함수형 인터페이스, 펑셔널 인터페이스, 프레디킷, 테스트, 임포트, 리스트, 어레이리스트, 애드, 포이치, 리무브이프, 소트, 시스템 닷 아웃 닷 프린트엘엔, 파이널, 메소드 참조)
  - 길이는 대본 전체를 먼저 써서 확인하고, 3분을 넘으면 음성 생성 전에 줄인다
- **정리 장면** (7줄 안팎, 대본 작성 때 확정)
  1. 람다식: `(매개변수) -> 몸체`, 구현 클래스를 한 줄로
  2. 줄여 쓰기: 타입·괄호·`{ return ; }` 생략, 0개·2개면 괄호 필수
  3. 함수형 인터페이스: 추상 메소드가 딱 하나
  4. `Predicate`: 자바가 미리 만든 함수형 인터페이스, `test`
  5. 리스트: `forEach`·`removeIf`·`sort`에 람다식을 넘긴다
  6. 람다식 안의 바깥 지역 변수는 값을 바꾸지 않는다
  7. `System.out::println` = 메소드 참조

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 실제로 컴파일·실행한 예제의 출력과 javac의 실제 오류 문구가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 17편 빌드의 컴파일·실행 대조 헬퍼와 컴파일 오류 대조 헬퍼를 그대로 쓴다. 새 테스트 지점은 만들지 않는다.
- **대조 항목**
  - 출력 대조(6건): why, pred, each, rmif, sort, ref
  - 컴파일 오류 대조(3건): fi 람다식 담기, fi `@FunctionalInterface`, final
  - 기대와 다르면(출력이 다르거나, 기대한 오류가 안 나거나, 다른 오류가 나면) 빌드를 멈춘다
  - syntax·short 장면의 코드 조각(타입 생략, 괄호 생략, 0개·2개 매개변수)도 숨긴 `main`으로 감싸 실제로 컴파일되는지 확인한다
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(why 또는 sort)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "칠십팔이 빠져요", "구십이, 팔십오, 칠십팔 순서"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 17편 빌드의 컴파일·실행·컴파일 오류 대조 헬퍼, 13편 인터페이스의 구현 클래스 장면, 14편의 `.vs` 비교 장면.
