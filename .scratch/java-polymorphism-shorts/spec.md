# 스펙: 자바 입문 열네 번째 — 다형성

Status: resolved

## Problem Statement

자바 입문 시리즈 시청자는 상속·오버라이딩(10편), 추상 클래스(12편), 인터페이스(13편)를 배웠다. 하지만 지금까지는 `Student s = new Student(...)`처럼 언제나 자기 클래스 타입 변수만 썼다. 그래서 "부모 클래스를 왜 만들고, 오버라이딩은 어디에 쓰이는가"라는 질문의 답을 아직 못 봤다. 그 답이 다형성이다.

입문자가 다형성에서 특히 자주 헷갈리는 점은 다음과 같다.

- `Person p = new Student(...)`처럼 변수 타입과 객체 타입이 달라도 되는 이유
- `p.hello()`를 부르면 Person의 것인지 Student의 것인지
- 다형성이 실제로 어디에 쓸모 있는지(배열, 매개변수)
- 부모 타입 변수로 자식의 필드를 왜 못 쓰는지
- 다운캐스팅은 언제 필요하고, 잘못하면 무슨 일이 생기는지
- 인터페이스 타입 변수도 같은 원리로 동작하는지

3분 이하 세로 쇼츠 한 편으로, 실제로 컴파일·실행되는 예제를 써서 이 개념들을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열네 번째 영상 "다형성"을 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 예시 클래스: 13편의 추상 클래스 `Person` → `Student`(민수·85) / `Teacher`(서준)와 인터페이스 `Studyable`을 그대로 이어 쓴다. 새 클래스는 만들지 않는다.
- 흐름: 부모 타입 변수에 자식 객체 → 누구의 메소드가 실행되나 → 배열·매개변수로 한 번에 → 부모 타입의 한계 → 다운캐스팅과 잘못된 캐스트 → 인터페이스 타입

장면 구성은 아래와 같다.

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | – | 자바 입문 열네 번째, 다형성 |
| up | 1. 부모 타입에 자식 객체 | 1 | `Person p = new Student("민수", 85);` — 업캐스팅, 자동으로 됨 |
| call | 1-1. 누구의 hello? | 1 | `p.hello()` → `학생 민수 안녕`: 변수 타입이 아니라 실제 객체의 메소드가 실행됨 |
| arr | 2. 배열로 한 번에 | 2 | `Person[] people = { 민수, 서준 }`을 for-each로 돌며 `hello()` → `학생 민수 안녕` / `서준 선생님 안녕` (핵심 장면) |
| param | 2-1. 매개변수로 | 2 | `static void greet(Person p)` 하나로 Student·Teacher 모두 → 같은 두 줄 |
| limit | 3. 부모 타입의 한계 | 3 | `p.score` → 컴파일 오류(Person에는 score가 없음) |
| down | 4. 다운캐스팅 | 4 | `if (p instanceof Student)` → `Student s = (Student) p;` → `s.score` → `85`. 메모: `p instanceof Student s`로 줄여 쓸 수 있음(Java 16+) |
| cce | 4-1. 잘못된 캐스트 | 4 | Teacher가 담긴 `p`를 `(Student) p` → 컴파일은 되지만 실행 중 `ClassCastException` |
| iface | 5. 인터페이스 타입 | 5 | `Studyable[] list = { 민수, 서준 }`을 for-each로 돌며 `study()` → `민수 공부 중` / `서준 공부 중` |
| outro | 정리 | – | 6줄 목록, 나레이션에 맞춰 줄 강조, 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열네 번째, 다형성"이라는 주제를 바로 알고 싶다. 따라오던 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 지난 편들의 `Person`·`Student`·`Teacher`, 민수·서준, `Studyable`이 다시 나오길 바란다. 새 예제를 익히는 부담 없이 개념에만 집중할 수 있기 때문이다.
3. 시청자로서, `Person p = new Student("민수", 85);`처럼 변수 타입과 객체 타입이 다른 코드를 보고 싶다. 다형성의 출발점을 정확히 알 수 있기 때문이다.
4. 시청자로서, 이것이 "Student는 Person이니까" 자동으로 된다는 설명을 듣고 싶다. 상속 관계에서 자연스럽게 이해할 수 있기 때문이다.
5. 시청자로서, 이것을 업캐스팅이라 부르고, 화면에 "(자식 → 부모 타입)"이 함께 적혀 있길 바란다. 용어와 뜻을 함께 기억할 수 있기 때문이다.
6. 시청자로서, `p.hello()`가 `학생 민수 안녕`을 출력하는 것을 보고 싶다. 부모 타입 변수로 불러도 실제 객체의 오버라이딩된 메소드가 실행된다는 것을 결과로 확인할 수 있기 때문이다.
7. 시청자로서, "변수 타입이 아니라 실제 객체가 결정한다"는 한 문장 규칙을 듣고 싶다. 다형성의 핵심을 짧게 기억할 수 있기 때문이다.
8. 시청자로서, `Person[]` 배열에 민수와 서준을 함께 담는 것을 보고 싶다. 서로 다른 클래스의 객체를 한 배열에 담을 수 있다는 것을 알 수 있기 때문이다.
9. 시청자로서, for-each 한 번으로 `hello()`를 불러 `학생 민수 안녕`, `서준 선생님 안녕`이 각각 다르게 출력되는 것을 보고 싶다. 같은 호출이 객체마다 다르게 동작하는 다형성을 직접 볼 수 있기 때문이다.
10. 시청자로서, 이것이 "다형성"이라는 이름의 뜻(여러 형태)이라는 설명을 듣고 싶다. 용어를 외우지 않고 이해할 수 있기 때문이다.
11. 시청자로서, `static void greet(Person p)` 메소드 하나로 Student와 Teacher를 모두 처리하는 것을 보고 싶다. 매개변수에서도 다형성이 쓰인다는 것을 알 수 있기 때문이다.
12. 시청자로서, 학생용·선생님용 메소드를 따로 만들 필요가 없다는 장점을 듣고 싶다. 다형성이 왜 쓸모 있는지 납득할 수 있기 때문이다.
13. 시청자로서, `p.score`가 컴파일 오류라는 것을 보고 싶다. 부모 타입 변수로는 부모에 있는 것만 쓸 수 있다는 한계를 알 수 있기 때문이다.
14. 시청자로서, 그 이유를 "컴파일러는 변수 타입(Person)만 보고 판단한다"로 듣고 싶다. 앞의 "실행은 실제 객체 기준"과 대비해 정확히 이해할 수 있기 때문이다.
15. 시청자로서, `(Student) p`로 다시 Student 타입으로 바꿔 `s.score`로 `85`를 읽는 것을 보고 싶다. 자식에만 있는 것을 다시 쓰는 방법을 알 수 있기 때문이다.
16. 시청자로서, 이것을 다운캐스팅이라 부르고, 화면에 "(부모 → 자식 타입)"이 함께 적혀 있길 바란다. 업캐스팅과 짝으로 기억할 수 있기 때문이다.
17. 시청자로서, 캐스트 전에 `instanceof`로 실제 객체가 Student인지 먼저 확인하는 것을 보고 싶다. 안전하게 다운캐스팅하는 습관을 들일 수 있기 때문이다.
18. 시청자로서, `p instanceof Student s`로 확인과 캐스트를 한 줄에 줄여 쓸 수 있다는 메모를 보고 싶다. 요즘 코드에서 자주 보는 모양을 알아볼 수 있기 때문이다.
19. 시청자로서, Teacher가 담긴 변수를 `(Student)`로 캐스트하면 컴파일은 되지만 실행 중 `ClassCastException`이 나는 것을 보고 싶다. 다운캐스팅이 위험할 수 있다는 것을 실제 오류로 확인할 수 있기 때문이다.
20. 시청자로서, 컴파일 오류와 실행 중 오류의 차이를 구분해 듣고 싶다. `instanceof` 확인이 왜 필요한지 이해할 수 있기 때문이다.
21. 시청자로서, `Studyable[]` 배열에 민수와 서준을 담아 `study()`를 부르는 것을 보고 싶다. 인터페이스 타입 변수도 같은 원리로 동작한다는 것을 알 수 있기 때문이다.
22. 시청자로서, 민수와 서준이 Person 자식이라서가 아니라 Studyable을 구현했기 때문에 같은 배열에 담긴다는 설명을 듣고 싶다. 13편 인터페이스가 어디에 쓰이는지 연결할 수 있기 때문이다.
23. 시청자로서, 정리 장면에서 여섯 가지 핵심을 목록으로 한꺼번에 보고, 나레이션이 말하는 줄이 강조되길 바란다. 복습하면서 따라 읽을 수 있기 때문이다.
24. 시청자로서, 모든 자막이 나레이션과 단어 단위로 맞길 바란다. 소리 없이 보더라도 내용을 따라갈 수 있기 때문이다.
25. 시청자로서, 휴대폰 화면에서도 코드가 읽히길 바란다. 쇼츠는 대부분 휴대폰으로 보기 때문이다.
26. 제작자로서, 화면의 모든 예제가 실제로 컴파일·실행되어 대본의 결과와 같은지 빌드가 확인하길 바란다. 틀린 코드를 올리는 일을 막을 수 있기 때문이다.
27. 제작자로서, 실행 중 오류(ClassCastException)도 빌드가 실제로 실행해 확인하길 바란다. 컴파일 오류와 달리 실행해야만 드러나기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-polymorphism-shorts`. 13편(인터페이스)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 입문 다형성 정리", "다형성"은 주황 강조. 진행 표시 5칸, 1-1은 1번째, 2-1은 2번째, 4-1은 4번째 칸에 속한다.
- **예시 데이터** (13편과 같음, 영상 전체에서 하나로 통일)
  - `Person` (k1): 추상 클래스. `String name`, 생성자, 추상 메소드 `hello()`, `bye()`.
  - `Student` (k2): `extends Person implements Studyable`, `int score`, `hello()` → `"학생 " + name + " 안녕"`, `study()` → `name + " 공부 중"`. 객체는 민수·85.
  - `Teacher` (k3): `extends Person implements Teachable, Studyable`, `hello()` → `name + " 선생님 안녕"`, `teach()`, `study()` → `name + " 공부 중"`. 객체는 서준.
  - `Studyable`: 13편과 같은 인터페이스 표시(파란 테두리).
  - 클래스 선언 전체는 화면에 거의 보이지 않고 숨김 줄로 완전한 프로그램을 만든다. 화면은 `main` 안의 문장 위주로 보여 준다.
  - 화면의 객체·출력 줄은 대상별 색(민수 k2, 서준 k3)을 유지한다.
- **장면별 기대 결과**
  - call: `학생 민수 안녕`
  - arr: `학생 민수 안녕`, `서준 선생님 안녕` 두 줄
  - param: `학생 민수 안녕`, `서준 선생님 안녕` 두 줄
  - down: `85` (기본 형태와 패턴 매칭 형태 모두 `85`)
  - iface: `민수 공부 중`, `서준 공부 중` 두 줄
  - up: 컴파일 성공 확인
  - 컴파일 오류 예제와 javac 오류 문구(대조 기준, 기획 단계에서 로컬 javac 25로 확인함):
    - limit: `cannot find symbol` (다음 줄: `symbol: variable score`, `location: variable p of type Person`)
  - 실행 중 오류(대조 기준, 로컬 java 25로 확인함):
    - cce: `java.lang.ClassCastException: class Teacher cannot be cast to class Student`. 화면에는 `ClassCastException`과 앞부분만 보여 주고 모듈·로더 설명은 생략한다.
- **헬퍼**: 직전 빌드 스크립트의 실행 헬퍼는 실행 중 오류의 첫 줄을 이미 돌려준다. 실행 중 오류를 기대값과 대조하는 헬퍼가 없으면 출력·컴파일 오류 대조 헬퍼와 같은 모양으로 하나 추가한다(기록 파일에도 남긴다).
- **장면 구성 요소**
  - up은 코드 한 줄 아래에 `Student → Person` 방향을 보여 주는 업캐스팅 표시(“자식 → 부모 타입”)를 둔다.
  - call은 "변수 타입: Person / 실제 객체: Student" 비교 카드(`.vs`)로 무엇이 실행을 결정하는지 보여 준다.
  - arr는 결과 두 줄을 대상별 색으로 보여 준다. 이 장면이 가장 크게 강조된다.
  - limit는 오류 예제 아래에 "컴파일러는 변수 타입만 본다" 메모를 둔다.
  - down은 `instanceof` 확인 → 캐스트 → `85`를 보여 주고, 패턴 매칭은 `.note` 한 줄로 둔다.
  - cce는 `.warn`으로 "컴파일은 OK, 실행 중 오류"를 강조한다.
- **대본**
  - 영어 키워드는 한글 발음으로 쓴다(퍼슨, 스튜던트, 티처, 스터디어블, 헬로, 스터디, 그리트, 스코어, 인스턴스오브, 클래스 캐스트 익셉션, 피, 에스).
  - 용어는 GLOSSARY를 따른다: 다형성, 업캐스팅, 다운캐스팅. "자동 형변환·강제 형변환"과 섞어 쓰지 않고, "동적 바인딩"을 단독으로 쓰지 않는다.
  - 길이는 대본 전체를 먼저 써서 확인하고, 3분을 넘으면 음성 생성 전에 줄인다.
- **정리 장면 6줄**
  1. 부모 타입 변수에 자식 객체 (업캐스팅)
  2. 메소드는 실제 객체 기준으로 실행
  3. 배열·매개변수 하나로 여러 객체 처리
  4. 부모 타입으로는 자식 것을 못 씀
  5. `instanceof`로 확인 후 다운캐스팅
  6. 인터페이스 타입도 똑같이

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 예제의 실제 출력, 실제 컴파일 오류, 실제 실행 중 오류가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 기존 빌드 과정의 Java 예제 검증을 그대로 쓴다. 실행 중 오류 대조는 같은 지점(실행 헬퍼의 결과)에 기대값 비교만 더한다. 새 테스트 지점은 만들지 않는다.
- **대조 항목**
  - 출력 대조(5건): call, arr, param, down, iface
  - 컴파일 성공 확인(1건): up
  - 컴파일 오류 대조(1건): limit `p.score`
  - 실행 중 오류 대조(1건): cce `ClassCastException`
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다.
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(down 또는 arr)을 390px 폭으로 줄여 모바일 가독성을 확인한다.
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다.
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재.
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "학생 민수 안녕, 서준 선생님 안녕이 차례로 나와요"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 배열 편의 실행 중 오류(인덱스 에러) 장면, 산술연산자 편의 0으로 나누기 장면 — 실행 중 오류를 화면에 보여 준 방식. 12편의 오버라이딩 결과 두 줄 장면.

## Out of Scope

- 오버로딩과 다형성의 관계(컴파일 시점 다형성)
- `Object` 클래스, `toString()`·`equals()` 오버라이딩
- 필드는 다형성이 적용되지 않는다는 규칙(필드 숨김)
- `static` 메소드는 오버라이딩되지 않는다는 규칙
- 제네릭, 컬렉션(`ArrayList<Person>`)
- `switch` 패턴 매칭, `sealed` 클래스
- 디자인·템포·제작 도구의 변경
