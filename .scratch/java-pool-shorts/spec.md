# 스펙: 자바 입문 스물네 번째 — 스레드 풀

Status: resolved

## Problem Statement

22편 "스레드"에서 시청자는 작업마다 `new Thread(람다)`로 스레드를 직접 만들고, `start()`로 시작하고, `join()`으로 끝나기를 기다렸다. 작업은 결과를 **출력**만 했고, 메인 스레드가 그 값을 돌려받는 방법은 없었다.

입문자가 다음으로 알아야 할 것은 다음과 같다.

- 작업마다 스레드를 새로 만들지 않고, 미리 만든 스레드 몇 개가 작업을 돌려 가며 맡는 **스레드 풀**
- 작업이 계산한 값을 메인 스레드가 **돌려받는** 방법(`Future`, `get()`)
- 다 쓴 풀은 닫아야 프로그램이 끝나고, try-with-resources(21편)가 "작업이 끝날 때까지 기다렸다가 닫기"를 해 준다는 것(`join`의 역할을 대신함)

기준 자료: [../java-thread-shorts/not-covered.md](../java-thread-shorts/not-covered.md)의 후보 2.

## Solution

시리즈 스물네 번째 영상 "스레드 풀"을 기존 영상과 같은 디자인·제작 방식으로 만든다. 썸네일도 이 영상 하나만 만든다.

- 영상 규격: 1080×1920, 2분 30초 이하, 1.2배 템포
- 흐름: 왜 풀이 필요한지 그림으로 보고 → 풀에 작업을 맡기고(`submit`) → 값을 돌려받고(`Future`·`get`) → 풀을 닫는 괄호의 의미를 알고, 가상 스레드와 한 줄로 비교한다
- 예시 데이터: 22편과 같은 민수 85(k1 주황)·서준 92(k2 초록). 이번에는 작업이 점수를 **돌려주고**, 메인이 합계 `177`을 낸다
- "실무"라는 말이나 실무 사례는 꺼내지 않는다. 22편과 이어지는 흐름으로만 동기를 준다

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "스레드 <em>풀</em>". "22편에서는 작업마다 스레드를 직접 뉴 했죠. 이번엔 스레드를 미리 만들어 두고 돌려 쓰는 방법을 알아볼게요" |
| why | 1. 왜 스레드 풀인가 | 1 | 스레드도 만들고 없애는 데 시간이 든다 / 작업이 천 개면 스레드도 천 개. 그림: 작업 3개 → 스레드 2칸, 먼저 끝난 스레드가 세 번째 작업을 맡음. 실행 예제·수치 없음 |
| submit | 2. 작업 맡기기 | 2 | 고정 풀 2개 + `submit(() -> System.out.println("민수 85"))`·`서준 92`. 22편 `new Thread(…).start()`와 나란히 비교. 출력 예시 `민수 85 / 서준 92`, 나레이션 "이번 실행에서는" |
| future | 3. 값 돌려받기 | 3 | `Future<Integer> f1 = pool.submit(() -> 85);` … `int sum = f1.get() + f2.get();` → `177`. 값을 돌려주는 작업은 `Callable`. `get()`은 작업이 끝날 때까지 기다렸다 꺼낸다 |
| close | 4. 풀 닫기 | 4 | try-with-resources 괄호 = 작업이 끝날 때까지 기다렸다 닫기(`join` 대신). `.warn` "닫지 않으면 프로그램이 끝나지 않아요". 가상 스레드 비교: `newFixedThreadPool(2)` ↓ `newVirtualThreadPerTaskExecutor()` |
| outro | 정리 | 5 | 목록 전체 → 나레이션에 맞춰 줄 강조. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 스물네 번째, 스레드 풀"이라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 22편의 `new Thread` 방식과 이어지는 말을 듣고 싶다. 이번 편이 무엇을 바꾸는지 바로 알 수 있기 때문이다.
3. 시청자로서, 스레드도 만들고 없애는 데 시간이 든다는 설명을 듣고 싶다. 풀이 왜 필요한지 이해할 수 있기 때문이다.
4. 시청자로서, 작업 3개를 스레드 2개가 돌려 가며 맡는 그림을 보고 싶다. "스레드를 돌려 쓴다"는 말이 무슨 뜻인지 눈으로 알 수 있기 때문이다.
5. 시청자로서, `Executors.newFixedThreadPool(2)`로 스레드 2개짜리 풀을 만드는 코드를 보고 싶다. 따라 칠 때 무엇을 써야 하는지 알 수 있기 때문이다.
6. 시청자로서, 22편의 `new Thread(…).start()`와 `pool.submit(…)`을 나란히 보고 싶다. 람다식은 그대로 두고 맡기는 방법만 바뀐다는 것을 알 수 있기 때문이다.
7. 시청자로서, 출력 순서가 실행할 때마다 다를 수 있다는 말을 듣고 싶다. 내 결과 순서가 화면과 달라도 당황하지 않기 때문이다.
8. 시청자로서, 작업이 `85`를 돌려주고 `Future<Integer>`로 받는 코드를 보고 싶다. 22편에서는 못 했던 "결과 돌려받기"를 할 수 있기 때문이다.
9. 시청자로서, 퓨처가 "나중에 결과를 꺼내는 상자"라는 설명을 듣고 싶다. `submit`이 결과가 아니라 상자를 바로 돌려준다는 것을 이해할 수 있기 때문이다.
10. 시청자로서, `get()`이 작업이 끝날 때까지 기다렸다가 값을 꺼낸다는 것을 알고 싶다. 결과가 아직 없을 때 어떻게 되는지 궁금하지 않기 때문이다.
11. 시청자로서, `f1.get() + f2.get()`이 항상 `177`이 되는 결과를 보고 싶다. 스레드를 써도 결과를 정확히 모을 수 있다는 것을 확인할 수 있기 때문이다.
12. 시청자로서, 값을 돌려주는 작업을 `Callable`이라고 부른다는 것을 알고 싶다. 다른 자료에서 이 이름을 만나도 알아볼 수 있기 때문이다.
13. 시청자로서, `main`에 `throws Exception`이 붙은 이유를 짧게 듣고 싶다. 22편 `join`처럼 `get()`도 예외를 던질 수 있다는 것만 알면 되기 때문이다.
14. 시청자로서, `try ( )` 괄호가 21편 파일 닫기와 같은 문법이라는 것을 알고 싶다. 이미 배운 것과 연결해 기억할 수 있기 때문이다.
15. 시청자로서, 괄호가 끝날 때 풀이 작업이 다 끝나기를 기다렸다가 닫힌다는 것을 알고 싶다. 22편의 `join`을 따로 쓰지 않아도 되는 이유를 알 수 있기 때문이다.
16. 시청자로서, 풀을 닫지 않으면 프로그램이 끝나지 않는다는 경고를 보고 싶다. 따라 하다가 프로그램이 멈춘 것처럼 보일 때 원인을 알 수 있기 때문이다.
17. 시청자로서, 풀을 만드는 줄만 `newVirtualThreadPerTaskExecutor()`로 바꾸면 가상 스레드를 쓸 수 있다는 것을 보고 싶다. 자바 21부터 생긴 방법을 알 수 있기 때문이다.
18. 시청자로서, 가상 스레드는 풀이 아니라 작업마다 가벼운 스레드를 새로 만든다는 것을 정확히 듣고 싶다. 두 방식을 헷갈리지 않기 때문이다.
19. 시청자로서, 정리 장면에서 여섯 가지 핵심을 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
20. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
21. 시청자로서, 모바일 화면에서 코드와 결과 상자가 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
22. 시청자로서, 화면 코드를 그대로 따라 쳐도 실행되고 같은 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
23. 시청자로서, 피드·채널 화면에서 주제가 바로 보이는 썸네일을 보고 싶다. 볼 영상을 고르기 쉽기 때문이다.
24. 제작자로서, 항상 `177`이 나와야 하는 예제를 여러 번 실행해 검증하길 원한다. 한 번 맞은 것을 우연으로 착각하지 않기 위해서다.
25. 제작자로서, 화면에 그리지 않는 가상 스레드 버전도 빌드가 실행해 `177`을 확인하길 원한다. 말로 소개한 코드도 실제로 동작해야 하기 때문이다.
26. 제작자로서, 출력 순서가 달라지는 예제는 고정 예시로 그려 다시 빌드해도 `index.html`이 바뀌지 않길 원한다. 결과물을 안정적으로 관리하기 위해서다.
27. 제작자로서, 썸네일이 영상과 같은 디자인 토큰·글꼴을 쓰고, 원본은 영상 폴더에 남기고 PNG는 커밋하지 않길 원한다. 시리즈의 일관성과 가벼운 저장소를 지키기 위해서다.
28. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고, `not-covered.md`의 **[24편 예정]**을 **[24편 완료]**로 바꾸고 싶다. 다음 편 기획이 이 파일에서 출발하기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-pool-shorts`. 23편(`java-sync-shorts`)의 음성 생성 스크립트와 빌드 스크립트를 복사해 장면만 바꾼다(`J.load(speed=1.2)`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: `자바 입문 <em>스레드 풀</em> 정리`. 진행 표시 5칸: why → 1, submit → 2, future → 3, close → 4. outro는 시리즈 관례대로 PROG에 넣지 않는다(23편 01 티켓 참고).
- **용어** (GLOSSARY, 기획 단계에서 등록함): 스레드 풀, 작업, 퓨처. 기존 용어 스레드·메인 스레드·람다식·try-with-resources를 그대로 쓴다.
  - "태스크", "쓰레드풀", "익스큐터"(단독)는 쓰지 않는다. `ExecutorService`는 화면에 코드로 나오고 나레이션은 "익스큐터 서비스"
  - 퓨처는 화면에 처음 한 번 "(나중에 결과를 꺼내는 상자)"를 덧붙인다
- **읽는 법**: 익스큐터 서비스, 익스큐터스 점 뉴 픽스드 스레드 풀, 서브밋, 퓨처, 콜러블, 겟, 트라이 위드 리소스, 뉴 버추얼 스레드 퍼 태스크 익스큐터, 스로우즈 익셉션.
- **예제 구조**: 모든 예제는 `main` 안의 문장이다. `J.MAIN_THROWS = "Exception"`, `J.IMPORTS`에 `import java.util.concurrent.*;`. 화면 코드는 try-with-resources 블록까지 포함한 **완전한 모양**으로 그려, 그대로 따라 쳐도 실행되고 끝난다(STEP 2부터 괄호를 쓰고, STEP 4에서 그 의미를 설명).
- **33자 제한에 맞춘 코드 모양** (기획 때 확정)

  ```java
  try (ExecutorService pool =
    Executors.newFixedThreadPool(2)
  ) {
    Future<Integer> f1 =
      pool.submit(() -> 85);
    Future<Integer> f2 =
      pool.submit(() -> 92);
    int sum = f1.get() + f2.get();
    System.out.println(sum);
  }
  ```

  - submit 장면도 같은 머리(`try (` … `) {`)에 `pool.submit(() ->` / `  System.out.println("민수 85"));` 두 번
  - 합계는 `int sum` 변수에 담아 출력한다(`println(f1.get() + f2.get())`은 42자)
- **장면별 기대 결과** (대조 기준)
  - submit: 기존 `jmulti` + `same_lines("민수 85", "서준 92")`. 화면 예시 `민수 85 / 서준 92`, 라벨은 22편 start와 같은 방식
  - future: 매 실행 `177` (`jmulti`, 여러 번 실행)
  - close(가상 스레드 버전): 화면에 그리지 않는다. `newFixedThreadPool(2)`만 `newVirtualThreadPerTaskExecutor()`로 바꾼 같은 프로그램을 빌드가 실행해 `177`인지 확인한다(기존 `check`/`wrap`으로 그리지 않고 실행). 새 헬퍼는 만들지 않는다
- **why 장면의 그림**: 23편 scope 그림처럼 빌드 스크립트 안의 짧은 HTML 조각(공용 모듈에 넣지 않음). 스레드 2칸(가로 줄) 위에 작업 상자 3개가 놓이고, 세 번째 작업이 먼저 빈 스레드 줄에 이어 붙는 모습. 시간·숫자는 넣지 않는다. 디자인 토큰 색만 쓴다.
- **submit 장면 비교**: 22편 `new Thread(() -> …)` + `start()`와 `pool.submit(() -> …)`을 비교한다. 형식(`.vs` 카드나 두 코드 블록)은 화면 높이를 보고 구현 때 정하되, 람다식 부분이 같다는 것이 보여야 한다.
- **close 장면**: 이미 본 코드의 `try (` … `)` 줄을 주황 강조(`mark`)하고, 메모로 "괄호가 끝나면 → 작업이 다 끝날 때까지 기다렸다 닫기 = `join` 대신". `.warn` "닫지 않으면 프로그램이 끝나지 않아요"는 실행 예제 없이 상자로만 둔다(검증 도구에 시간 제한을 새로 만들지 않음). 가상 스레드는 코드 블록이 아닌 비교 상자에 메소드 이름만 위아래로 보여 준다: `newFixedThreadPool(2)` ↓ `newVirtualThreadPerTaskExecutor()`(33자, 줄바꿈 없이 한 줄에 들어가는지 390px에서 확인).
- **사실 표현 주의**
  - "실무", "현업" 같은 말은 쓰지 않는다
  - 스레드 생성 비용은 수치 없이 "시간이 든다"로만 말한다. "풀이 몇 배 빠르다"처럼 말하지 않는다
  - 가상 스레드를 "가상 스레드 풀"이라고 부르지 않는다. "작업마다 가벼운 가상 스레드를 하나씩 만든다", "자바 21부터"
  - try-with-resources로 풀을 닫는 것은 자바 19부터 가능하다. 영상에서는 버전을 말하지 않되, 나레이션이 "예전부터 됐다"처럼 들리지 않게 한다
  - `get()`이 던지는 예외 이름(`InterruptedException`·`ExecutionException`)은 말하지 않는다. "겟도 예외를 던질 수 있어서 메인에 스로우즈 익셉션을 붙여요" 정도
  - 출력 순서는 "이번 실행에서는", "실행할 때마다 달라질 수 있어요"
- **썸네일** (이 영상 하나만, 23편과 같은 방식)
  - 1080×1920 PNG. 빌드 스크립트가 영상과 같은 CSS로 영상 폴더에 `thumbnail.html`을 만든다
  - 구성: 작은 글씨 "자바 입문 24" → 큰 글씨 "스레드 <em>풀</em>"(주황 강조) → 작은 줄 `submit · Future · get`
  - 하단 300px에는 아무것도 두지 않는다. PNG는 `output/java-pool-shorts-thumb.png`(git 제외), 렌더링 명령은 23편에서 정한 것을 그대로 쓴다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 실제로 컴파일·실행한 예제의 출력이 대본의 기대 조건을 만족하는지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 빌드 자체. 새 헬퍼나 새 검증 지점은 만들지 않는다.
- **대조 항목**

## Out of Scope

- `CompletableFuture`, `invokeAll`·`invokeAny`, `shutdown()`·`awaitTermination()`만 쓰는 닫기 방식
- `get()`의 예외 종류(`InterruptedException`·`ExecutionException`)와 시간 제한 `get(시간)`
- 풀 크기 정하는 법, `newCachedThreadPool` 등 다른 풀 종류
- 스레드 재사용을 보여 주는 실행 예제(`Thread.currentThread().getName()`)
- 풀을 닫지 않아 프로그램이 끝나지 않는 모습의 실행 예제
- 가상 스레드 전용 장면, `Thread.ofVirtual()`
- `interrupt()`, 데몬 스레드, 데드락 (후보 3)
- 실무 언급, 실행 시간 측정·성능 비교
- 디자인·템포·제작 도구의 변경(why 장면 그림, 썸네일 제외)
