# 스펙: 자바 입문 열한 번째 — static과 final

Status: ready-for-agent

## Problem Statement

자바 입문 시리즈를 따라온 시청자는 클래스·객체, 메소드·생성자, 상속까지 배웠다. 지금까지 모든 예제의 `main` 앞에 `static`이 붙어 있었지만, 그 뜻은 아직 설명하지 않았다. 또 "값을 바꿀 수 없게 만드는" `final`도 아직 배우지 않았다.

입문자는 특히 다음을 자주 헷갈린다.

- 객체마다 따로 있는 필드와 모두가 함께 쓰는 필드의 차이
- static 메소드 안에서 인스턴스 필드를 쓰면 왜 오류가 나는지
- `final` 참조 변수인데도 객체 내용은 왜 바뀌는지
- 상수를 왜 `static final`로 만드는지

3분 이하 세로 쇼츠 한 편으로, 실제로 컴파일·실행되는 예제를 써서 이 개념들을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열한 번째 영상 "static과 final"을 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 다루는 순서: static을 먼저 다루고, 다음에 final을 다룬 뒤, 둘을 합친 `static final` 상수로 마무리한다.
- 예시 클래스: 지난 영상들의 `Student`(민수·85, 지영·92)를 이어서 쓴다. final 메소드·클래스 장면에서만 `Person`을 부모 클래스로 쓴다.

장면 구성은 아래와 같다.

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열한 번째, static과 final"이라는 주제를 바로 알고 싶다. 따라오던 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 지난 영상들의 `Student`·민수·85·지영·92가 다시 나오길 바란다. 앞에서 배운 내용 위에 새 개념을 쌓을 수 있기 때문이다.
3. 시청자로서, 지금까지 그냥 "필드"라고 부른 것이 객체마다 따로 있는 인스턴스 필드라는 설명을 듣고 싶다. static 필드와의 차이를 정확히 비교할 수 있기 때문이다.
4. 시청자로서, `score`와 `static int count`를 한 클래스 안에 나란히 놓고 비교하고 싶다. 무엇이 객체마다 따로 있고 무엇이 하나만 있는지 한눈에 볼 수 있기 때문이다.
5. 시청자로서, 생성자 안의 `count++` 덕분에 객체를 만들 때마다 `count`가 늘어나는 것을 보고 싶다. static 필드를 모든 객체가 함께 쓴다는 것을 실감할 수 있기 때문이다.
6. 시청자로서, 민수와 지영을 만든 뒤 `Student.count`가 2로 출력되는 것을 보고 싶다. 결과로 확인하면 확실히 기억할 수 있기 때문이다.
7. 시청자로서, static 필드는 `클래스이름.필드`로 쓴다는 것을 보고 싶다. 객체가 아니라 클래스에 속한다는 것을 문법으로 알 수 있기 때문이다.
8. 시청자로서, static 메소드 `getCount()`를 객체를 하나도 만들기 전에 불러도 0이 나오는 것을 보고 싶다. 객체 없이 호출할 수 있다는 것을 증명으로 볼 수 있기 때문이다.
9. 시청자로서, 두 명을 만든 뒤 같은 `Student.getCount()`가 2를 돌려주는 것을 보고 싶다. static 메소드와 static 필드가 함께 동작하는 모습을 볼 수 있기 때문이다.
10. 시청자로서, static 메소드 안에서 `score`를 쓰면 컴파일 오류가 나는 것을 보고 싶다. 실제로 코드를 짤 때 자주 만나는 오류를 미리 알 수 있기 때문이다.
11. 시청자로서, 그 오류의 이유를 "static 메소드는 객체 없이 실행되니, 누구의 `score`인지 알 수 없다"로 듣고 싶다. 규칙을 외우지 않고 이해할 수 있기 때문이다.
12. 시청자로서, 지금까지 써 온 `main`도 static이라 같은 이유로 객체를 만들어 점으로 필드를 썼다는 설명을 듣고 싶다. 시리즈 첫 편부터 보던 코드의 의미를 알게 되기 때문이다.
13. 시청자로서, `final int x`에 다시 대입하면 컴파일 오류가 나는 것을 보고 싶다. final의 기본 의미를 가장 단순한 예로 익힐 수 있기 때문이다.
14. 시청자로서, `final String name`을 생성자에서 한 번 넣는 것은 되고, 나중에 다시 넣으면 오류가 나는 것을 보고 싶다. final 필드가 "한 번만 대입"이라는 것을 알 수 있기 때문이다.
15. 시청자로서, 이름은 한 번 정하면 바뀌지 않고 점수는 계속 바뀌는 값이라 `name`만 final로 했다는 이유를 듣고 싶다. 어떤 필드에 final을 붙이는지 감을 잡을 수 있기 때문이다.
16. 시청자로서, `final Student s`라도 `s.score = 100`은 되고 출력이 100이라는 것을 보고 싶다. final이 객체가 아니라 변수를 막는다는 것을 알 수 있기 때문이다.
17. 시청자로서, 같은 `s`에 `new Student(...)`를 다시 대입하면 오류가 나는 것을 보고 싶다. final 참조 변수가 막는 것이 정확히 무엇인지 구분할 수 있기 때문이다.
18. 시청자로서, final 참조 주의를 클래스 편의 "참조 주의"(대입은 같은 객체를 가리킬 뿐)와 연결해서 듣고 싶다. 앞뒤 개념이 하나로 이어지기 때문이다.
19. 시청자로서, 부모 클래스 `Person`의 final `hello()`를 자식 클래스가 오버라이딩하면 오류가 나는 것을 보고 싶다. 지난 편의 오버라이딩을 막는 방법을 알 수 있기 때문이다.
20. 시청자로서, final 클래스 `Person`을 `extends`하면 오류가 나는 것을 보고 싶다. 상속 자체를 막는 방법을 알 수 있기 때문이다.
21. 시청자로서, 자바의 `String`도 final 클래스라는 것을 화면 메모로 보고 싶다. final이 실제로 어디에 쓰이는지 감을 잡을 수 있기 때문이다.
22. 시청자로서, `isPass()` 속 숫자 60을 `PASS_SCORE` 상수로 바꾸는 장면을 보고 싶다. 숫자에 이름을 붙이면 읽기 쉬워진다는 상수의 목적을 알 수 있기 때문이다.
23. 시청자로서, 상수는 `static final`로 만들고 이름은 대문자와 `_`로 쓴다는 규칙을 보고 싶다. 다른 사람의 코드에서 상수를 바로 알아볼 수 있기 때문이다.
24. 시청자로서, 상수에 다시 대입하면 오류가 나는 것을 보고 싶다. 상수는 바뀌지 않는다는 것을 확인할 수 있기 때문이다.
25. 시청자로서, static은 "클래스에 하나", final은 "한 번만 대입", 상수는 "둘의 조합"이라는 큰 그림을 정리 장면에서 보고 싶다. 두 키워드를 헷갈리지 않고 기억할 수 있기 때문이다.
26. 시청자로서, 정리 장면에서 항목 전체를 한 화면으로 보고, 나레이션이 말하는 줄이 강조되길 바란다. 복습하기 쉽기 때문이다.
27. 시청자로서, 나레이션과 단어 단위로 맞는 한국어 자막을 보고 싶다. 소리 없이 보거나 빠른 템포에서도 따라갈 수 있기 때문이다.
28. 시청자로서, 나레이션에서 말한 코드·결과·오류가 모두 화면에 보이길 바란다. 말로만 나오는 내용 때문에 혼란스럽지 않기 때문이다.
29. 휴대폰 시청자로서, 코드가 한 줄 33자 이하이고 하단 쇼츠 UI에 가리지 않길 바란다. 작은 화면에서도 읽을 수 있기 때문이다.
30. 시청자로서, 영상이 3분을 넘지 않고 지난 영상들과 같은 속도·디자인이길 바란다. 시리즈를 일관되게 볼 수 있기 때문이다.
31. 제작자로서, 화면의 모든 예제가 빌드할 때 실제로 컴파일·실행되고, 대본의 기대 결과와 다르면 빌드가 멈추길 바란다. 틀린 코드가 영상에 나가지 않기 때문이다.
32. 제작자로서, 컴파일 오류 예제도 실제 컴파일러의 오류와 대조되길 바란다. "오류가 난다"는 설명이 사실임을 보장할 수 있기 때문이다.
33. 제작자로서, 영상에 나온 예제 프로그램 전체가 파일 하나로 저장되길 바란다. 시청자 질문에 답하거나 나중에 다시 확인할 수 있기 때문이다.
34. 제작자로서, 용어가 GLOSSARY의 표기(static 필드·static 메소드·인스턴스 필드·상수·부모 클래스·자식 클래스·오버라이딩)로 통일되길 바란다. 시리즈 전체의 표기가 흔들리지 않기 때문이다.
35. 제작자로서, 렌더링 결과가 1080×1920이고 오디오 트랙이 있는지 확인되길 바란다. 업로드 전에 규격 문제를 잡을 수 있기 때문이다.
36. 제작자로서, README의 영상 목록에 이 영상의 행이 추가되길 바란다. 시리즈 기록이 이어지기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-static-final-shorts`. 직전 영상(클래스의 상속)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: "자바 입문 static·final 정리"로 하고, "static·final"은 주황으로 강조한다. 진행 표시는 5칸이며, 2-1은 2번째 칸, 3-1은 3번째 칸에 속한다.
- **예시 데이터** (영상 전체에서 하나로 통일)
  - `Student`: STEP 1·2·3·5에서 쓰며, 부모 클래스 없는 단독 클래스다. 색 k2(상속 편과 같다).
    - 인스턴스 필드: `final String name`(STEP 3부터 final), `int score`
    - static 필드: `count`
    - 생성자: `Student(String name, int score)` 안에서 `count++`
    - 메소드: `static int getCount()`, `boolean isPass()`
    - 객체: 민수·85, 지영·92
  - `Person`: STEP 4에서만 쓰는 부모 클래스, 메소드 `hello()`. 색 k1. 자식 클래스는 `Student`를 쓴다.
  - `static final int PASS_SCORE = 60`: `isPass()`는 `score >= PASS_SCORE`이고, 민수(85)는 true다.
- **필드 접근 표기**: static 필드와 static 메소드는 항상 `Student.count`, `Student.getCount()`처럼 클래스 이름으로 쓴다. 객체 변수로 static 필드에 접근하는 방식은 다루지 않는다.
- **장면별 기대 결과**
  - sfrun: `2`
  - smethod: `0`, `2` 두 줄
  - fref: 첫 블록은 `100`을 출력하고, 둘째 블록은 컴파일 오류다.
  - const: `true`이고, 상수에 다시 대입하는 블록은 컴파일 오류다.
  - 컴파일 오류 예제와 javac 오류 문구(대조 기준):
    - sme: `non-static variable score cannot be referenced from a static context`
    - fvar·ffield·fref·const: `cannot assign a value to final variable`
    - fmc: `hello() in Student cannot override hello() in Person`(메소드, 다음 줄에 `overridden method is final`), `cannot inherit from final Person`(클래스)
  - 위 문구는 기획 단계에서 로컬 javac로 확인했다.
- **장면 구성 요소**
  - sfield는 인스턴스 필드와 static 필드를 두 개념 비교 카드(`.vs`)로 대비한다. "인스턴스 필드"는 처음 한 번 "(객체마다 따로)"를 덧붙인다.
  - sme에는 "main도 static" 메모를 둔다.
  - fmc는 오류 예제 두 개와 `public final class String` 메모(`.note`)로 구성한다.
- **예제 표시 헬퍼**: 출력이 있는 예제는 출력 대조 헬퍼로, 컴파일 오류 예제는 오류 대조 헬퍼로 넣는다. 화면에 일부 줄만 보여 줄 때는 숨김 줄로 완전한 프로그램을 만든다. 예제 프로그램 전체는 빌드가 예제 목록 파일로 저장한다.
- **대본**
  - 장면 id는 위 표와 같다.
  - 영어 키워드는 한글 발음으로 쓴다(스태틱, 파이널, 카운트, 겟카운트, 패스 스코어, 이즈 패스, 헬로, 스트링).
  - 용어는 GLOSSARY를 따른다. "정적 변수·클래스 변수·멤버 변수"는 쓰지 않고, final 변수를 "상수"라고 부르지 않는다.
- **정리 장면 6줄**
  1. static 필드 → 모든 객체가 함께 쓰는 하나
  2. static 메소드 → 객체 없이 `클래스이름.메소드()`로 호출
  3. static 메소드에서는 인스턴스 필드를 쓸 수 없음
  4. final 변수·필드 → 한 번만 대입
  5. final 메소드는 오버라이딩 금지, final 클래스는 상속 금지
  6. `static final` → 상수, 이름은 대문자

  final 참조 주의는 본문 장면에서만 다룬다.

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 예제의 실제 출력과 실제 컴파일 오류가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 기존 빌드 과정의 Java 예제 검증을 그대로 쓴다. 빌드는 장면마다 예제를 실제 JDK로 컴파일·실행한다. 출력이 기대값과 다르거나, 오류 예제가 기대한 컴파일 오류를 내지 않으면 멈춘다. 새 테스트 지점은 만들지 않는다.
- **대조 항목**
  - 출력 대조: `count` → 2, `getCount()` → 0과 2, final 참조 → 100, `isPass()` → true
  - 컴파일 오류 대조(7건): static 문맥 오류, final 변수·필드·참조·상수 재대입, final 메소드 오버라이딩, final 클래스 상속
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다.
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(sfield 또는 fmc)을 390px 폭으로 줄여 모바일 가독성을 확인한다.
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다.
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재.
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다. 자동 대조는 예제 결과까지만 하기 때문이다. 예: "카운트는 이가 돼요", "처음엔 영, 두 명을 만든 뒤엔 이".
- **참고할 기존 사례**: 상속 편의 출력 대조·컴파일 오류 대조 예제(특히 "super() 주의", "단일 상속" 오류 장면)와 메소드·생성자 편의 "기본 생성자 주의" 장면.

## Out of Scope

- 객체 변수로 static 필드에 접근하는 방식(`s1.count`)
- static 블록(초기화 블록), static import, static 중첩 클래스
- 접근 제어자(`private`·`public`)와 싱글턴 같은 설계 패턴
- final 매개변수, `Math.PI` 같은 다른 라이브러리 상수 예시
- 불변 객체(immutable) 설계, `String`이 불변인 이유
- 디자인·템포·제작 도구의 변경
