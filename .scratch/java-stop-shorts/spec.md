# 스펙: 자바 입문 스물다섯 번째 — 스레드 멈추기와 끝내기

Status: ready-for-agent

## Problem Statement

22편 "스레드"에서 시청자는 스레드를 만들고(`start`), 기다리고(`join`), 경쟁 조건을 막는(`synchronized`) 것까지 배웠다. 24편에서는 풀에 작업을 맡기고 결과를 돌려받았다. 하지만 **계속 도는 스레드를 어떻게 멈추는지**는 한 번도 다루지 않았다.

입문자는 여기서 이렇게 헷갈린다.

- "멈추기"라고 하면 `stop()` 메소드를 먼저 찾는다. 하지만 이 메소드는 사용 중단됐고, 지금 자바에서는 호출하면 예외만 난다
- 22편에서 `sleep` 때문에 람다 안에 빈 `catch (InterruptedException e) {}`를 썼다. 이 예외가 무엇을 알리는지, 왜 삼키면 안 되는지는 설명하지 않았다
- 22편의 `start` 장면에서 `main 끝`이 출력된 뒤에도 `서준 92`가 나왔다. 24편에서는 "풀을 닫지 않으면 프로그램이 끝나지 않는다"고 했다. 그런데 프로그램이 언제 끝나는지(일반 스레드와 데몬 스레드의 차이)는 설명하지 않았다

기준 자료: [../java-thread-shorts/not-covered.md](../java-thread-shorts/not-covered.md)의 후보 3. 기획 회의에서 범위를 바꿨다. 데드락을 빼고 멈춤 신호(`volatile`)를 넣었다.

## Solution

시리즈 스물다섯 번째 영상 "스레드 멈추기와 끝내기"를 기존 영상과 같은 디자인·제작 방식으로 만든다. 썸네일도 이 영상 하나만 만든다.

- 영상 규격: 1080×1920, 2분 30초 이하(목표 2분 10초 안팎), 1.2배 템포
- 핵심 메시지: 스레드는 밖에서 강제로 멈출 수 없다. 멈춰 달라고 **요청**하고, 스레드가 그 요청을 확인해 **스스로** 끝낸다
- 흐름: 직접 만든 신호로 멈추기 → 자바가 주는 신호(인터럽트)로 멈추기 → 그 신호를 삼키지 않기 → 일반 스레드가 모두 끝나면 함께 끝나는 데몬 스레드
- 예시: 영상 전체가 같은 작업 스레드를 쓴다. 작업 스레드는 0.2초마다 `작업 중`을 출력하고, `main`은 1초 뒤 멈춤을 요청한다. STEP마다 **멈추는 방법만** 바뀐다. 22편의 민수·서준 데이터는 쓰지 않는다
- 22편 장면(빈 `catch`, `main 끝` 뒤의 출력)과 24편 문장("닫지 않으면 끝나지 않아요")을 되짚어 연결한다

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "스레드 <em>멈추기</em>". 22편 되짚기. `.warn` "`stop()`은 이제 예외만 던져요"(`UnsupportedOperationException`). "멈춰 달라고 요청하고, 스레드가 스스로 끝내요" |
| flag | 1. 멈춤 신호 | 1 | `static volatile boolean stop;` → `while (!stop)` 반복, `main`이 1초 뒤 `stop = true;`. 출력 예시 `작업 중`×5 + `작업 끝`. `.note` "`volatile`이 없으면 바뀐 값을 못 보고 계속 돌 수도 있어요". 자는 동안(0.2초)에는 신호를 확인하지 못한다 |
| interrupt | 2. 인터럽트 | 2 | 같은 코드에서 두 줄만 바꾼다: `while (true)`와 `t.interrupt();`. 자고 있던 `sleep`이 `InterruptedException`을 던지고, 반복 바깥의 `catch`로 빠져나와 `작업 끝`을 출력한다. 출력 예시는 STEP 1과 같다 |
| swallow | 3. 예외 삼키지 않기 | 3 | 반복 조건을 `isInterrupted()`로 바꾸고 `try`를 반복 안에 둔다. 빈 `catch`면 예외가 나는 순간 인터럽트 상태가 지워져 **끝나지 않는다**(`.warn`). 고친 카드: `catch` 안에서 `Thread.currentThread().interrupt();`로 다시 켜면 → `작업 끝` |
| daemon | 4. 데몬 스레드 | 4 | `while (true)` 작업 스레드 + `t.setDaemon(true);`(주황 강조). 출력 예시 `작업 중`×5 + `main 끝`, 그 뒤 프로그램이 끝난다. "이 한 줄이 없으면 프로그램이 끝나지 않아요". 22편 `main 끝` 뒤의 출력, 24편 "닫지 않으면 끝나지 않아요"와 연결 |
| outro | 정리 | 5 | 목록 전체 → 나레이션에 맞춰 줄 강조. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 스물다섯 번째, 스레드 멈추기"라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 22편 장면을 짧게 되짚는 말을 듣고 싶다. 이번 편이 지난 편의 어떤 빈칸을 채우는지 알 수 있기 때문이다.
3. 시청자로서, `stop()`을 쓰면 안 되고 지금 자바에서는 예외만 난다는 경고를 보고 싶다. 검색해서 찾은 옛 코드를 그대로 따라 하지 않기 때문이다.
4. 시청자로서, "멈춰 달라고 요청하고, 스레드가 스스로 끝낸다"는 원칙을 처음에 듣고 싶다. 뒤에 나오는 네 가지 방법을 하나의 생각으로 묶을 수 있기 때문이다.
5. 시청자로서, 영상 전체가 같은 작업 스레드(0.2초마다 `작업 중`) 예제를 쓰길 원한다. 멈추는 방법만 바뀐다는 것을 쉽게 비교할 수 있기 때문이다.
6. 시청자로서, `boolean` 변수 하나를 멈춤 신호로 쓰는 코드를 보고 싶다. 가장 단순한 방법부터 이해할 수 있기 때문이다.
7. 시청자로서, 멈춤 신호에 `volatile`을 붙이는 이유를 한 줄로 듣고 싶다. 다른 스레드가 바꾼 값을 보게 해 준다는 것만 알면 되기 때문이다.
8. 시청자로서, 자고 있는 동안에는 멈춤 신호를 확인하지 못한다는 한계를 듣고 싶다. 인터럽트가 왜 필요한지 자연스럽게 이어지기 때문이다.
9. 시청자로서, STEP 1과 STEP 2의 코드가 두 줄만 다르다는 것을 보고 싶다. 인터럽트가 멈춤 신호를 대신한다는 것을 한눈에 알 수 있기 때문이다.
10. 시청자로서, `t.interrupt()`가 자고 있는 스레드를 깨워 `InterruptedException`이 난다는 것을 알고 싶다. 22편에서 그냥 넘어간 그 예외가 무엇인지 알 수 있기 때문이다.
11. 시청자로서, `try`가 반복 바깥에 있으면 예외가 나면서 반복을 빠져나간다는 것을 보고 싶다. 예외가 곧 "끝내라"는 신호로 쓰인다는 것을 이해할 수 있기 때문이다.
12. 시청자로서, `catch`를 반복 안에 두고 비워 두면 스레드가 끝나지 않는다는 것을 보고 싶다. 22편처럼 빈 `catch`를 습관적으로 쓰면 생기는 문제를 알 수 있기 때문이다.
13. 시청자로서, 예외가 나면 인터럽트 상태가 지워진다는 설명을 듣고 싶다. 요청을 보냈는데도 왜 멈추지 않는지 이해할 수 있기 때문이다.
14. 시청자로서, `catch` 안에서 `Thread.currentThread().interrupt()`로 상태를 다시 켜는 코드를 보고 싶다. 예외를 삼키지 않는 바른 방법을 따라 할 수 있기 때문이다.
15. 시청자로서, `setDaemon(true)` 한 줄로 `main`이 끝나면 함께 끝나는 스레드를 만드는 것을 보고 싶다. 무한 반복 스레드도 프로그램을 붙잡지 않게 할 수 있기 때문이다.
16. 시청자로서, 일반 스레드가 남아 있으면 `main`이 끝나도 프로그램이 끝나지 않는다는 것을 듣고 싶다. 22편에서 `main 끝` 뒤에 출력이 나온 이유와, 24편에서 풀을 닫아야 했던 이유를 이해할 수 있기 때문이다.
17. 시청자로서, `setDaemon`은 `start()`보다 먼저 불러야 한다는 것을 코드 순서로 보고 싶다. 따라 칠 때 순서를 틀리지 않기 때문이다.
18. 시청자로서, 출력의 `작업 중` 줄 수가 실행할 때마다 다를 수 있다는 말을 듣고 싶다. 내 결과가 화면과 조금 달라도 당황하지 않기 때문이다.
19. 시청자로서, 정리 장면에서 다섯 가지 핵심을 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
20. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
21. 시청자로서, 모바일 화면에서 코드와 결과 상자가 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
22. 시청자로서, 화면 코드를 그대로 따라 쳐도 실행되고 같은 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
23. 시청자로서, 피드·채널 화면에서 주제가 바로 보이는 썸네일을 보고 싶다. 볼 영상을 고르기 쉽기 때문이다.
24. 제작자로서, 출력이 실행마다 다를 수 있는 예제는 여러 번 실행해 "`작업 중` 1줄 이상, 마지막 줄은 `작업 끝`/`main 끝`"인지 검증하길 원한다. 한 번 맞은 것을 우연으로 착각하지 않기 위해서다.
25. 제작자로서, "끝나지 않는다"고 말하는 두 예제(빈 `catch`, 데몬이 아닌 스레드)도 빌드가 실행해, 제한 시간 안에 끝나지 않는지 확인하길 원한다. 나레이션의 주장도 실제로 확인해야 하기 때문이다.
26. 제작자로서, 끝나지 않는 예제를 검증한 뒤 그 프로세스가 반드시 종료되길 원한다. 빌드가 멈추거나 자바 프로세스가 남지 않아야 하기 때문이다.
27. 제작자로서, `stop()`이 `UnsupportedOperationException`을 던진다는 경고 문구도 빌드가 실행해 확인하길 원한다. JDK가 바뀌어도 사실이 맞는지 알 수 있기 때문이다.
28. 제작자로서, 공용 빌드 모듈에 시간 제한을 넣은 뒤 기존 영상의 빌드 결과가 그대로이길 원한다. 다른 편을 망가뜨리지 않기 위해서다.
29. 제작자로서, 새 헬퍼의 사용법이 자바 헬퍼 문서에 적혀 있길 원한다. 다음 편(예: 데드락)에서 바로 쓸 수 있기 때문이다.
30. 제작자로서, 화면의 출력 예시는 고정해 두어 다시 빌드해도 `index.html`이 바뀌지 않길 원한다. 결과물을 안정적으로 관리하기 위해서다.
31. 제작자로서, 썸네일이 영상과 같은 디자인 토큰·글꼴을 쓰고, 원본은 영상 폴더에 남기고 PNG는 커밋하지 않길 원한다. 시리즈의 일관성과 가벼운 저장소를 지키기 위해서다.
32. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고, `not-covered.md`의 **[25편 예정]**을 **[25편 완료]**로 바꾸고 싶다. 다음 편 기획이 이 파일에서 출발하기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-stop-shorts`. 24편(`java-pool-shorts`)의 음성 생성 스크립트와 빌드 스크립트를 복사해 장면만 바꾼다(`J.load(speed=1.2)`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: `자바 <em>스레드 멈추기</em> 정리`. 진행 표시 5칸: flag → 1, interrupt → 2, swallow → 3, daemon → 4. outro는 시리즈 관례대로 PROG에 넣지 않는다.
- **용어** (GLOSSARY, 기획 단계에서 등록함): 멈춤 신호, 인터럽트, 인터럽트 상태, 데몬 스레드. 기존 용어 스레드·메인 스레드·람다식·스레드 풀을 그대로 쓴다.
  - "플래그"는 나레이션에 쓰지 않는다. 화면 메모에만 "(플래그)"를 덧붙일 수 있다
  - "인터럽트 플래그", "강제 종료", "백그라운드 스레드"는 쓰지 않는다
- **읽는 법**: 볼라타일, 인터럽트, 인터럽티드 익셉션, 이즈 인터럽티드, 스레드 점 커런트 스레드, 셋 데몬 트루, 스탑, 언서포티드 오퍼레이션 익셉션(도입 경고에서 이름을 말할 경우), 와일 트루.
- **예제 구조**: `J.MAIN_THROWS = "InterruptedException"`(`main`의 `Thread.sleep(1000)`). 작업 스레드의 `sleep`은 람다 안에서 `try-catch`한다(22편과 같은 이유). 화면 코드는 `Thread t = new Thread(() -> { … });` → `t.start();` → `Thread.sleep(1000);` → 멈춤 요청 순서의 **완전한 모양**으로 그려, 그대로 따라 쳐도 실행되고 끝난다. `stop`은 클래스 멤버이므로 flag 장면에서만 선언 줄을 함께 그린다.
- **33자 제한에 맞춘 코드 모양** (기획 때 확정, 22편 `catch (` 줄바꿈 관례를 따름). flag·interrupt 공통 뼈대:

  ```java
  Thread t = new Thread(() -> {
    try {
      while (!stop) {            // interrupt: while (true)
        System.out.println("작업 중");
        Thread.sleep(200);
      }
    } catch (
      InterruptedException e) {}
    System.out.println("작업 끝");
  });
  t.start();
  Thread.sleep(1000);
  stop = true;                   // interrupt: t.interrupt();
  ```

  - flag와 interrupt는 위 두 줄만 다르다. 이 차이를 주황 강조(`mark`)로 보여 준다
  - 이 `catch`는 비어 있지만 반복 **바깥**에 있어서, 예외가 나면 스레드가 끝난다. swallow에서 문제 삼는 것은 "반복 안에서 삼키고 계속 도는 것"이다. 나레이션에서 이 둘을 구분하고, "빈 `catch`는 무조건 나쁘다"처럼 단정하지 않는다
  - swallow(문제 버전): `while (!Thread.currentThread()` / `.isInterrupted()) {` 두 줄 조건, 반복 안에 `try { Thread.sleep(200); }`와 빈 `catch`
  - swallow(고친 카드): 화면에는 `catch` 부분만 다시 그린다. `InterruptedException e) {` / `Thread.currentThread()` / `.interrupt();` / `}`. 빌드는 고친 전체 프로그램을 실행한다
  - daemon: flag/interrupt 뼈대에서 `작업 끝` 출력 줄을 빼고 `while (true)`, `t.start();` 앞에 `t.setDaemon(true);`, 마지막 줄 `System.out.println("main 끝");`
- **장면별 기대 결과** (대조 기준)
  - hook: `stop()` 호출이 `UnsupportedOperationException`으로 끝나는지 기존 실행 오류 헬퍼로 확인한다. 화면에는 코드 블록 없이 `.warn` 상자만 둔다(그리지 않고 실행만)
  - flag · interrupt · swallow(고친 버전): `jmulti`. 매 실행 `작업 중` 1줄 이상, 그 밖의 줄은 마지막 `작업 끝` 하나뿐. 화면 예시는 `작업 중`×5 + `작업 끝`
  - daemon: `jmulti`. 매 실행 `작업 중` 1줄 이상과 `main 끝` 한 줄, `작업 끝`은 없음. 화면 예시는 `작업 중`×5 + `main 끝`
  - swallow(빈 `catch` 버전), daemon(`setDaemon` 뺀 버전): 새 헬퍼 `jhang`. 제한 시간 안에 끝나지 않아야 통과. 끝나 버리면 빌드를 멈춘다. 두 프로그램 모두 화면에 출력 상자를 그리지 않는다(swallow는 코드만 그리고 `.warn`, daemon 쪽은 그리지 않음)
- **공용 모듈 변경** (`tools/javashorts.py`)
  - 프로그램 실행 함수에 선택 인자 `timeout`을 추가한다. 기본값은 지금처럼 제한 없음이다. 그래서 기존 호출의 동작은 바뀌지 않는다
  - 새 헬퍼 `jhang(sid, lines, secs=3, …)`: 한 번 컴파일해 `secs`초 동안 실행한다. 끝나지 않으면 프로세스를 종료하고 통과한다. 그 사이 출력이 있었다면 함께 기록한다. 제한 시간 안에 끝나거나 실행 오류가 나면 빌드를 멈춘다. `examples.txt`에는 "N초 안에 끝나지 않음(의도)"으로 남긴다. 코드 블록은 다른 헬퍼처럼 돌려주며, 그리지 않고 검증만 할 수도 있어야 한다
  - `docs/java-helpers.md`의 헬퍼 표에 `jhang` 행을 추가한다
- **인터럽트 설명의 정확성**
  - `interrupt()`는 "멈춰 달라는 요청"이다. "스레드를 멈춘다", "강제 종료한다"라고 말하지 않는다
  - 자고 있지 않을 때는 예외가 나지 않고 인터럽트 상태만 켜진다. 그래서 swallow에서는 반복 조건에서 상태를 확인한다
  - "예외가 나면 인터럽트 상태가 지워진다"(`sleep`이 `InterruptedException`을 던질 때)
  - `volatile` 설명은 "다른 스레드가 바꾼 값을 보게 해 준다"까지만 한다. "`volatile`이 없으면 반드시 멈추지 않는다"고 말하지 않는다("못 볼 수도 있어요")
  - `stop()`: "오래전에 사용 중단됐고, 지금 자바에서는 예외만 던져요". 처음 쓰지 말라고 한 버전 같은 숫자는 말하지 않는다
- **데몬 장면의 연결**: 22편 start 장면(`main 끝` 뒤 `서준 92`)과 24편 close 장면("고정 풀은 닫지 않으면 스레드가 남아서 프로그램이 끝나지 않아요")을 나레이션 한두 문장으로 잇는다. 이전 편 화면을 다시 그리지는 않는다.
- **썸네일** (이 영상 하나만, 24편과 같은 방식)
  - 1080×1920 PNG. 빌드 스크립트가 영상과 같은 CSS로 영상 폴더에 `thumbnail.html`을 만든다
  - 구성: 작은 글씨 "자바 입문 25" → 큰 글씨 "스레드 <em>멈추기</em>"(주황 강조) → 작은 줄 `volatile · interrupt · 데몬`
  - 하단 300px에는 아무것도 두지 않는다. PNG는 `output/java-stop-shorts-thumb.png`(git 제외), 렌더링 명령은 24편과 같다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보고 듣는 주장을 검사한다. 실제로 컴파일·실행한 예제의 출력과 종료 여부가 대본의 기대 조건을 만족하는지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점 1: 빌드 자체** (24편과 같은 방식). 위 "장면별 기대 결과"를 빌드가 대조하고, 다르면 멈춘다.
  - `jmulti` 예제는 20회 실행한다. 화면 고정 예시도 같은 조건을 통과해야 한다
  - `jhang` 예제는 약 3초 제한. 검증 뒤 남은 `java` 프로세스가 없어야 한다
- **테스트 지점 2: 공용 모듈 회귀**. 시간 제한을 추가한 뒤 기존 자바 영상 두 편(`java-pool-shorts`, `java-thread-shorts`)을 다시 빌드한다. 두 편 모두 `index.html`·`examples.txt`에 `git diff`가 없어야 한다. 별도 단위 테스트는 만들지 않는다.
- **빌드 이후 검증** (`tools/verify-video.sh java-stop-shorts`)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(swallow 또는 flag)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **썸네일 확인**: PNG가 1080×1920인지, 글자가 하단 300px 밖에 있는지, 390px 폭으로 줄여도 큰 제목이 읽히는지 본다.
- **수동 검토**: 나레이션 문장이 화면 결과와 맞는지 직접 확인한다(예: "작업 중이 다섯 번쯤", "이번 실행에서는"). 위 "인터럽트 설명의 정확성"을 어기는 문장이 없는지도 본다.
- **참고할 기존 사례**: 22편 join 장면(람다 안 `try-catch`, `catch (` 줄바꿈, `MAIN_THROWS`), 22·24편 `jmulti` 장면, 24편 썸네일·정리 장면, 실행 오류 헬퍼를 쓴 예외 편(20편) 장면.

## Out of Scope

- 데드락과 잠금 순서(새 `jhang`으로 이후 편에서 검증할 수 있음)
- `ConcurrentHashMap`, `Lock`(`ReentrantLock`), `wait`/`notify`
- `volatile`이 경쟁 조건(`count++`)은 막지 못한다는 비교
- `volatile` 없이 멈추지 않는 모습의 실행 예제(JIT에 따라 달라서 재현을 보장할 수 없음)
- `Thread.interrupted()`(상태를 확인하면서 지우는 정적 메소드), `isInterrupted()`와의 차이
- 풀의 `shutdownNow()`·`Future.cancel(true)`가 인터럽트를 쓴다는 연결
- 스레드 상태(`getState()`), 우선순위, 스레드 이름, 스레드 안의 잡지 않은 예외
- `CompletableFuture`, 가상 스레드
- 실무 언급, 실행 시간 측정·성능 비교
- 디자인·템포·제작 도구의 변경(`jhang`·시간 제한, 썸네일 제외)

## Further Notes

- 시리즈 순서: … → 스레드(22) → 동기화 더 깊이(23) → 스레드 풀(24) → 스레드 멈추기와 끝내기(25).
- 기획 중 로컬 macOS · OpenJDK 25.0.4에서 확인했다.
  - `t.stop()`: 컴파일하면 `[removal]` 경고, 실행하면 `java.lang.UnsupportedOperationException`
  - flag · interrupt · swallow 고친 버전: 각 10회 실행, 모두 `작업 중`×5 + `작업 끝`
  - daemon: 10회 모두 `작업 중`×5 + `main 끝`, 그 뒤 종료
  - swallow 빈 `catch` 버전, `setDaemon` 뺀 버전: 3초 뒤에도 실행 중(`작업 중` 15줄), 파이썬 `subprocess`의 `timeout`으로 종료됨
