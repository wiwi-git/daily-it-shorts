# 스펙: 자바 입문 열아홉 번째 — 스트림

Status: resolved

## Problem Statement

시청자는 17편에서 `List`를, 18편에서 람다식과 `forEach`·`removeIf`·`sort`를 배웠다. 하지만 "80점 이상만 골라 새 리스트로 만들기", "점수마다 5점 더하기", "80점 이상이 몇 명인지 세기" 같은 일을 하려면 아직 향상된 for 문과 빈 리스트를 직접 만들어야 한다. 18편 함정 장면에서도 합계 255를 향상된 for 문으로 구했다. 실무 코드와 자바 라이브러리에는 `scores.stream().filter(…).map(…).toList()` 같은 스트림 코드가 계속 나오는데, 시리즈에서는 아직 다루지 않았다.

입문자가 스트림을 처음 볼 때 특히 막히는 점은 다음과 같다.

- 18편 `removeIf`와 `filter`가 둘 다 "거르는" 것 같은데 무엇이 다른지(원본이 바뀌는지)
- `stream()`, `filter`, `toList()`가 각각 어떤 역할이고 왜 점으로 이어 붙이는지
- `filter`(거르기)와 `map`(바꾸기)의 차이
- 이어 붙인 연산 중 어디까지가 중간이고 어디서 결과가 나오는지(중간 연산 / 최종 연산)
- 정렬 순서를 바꾸는 방법, 개수와 합계를 구하는 방법
- 같은 스트림을 두 번 쓰면 실행 중 오류가 난다는 것

3분 이하 세로 쇼츠 한 편으로, 실제로 실행한 결과와 오류로 이 내용을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 열아홉 번째 영상 "스트림"을 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 흐름: 18편 `removeIf`(원본을 바꿈)와 대비해 "원본은 그대로"에서 출발하고, 스트림 3단계(만들기 → 중간 연산 → 최종 연산)를 배운 뒤, `map`·이어 붙이기·`sorted`·`count`·`sum`을 써 보고, "한 번만 쓴다" 함정으로 마무리한다
- 예시 데이터: 17·18편과 같은 이름 민수·서준·지우, 점수 85·92·78

장면 구성은 아래와 같다.

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | – | 자바 입문 열아홉 번째, 스트림. 큰 제목 `.stream()`(`stream` 주황), 아래 `.hook`에 `filter → map → toList` 흐름 |
| why | 1. 원본은 그대로 | 1 | 18편 `scores.removeIf(s -> s < 80);` → `scores`가 `[85, 92]`로 바뀜 vs `scores.stream().filter(s -> s >= 80).toList()` → 결과 `[85, 92]`, `scores`는 그대로 `[85, 92, 78]` |
| flow | 2. 스트림 3단계 | 2 | 만들기 `stream()` → 중간 연산 `filter` → 최종 연산 `toList()`를 한 줄씩 강조. `.note`: 옛 코드에서는 `collect(Collectors.toList())` |
| map | 2-1. map | 2 | `names.stream().map(n -> n + "님").toList()` → `[민수님, 서준님, 지우님]`. `map`은 값을 다른 값으로 바꾼다 |
| chain | 3. 이어 붙이기 | 3 | `scores.stream().filter(s -> s >= 80).map(s -> s + 5).toList()` → `[90, 97]`. 중간 연산(`filter`·`map`)과 최종 연산(`toList`) 구분. `.note`: 최종 연산이 없으면 기본적으로 실행되지 않는다 |
| sorted | 3-1. sorted | 3 | `sorted()` → `[78, 85, 92]`(작은 순), `sorted((a, b) -> b - a)` → `[92, 85, 78]`(큰 순, 18편 `sort`와 같은 람다식) |
| count | 4. count · sum | 4 | `filter(s -> s >= 80).count()` → `2`, `mapToInt(s -> s).sum()` → `255`. 18편에서 향상된 for 문으로 구한 합계를 한 줄로 |
| once | 5. 한 번만 쓴다 | 5 | `Stream<Integer> st = scores.stream();` 뒤 `st.count()` 두 번 → `3` 다음 실행 중 오류 `IllegalStateException`(`.warn`). 다시 쓰려면 `stream()`으로 새로 만든다 |
| outro | 정리 | – | 목록 전체 → 나레이션에 맞춰 줄 강조 → 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 열아홉 번째, 스트림"이라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 도입에서 `.stream()`과 `filter → map → toList` 흐름을 먼저 보고 싶다. 오늘 무엇을 읽을 수 있게 되는지 알 수 있기 때문이다.
3. 시청자로서, 18편 `removeIf`를 쓰면 원본 `scores`가 `[85, 92]`로 바뀌는 것을 다시 보고 싶다. 스트림과 비교할 기준이 생기기 때문이다.
4. 시청자로서, 같은 조건을 스트림 `filter`로 쓰면 결과는 `[85, 92]`인데 `scores`는 `[85, 92, 78]` 그대로인 것을 실제 출력으로 보고 싶다. 스트림이 원본을 바꾸지 않는다는 것을 결과로 확인할 수 있기 때문이다.
5. 시청자로서, `removeIf`의 람다식은 "지울 조건", `filter`의 람다식은 "남길 조건"이라는 차이를 보고 싶다. 두 조건의 부등호가 반대인 이유를 알 수 있기 때문이다.
6. 시청자로서, 스트림 코드가 만들기 · 중간 연산 · 최종 연산 세 단계로 나뉜다는 것을 줄마다 강조해 보고 싶다. 긴 체인을 읽는 순서를 알 수 있기 때문이다.
7. 시청자로서, 체인 코드가 점 앞에서 줄을 바꿔 한 줄에 연산 하나씩 쓰인 모습을 보고 싶다. 실무 코드의 들여쓰기 관례에 익숙해지기 때문이다.
8. 시청자로서, `stream()`이 리스트에서 스트림을 만든다는 것을 듣고 싶다. 스트림의 출발점을 알 수 있기 때문이다.
9. 시청자로서, `filter`에 18편에서 배운 람다식을 넘긴다는 것을 보고 싶다. 배운 것을 연결할 수 있기 때문이다.
10. 시청자로서, `toList()`가 결과를 새 리스트로 모은다는 것을 보고 싶다. 스트림의 결과를 어떻게 받는지 알 수 있기 때문이다.
11. 시청자로서, 옛 코드에서는 `collect(Collectors.toList())`로 쓴다는 메모를 보고 싶다. 책이나 옛 코드에서 다른 모양을 봐도 당황하지 않기 때문이다.
12. 시청자로서, `map`이 값을 다른 값으로 바꾼다는 것을 이름 리스트 예제로 보고 싶다. `filter`(거르기)와 `map`(바꾸기)의 차이를 알 수 있기 때문이다.
13. 시청자로서, `map(n -> n + "님")`의 결과가 `[민수님, 서준님, 지우님]`인 것을 보고 싶다. 개수는 그대로이고 값만 바뀐다는 것을 확인할 수 있기 때문이다.
14. 시청자로서, `filter`와 `map`을 이어 붙여 80점 이상만 5점 더한 `[90, 97]`을 보고 싶다. 여러 연산을 한 번에 쓰는 방법을 알 수 있기 때문이다.
15. 시청자로서, `filter`·`map`처럼 이어 붙이는 연산을 중간 연산, `toList`처럼 결과를 내는 연산을 최종 연산이라고 부른다는 것을 듣고 싶다. 용어와 역할을 함께 기억할 수 있기 때문이다.
16. 시청자로서, 최종 연산이 없으면 기본적으로 아무것도 실행되지 않는다는 메모를 보고 싶다. 최종 연산을 빠뜨리는 실수를 피할 수 있기 때문이다.
17. 시청자로서, `sorted()`가 작은 순서로 정렬한 `[78, 85, 92]`를 보고 싶다. 스트림으로 정렬하는 기본 방법을 알 수 있기 때문이다.
18. 시청자로서, `sorted((a, b) -> b - a)`로 큰 순서 `[92, 85, 78]`을 보고 싶다. 18편 `sort`와 같은 람다식을 쓴다는 것을 알 수 있기 때문이다.
19. 시청자로서, `count()`로 80점 이상이 `2`명인 것을 보고 싶다. 개수를 세는 방법을 알 수 있기 때문이다.
20. 시청자로서, `mapToInt(s -> s).sum()`으로 합계 `255`를 보고 싶다. 18편에서 향상된 for 문으로 구한 합계를 한 줄로 구할 수 있다는 것을 알 수 있기 때문이다.
21. 시청자로서, `mapToInt(s -> s)`가 인티저를 int로 바꿔(17편 언박싱) 숫자 전용 스트림으로 만든다는 설명을 한 문장으로 듣고 싶다. `s -> s`가 왜 필요한지 납득할 수 있기 때문이다.
22. 시청자로서, 스트림을 변수에 담으려면 `Stream<Integer>` 타입과 `import java.util.stream.Stream;`이 필요하다는 것을 보고 싶다. 15편 import와 이어지기 때문이다.
23. 시청자로서, 같은 스트림에 `count()`를 두 번 하면 첫 번째는 `3`이 나오고 두 번째에 실행 중 오류가 나는 것을 실제 오류 문구로 보고 싶다. 직접 같은 오류를 만났을 때 원인을 알 수 있기 때문이다.
24. 시청자로서, 다시 쓰려면 `stream()`으로 새 스트림을 만들면 된다는 것을 듣고 싶다. 오류를 고치는 방법을 알 수 있기 때문이다.
25. 시청자로서, 같은 학생·점수는 모든 장면에서 같은 색으로 보고 싶다. 결과에서 무엇이 빠지고 바뀌고 움직였는지 따라갈 수 있기 때문이다.
26. 시청자로서, 정리 장면에서 오늘 배운 내용을 한 화면에 보고 싶다. 영상을 다시 보지 않아도 복습할 수 있기 때문이다.
27. 시청자로서, 나레이션이 말하는 순간 정리 항목이 강조되길 바란다. 어디를 읽어야 할지 따라갈 수 있기 때문이다.
28. 시청자로서, 화면의 모든 출력과 오류가 실제로 실행한 결과이길 바란다. 직접 따라 쳤을 때 같은 결과가 나와야 믿을 수 있기 때문이다.
29. 시청자로서, 휴대폰 화면에서도 코드를 읽을 수 있길 바란다. 쇼츠는 주로 휴대폰으로 보기 때문이다.
30. 시청자로서, 나레이션과 단어 단위로 맞는 한국어 자막을 보고 싶다. 소리 없이 봐도 이해할 수 있기 때문이다.
31. 제작자로서, 화면의 결과나 오류가 대본과 다르면 빌드가 멈추길 바란다. 틀린 내용을 올리는 실수를 막을 수 있기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-stream-shorts`. 18편(람다식)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(템포 1.2배, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: 18편 실제 구현과 같이 "자바 입문 <em>스트림</em> 정리" 형태로 "스트림"을 주황으로 강조한다. 진행 표시는 5칸이다. 2-1은 2번째 칸, 3-1은 3번째 칸에 속한다.
- **용어** (GLOSSARY): 스트림, 중간 연산, 최종 연산(기획 단계에서 등록함). 기존 용어 람다식·화살표·리스트·ArrayList·담을 타입·import·오토박싱 / 언박싱을 그대로 쓴다.
  - "중개 연산", "종단 연산", "터미널 연산"은 쓰지 않는다
  - 파일 입출력의 스트림과 다르다는 메모는 넣지 않는다(입문자 혼란만 늘어남)
- **예시 데이터** (영상 전체에서 하나로 통일)
  - 이름: 민수(k1), 서준(k2), 지우(k3). `names` 리스트의 순서도 이 순서다
  - 점수: 85, 92, 78. `scores` 리스트의 순서도 이 순서다. 점수 색은 사람을 따라간다(85=k1, 92=k2, 78=k3). `map`·정렬 뒤에도 색은 원래 값을 따라간다(90=k1, 97=k2)
  - `Student` 같은 클래스는 만들지 않는다. `names`와 `scores`는 서로 다른 리스트다
  - 리스트를 만드는 `add` 줄은 why 장면에서 한 번 보여 주고, 이후 장면은 같은 `scores`·`names`를 쓴다는 전제로 체인 코드만 보여 준다(숨긴 코드로는 항상 만들어 실행한다)
- **장면별 기대 결과** (기획 단계에서 로컬 JDK 25, 영문 로케일로 확인함. 대조 기준)
  - 출력
    - why: `removeIf` 쪽 `[85, 92]` / 스트림 쪽 결과 `[85, 92]`, 원본 `[85, 92, 78]`
    - flow: `[85, 92]`
    - map: `[민수님, 서준님, 지우님]`
    - chain: `[90, 97]`
    - sorted: `[78, 85, 92]`, `[92, 85, 78]`
    - count: `2`, `255`
  - 실행 중 오류
    - once: 출력 `3` 다음 `java.lang.IllegalStateException: stream has already been operated upon or closed`
- **컴파일·실행 헬퍼**: 18편의 출력 대조 헬퍼와 실행 중 오류 대조 헬퍼를 그대로 쓴다. 이번 편은 컴파일 오류 장면이 없다. 화면의 출력·오류 콘솔은 헬퍼가 얻은 실제 결과로 그린다. 모든 예제는 예제 기록 파일에 남긴다.
- **결과 모으기**: 메인은 `.toList()`(자바 16부터). `collect(Collectors.toList())`는 flow 장면 `.note`에 한 번만 보여 준다. `toList()` 결과를 수정할 수 없다는 점은 다루지 않는다.
- **사실 표현 주의**
  - "스트림은 원본 리스트를 바꾸지 않고 새 결과를 만든다"로 말한다
  - 지연 실행은 "최종 연산이 없으면 기본적으로 실행되지 않는다"로 메모 한 줄만. "지연 평가" 같은 용어는 쓰지 않는다
  - `map`은 "값을 다른 값으로 바꾼다"로만 말한다
  - `mapToInt`는 "인티저를 int로 바꿔 숫자 전용 스트림으로 만든다"로 한 문장만 말하고 `IntStream`이라는 이름은 화면·나레이션에 내지 않는다
  - `b - a` 정렬은 18편과 같이 "빼기 결과로 순서를 정한다" 수준으로만 말한다
  - once 장면은 "한 번 최종 연산을 한 스트림은 다시 쓸 수 없다"로 말한다
- **장면 구성 요소**
  - 체인 코드는 점(`.`) 앞에서 줄을 바꿔 한 줄에 연산 하나씩 쓰고, 연산 줄은 `stream()` 아래로 들여쓴다. 코드 한 줄은 33자 이하
  - why는 위아래 두 코드 블록(18편 `removeIf` → 스트림 `filter`)과 각 결과를 비교하고, 원본 `scores`가 그대로인 줄을 강조한다
  - flow는 같은 체인을 세 단계 이름표(만들기 · 중간 연산 · 최종 연산)와 함께 줄마다 `mark`로 강조한다
  - chain은 중간 연산 줄과 최종 연산 줄을 다른 이름표로 구분한다
  - sorted는 두 코드와 결과를 위아래로 비교한다
  - once 오류는 `.warn`, 결과는 코드 블록 아래 콘솔
  - 도입 장면은 150px `.big`에 `.stream()`, `.hook`에 `filter → map → toList`

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 즉 실제로 컴파일·실행한 예제의 출력과 실행 중 오류 문구가 대본의 기대값과 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 18편 빌드의 출력 대조 헬퍼와 실행 중 오류 대조 헬퍼를 그대로 쓴다. 새 테스트 지점은 만들지 않는다.
- **대조 항목**
  - 출력 대조(7건): why(`removeIf`), why(스트림 + 원본), flow, map, chain, sorted, count
  - 실행 중 오류 대조(1건): once(앞선 출력 `3` 포함)
  - 기대와 다르면(출력이 다르거나, 기대한 오류가 안 나거나, 컴파일 오류가 나면) 빌드를 멈춘다
  - 화면에 체인만 보여 주는 장면도 리스트를 만드는 숨긴 코드와 함께 실제로 실행한다
- **빌드 이후 검증** (기존 절차)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(why 또는 sorted)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **수동 검토**: 나레이션 문장이 화면의 기대 결과와 같은지 직접 확인한다(예: "팔십오, 구십이가 남고 원본은 그대로", "두 명", "이백오십오"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 18편 빌드의 출력·실행 중 오류 대조 헬퍼와 removeIf·sort 장면, 17편의 리스트 결과 칩.
