# 스펙: 자바 입문 스물세 번째 — 동기화 더 깊이

Status: resolved

## Problem Statement

22편 "스레드"는 경쟁 조건을 `synchronized` 메소드로 고쳤다. 그런데 화면의 `inc()`는 `count++`를 만 번 도는 메소드 **전체**를 잠갔다. 그래서 한 스레드가 반복을 다 끝내야 다른 스레드가 들어오고, 결과(20000)는 맞지만 사실상 순차 실행이 됐다. 시청자는 이 점을 모른 채 "스레드 문제엔 메소드에 `synchronized`"라고 기억할 수 있다.

입문자가 다음으로 알아야 할 것은 다음과 같다.

- 잠그는 범위는 필요한 만큼만 좁힌다는 원칙과, 그 방법인 동기화 블록·잠금 객체
- `synchronized` 없이 카운터를 안전하게 올리는 `AtomicInteger`(원자적 연산). 22편의 "읽기→더하기→쓰기" 설명이 바로 이 도구가 필요한 이유다
- 변수뿐 아니라 `ArrayList` 같은 컬렉션도 여러 스레드가 함께 바꾸면 깨지고, 스레드 안전한 리스트로 감싸야 한다는 것

기준 자료: [../java-thread-shorts/not-covered.md](../java-thread-shorts/not-covered.md)의 후보 1, 같은 파일 2절의 "`synchronized` 범위".

## Solution

시리즈 스물세 번째 영상 "동기화 더 깊이"를 기존 영상과 같은 디자인·제작 방식으로 만든다. 썸네일도 이 영상 하나만 만든다.

- 영상 규격: 1080×1920, 2분 30초 이하, 1.2배 템포
- 흐름: 22편 `synchronized` 메소드의 문제를 짚고 → 필요한 줄만 잠그고(동기화 블록) → `synchronized` 없이 푼 다음(`AtomicInteger`) → 같은 문제를 리스트에서 보고 고친다(`synchronizedList`)
- 예시 데이터: 22편과 같다. 공유 변수 `count`, 스레드 2개가 각각 10000번. 리스트 장면은 같은 방식으로 각각 10000번 `add`

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "동기화 <em>더 깊이</em>". 22편의 `synchronized`는 20000을 맞췄지만 문제가 하나 있었다 |
| scope | 1. 메소드 전체를 잠그면 | 1 | 22편 코드 `static synchronized void inc()`(만 번 반복) → 항상 `20000`. 그 아래 그림: 스레드 1이 만 번을 다 돈 다음에야 스레드 2가 들어간다. 결과는 맞지만 사실상 순차 실행. 시간은 재지 않는다 |
| block | 2. 동기화 블록 | 2 | 잠금 객체 `lock`을 만들고 반복 안의 `count++` 한 줄만 `synchronized (lock) { }`로 감싼다 → 항상 `20000`. 두 스레드가 **같은** 잠금 객체를 써야 한다 |
| atomic | 3. AtomicInteger | 3 | `AtomicInteger count` + `count.incrementAndGet()` → `synchronized` 없이 항상 `20000`. 읽기·더하기·쓰기를 한 번에 하는 원자적 연산(쪼개지지 않는) |
| list | 4. 스레드 안전 리스트 | 4 | `ArrayList`에 두 스레드가 각각 10000번 `add` → 크기 예시 `14302`(20000보다 적고, 예외가 나기도 함). `Collections.synchronizedList(new ArrayList<>())`로 바꾸면 항상 `20000` |
| outro | 정리 | 5 | 목록 전체 → 나레이션에 맞춰 줄 강조. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 스물세 번째, 동기화 더 깊이"라는 주제를 바로 알고 싶다. 22편에서 이어지는 편이라는 것을 알 수 있기 때문이다.
2. 시청자로서, 도입에서 22편의 `synchronized`에 문제가 있었다는 말을 듣고 싶다. 이번 편을 봐야 하는 이유가 생기기 때문이다.
3. 시청자로서, 22편과 같은 `count` 예제를 다시 보고 싶다. 새 예제를 익히는 부담 없이 차이에만 집중할 수 있기 때문이다.
4. 시청자로서, 메소드 전체를 잠그면 한 스레드가 반복을 다 끝낸 뒤에야 다른 스레드가 들어온다는 그림을 보고 싶다. "결과가 맞다"와 "스레드를 잘 썼다"가 다르다는 것을 알 수 있기 때문이다.
5. 시청자로서, 그 방식이 사실상 순차 실행이라는 설명을 듣고 싶다. 잠금 범위를 왜 좁혀야 하는지 이해할 수 있기 때문이다.
6. 시청자로서, `synchronized (lock) { count++; }`처럼 필요한 줄만 감싸는 동기화 블록을 보고 싶다. 잠금 범위를 직접 정하는 법을 알 수 있기 때문이다.
7. 시청자로서, 괄호 안의 `lock`이 잠금 객체이고 두 스레드가 같은 객체를 써야 한다는 것을 보고 싶다. 서로 다른 객체로 잠그면 막아지지 않는다는 실수를 피할 수 있기 때문이다.
8. 시청자로서, 잠금 객체를 `static final Object`로 만드는 코드를 보고 싶다. 따라 칠 때 무엇을 선언해야 하는지 알 수 있기 때문이다.
9. 시청자로서, 동기화 블록으로 바꿔도 항상 20000이 나오는 결과를 보고 싶다. 범위를 좁혀도 정확하다는 것을 확인할 수 있기 때문이다.
10. 시청자로서, `AtomicInteger`와 `incrementAndGet()`으로 `synchronized` 없이 20000이 나오는 것을 보고 싶다. 카운터에는 더 간단한 도구가 있다는 것을 알 수 있기 때문이다.
11. 시청자로서, `incrementAndGet()`이 읽기·더하기·쓰기를 한 번에 하는 원자적 연산이라는 설명을 22편의 세 단계 그림과 이어서 듣고 싶다. 왜 안전한지 이해할 수 있기 때문이다.
12. 시청자로서, 값을 꺼낼 때 `count.get()`을 쓰는 것을 보고 싶다. `AtomicInteger`는 그냥 `int`처럼 쓸 수 없다는 것을 알 수 있기 때문이다.
13. 시청자로서, `ArrayList`에 두 스레드가 10000번씩 넣으면 크기가 20000보다 적게 나오는 결과를 보고 싶다. 변수만이 아니라 컬렉션도 경쟁 조건에 걸린다는 것을 알 수 있기 때문이다.
14. 시청자로서, 리스트 예제가 값이 빠지기도 하고 예외가 나기도 한다는 말을 듣고 싶다. 내가 실행했을 때 예외가 나와도 당황하지 않기 때문이다.
15. 시청자로서, 결과 숫자가 실행할 때마다 다르다는 것을 듣고 싶다. 화면 숫자와 내 결과가 달라도 이해할 수 있기 때문이다.
16. 시청자로서, `Collections.synchronizedList`로 감싸면 항상 20000이 나오는 것을 보고 싶다. 18편의 `ArrayList`를 스레드에서 안전하게 쓰는 법을 알 수 있기 때문이다.
17. 시청자로서, "스레드 안전"이라는 말의 뜻을 듣고 싶다. 다른 자료에서 같은 말을 만나도 알아볼 수 있기 때문이다.
18. 시청자로서, 정리 장면에서 여섯 가지 핵심을 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
19. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
20. 시청자로서, 모바일 화면에서 코드와 결과 상자가 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
21. 시청자로서, 화면 코드를 그대로 따라 쳐도 같은 종류의 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
22. 시청자로서, 피드·채널 화면에서 주제가 바로 보이는 썸네일을 보고 싶다. 볼 영상을 고르기 쉽기 때문이다.
23. 제작자로서, 항상 20000이 나와야 하는 예제도 여러 번 실행해 검증하길 원한다. 한 번 맞은 것을 우연으로 착각하지 않기 위해서다.
24. 제작자로서, 리스트 예제처럼 매번 다른 결과는 고정 예시로 그리고, 다시 빌드해도 `index.html`이 바뀌지 않길 원한다. 결과물을 안정적으로 관리하기 위해서다.
25. 제작자로서, 썸네일이 영상과 같은 디자인 토큰·글꼴을 쓰길 원한다. 시리즈의 일관성을 지키기 위해서다.
26. 제작자로서, 썸네일 원본을 영상 폴더에 남기고 PNG는 커밋하지 않길 원한다. 다시 만들 수 있고 저장소가 무거워지지 않기 때문이다.
27. 제작자로서, 디자인·템포·자막 방식이 22편과 같길 원한다. 시리즈의 일관성을 지키기 위해서다.
28. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고, `not-covered.md`의 **[23편 예정]**을 **[23편 완료]**로 바꾸고 싶다. 다음 편 기획이 이 파일에서 출발하기 때문이다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-sync-shorts`. 22편(`java-thread-shorts`)의 음성 생성 스크립트와 빌드 스크립트를 복사해 장면만 바꾼다(`J.load(speed=1.2)`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: `자바 입문 <em>동기화</em> 정리`. 진행 표시 5칸: scope → 1, block → 2, atomic → 3, list → 4, outro → 5.
- **용어** (GLOSSARY, 기획 단계에서 등록함): 동기화 블록, 잠금 객체, 원자적 연산, 스레드 안전. 기존 용어 스레드·경쟁 조건·동기화·static 필드·static 메소드를 그대로 쓴다.
  - "잠금"은 단독으로 쓰지 않고 "잠금 객체"로만 쓴다. "락", "모니터", "임계 구역"은 쓰지 않는다
  - 원자적 연산은 화면에 처음 한 번 "(쪼개지지 않는)"을 덧붙인다
- **읽는 법**: 싱크로나이즈드 블록, 잠금 객체, 아토믹 인티저, 인크리먼트 앤 겟, 겟, 컬렉션스 점 싱크로나이즈드 리스트, 어레이 리스트, 애드, 사이즈.
- **예제 구조**: 22편 race·sync와 같다. `count`(또는 `list`)와 `inc()`(또는 `add()`)는 `Main`의 static 멤버이고, `main`은 `new Thread(Main::inc)` 두 개를 `start`·`join`한 뒤 결과를 출력한다. `J.MAIN_THROWS = "InterruptedException"`. 화면에는 22편처럼 바뀌는 부분(멤버 선언과 메소드)을 중심으로 그리고, 스레드 시작·`join` 줄은 22편과 같은 방식으로 처리한다.
- **장면별 기대 결과** (대조 기준, 모두 기존 `jmulti`로 여러 번 실행)
  - scope: 매 실행 `20000` (22편 sync와 같은 코드)
  - block: 매 실행 `20000`
  - atomic: 매 실행 `20000`
  - list(ArrayList): 매 실행 크기가 20000 이하이고, 한 번 이상 20000 미만. 화면 예시 `14302`(기획 중 실제로 관찰한 값). 라벨 "실행 결과 예시 · 매번 다름"
  - list(synchronizedList): 매 실행 `20000`
- **리스트 예제의 예외**: `ArrayList` 동시 `add`는 일부 실행에서 작업 스레드가 `ArrayIndexOutOfBoundsException`으로 끝난다. 이 예외는 그 스레드만 끝내고 프로그램 종료 코드는 0이라서, `jmulti`는 실행 오류로 보지 않고 표준 출력(크기)만 검사한다. 이 동작에 기대므로 헬퍼는 고치지 않는다. 화면에는 예외 상자를 그리지 않고, 나레이션과 `.warn` 한 줄("예외가 나기도 해요")로만 알린다.
- **scope 장면의 그림**: 새 화면 조각 하나. 가로 막대 두 줄로 "스레드 1 ██████ → 스레드 2 ██████"(k1 주황, k2 초록 — 디자인 토큰의 k1·k2)처럼 시간축에서 차례로 이어지는 모습을 보여 준다. 실제 시간을 재지 않는 개념도이므로 숫자·초 단위는 넣지 않는다. 디자인 토큰 색만 쓰고, 빌드 스크립트 안의 짧은 HTML로 만든다(공용 모듈에 넣지 않음).
- **33자 제한**: 긴 줄은 의미 단위로 나눈다.
  - `static final Object lock =` / `new Object();`
  - `static AtomicInteger count =` / `new AtomicInteger();`
  - `Collections.synchronizedList(` / `new ArrayList<>());`
  - `synchronized (lock) {` / `count++;` / `}`처럼 블록은 세 줄로
- **import**: `AtomicInteger`(`java.util.concurrent.atomic`)와 `List`·`ArrayList`·`Collections`(`java.util`)는 import가 필요하다. 화면에 import 줄을 보여 줄지는 33자 제한과 화면 높이를 보고 구현 때 정하되, 실행 코드에는 반드시 넣는다.
- **사실 표현 주의**
  - 동기화 블록은 "필요한 줄만 잠근다"는 **원칙**으로 말한다. 이 예제는 반복 안에 다른 일이 없어 실제로 더 빨라지지는 않으므로 "더 빠르다"고 말하지 않는다
  - `AtomicInteger`도 "더 빠르다"고 단정하지 않는다. "싱크로나이즈드 없이", "한 번에"로 말한다("잠금"은 "잠금 객체"로만 쓰므로 "잠금 없이"라고 하지 않는다)
  - 리스트 결과는 특정 숫자를 말하지 않는다("이만보다 적게, 실행할 때마다 달라요")
  - `synchronizedList`는 `add`·`get` 같은 메소드 하나하나를 안전하게 할 뿐이라는 한계는 이번 편에서 말하지 않는다. 다만 "이제 어떤 사용이든 안전하다"처럼 넓게 말하지도 않는다
- **썸네일** (이 영상 하나만)
  - 1080×1920 PNG. 빌드 스크립트가 영상과 같은 CSS(토큰·Pretendard·배경 그라디언트)로 영상 폴더에 `thumbnail.html`을 만든다
  - 구성: 작은 글씨 "자바 입문 23" → 큰 글씨 "동기화 <em>더 깊이</em>"(주황 강조) → 키워드 칩 `synchronized 블록` · `AtomicInteger` · `synchronizedList`
  - 쇼츠 UI에 가리지 않도록 하단 300px에는 아무것도 두지 않는다
  - PNG는 `output/java-sync-shorts-thumb.png`(git 제외). 렌더링 방법(HyperFrames snapshot 또는 헤드리스 브라우저 캡처)은 구현 때 정하고, 정한 명령을 티켓에 남긴다
  - 썸네일을 매번 만드는 정식 절차(CLAUDE.md 반영)는 이번 결과를 보고 따로 정한다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 실제로 컴파일·실행한 예제의 출력이 대본의 기대 조건을 만족하는지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 빌드 자체. 모든 예제를 기존 `jmulti`로 여러 번 실행해 조건을 검사한다. 새 헬퍼나 새 검증 지점은 만들지 않는다.
- **대조 항목**
  - 매 실행 `20000`: scope, block, atomic, synchronizedList
  - 매 실행 20000 이하 + 한 번 이상 미만: ArrayList

## Out of Scope

- `volatile`(별도 "멈춤 신호" 예제가 필요), `ConcurrentHashMap`, 데드락
- `Lock`·`ReentrantLock`, `wait`/`notify`
- `ExecutorService`·스레드 풀, `Callable`·`Future`, 가상 스레드 (후보 2 → 24편 추천)
- `interrupt()`, 데몬 스레드, 스레드 상태
- 실행 시간 측정, 잠금 범위에 따른 성능 비교
- `synchronizedList`로 감싸도 여러 메소드를 묶은 동작(확인 후 추가 등)은 안전하지 않다는 한계
- 디자인·템포·제작 도구의 변경(scope 장면 그림, 썸네일 제외)
