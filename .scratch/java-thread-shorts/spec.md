# 스펙: 자바 입문 스물두 번째 — 스레드

Status: resolved

## Problem Statement

지금까지의 예제는 모두 위에서 아래로 한 줄씩 실행됐다. 시청자는 이것이 **메인 스레드** 하나가 `main`을 실행한 결과라는 것을 모른다. 19편에서 람다를, 20편에서 체크 예외를 배웠으므로 `new Thread(() -> ...)`와 `InterruptedException`을 이해할 준비가 됐다.

입문자가 스레드를 처음 배울 때 특히 막히는 점은 다음과 같다.

- 스레드가 무엇인지, 메인 스레드가 원래 있었다는 것
- `start()`를 해야 새 스레드가 생기고, `run()`을 직접 부르면 그냥 메소드 호출이 된다는 것
- 여러 스레드의 출력 순서가 보장되지 않고, 메인 스레드는 다른 스레드를 기다리지 않는다는 것
- 끝날 때까지 기다리려면 `join()`이 필요하다는 것, `sleep`·`join`에 왜 `throws`가 붙는지
- 같은 변수를 여러 스레드가 바꾸면 값이 사라진다는 것(경쟁 조건)과 `synchronized`로 막는 법

3분 이하 세로 쇼츠 한 편으로, 실제로 실행한 결과로 이 내용을 정확히 보여 줄 영상이 필요하다.

## Solution

시리즈 스물두 번째 영상 "스레드"를 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포
- 흐름: 메인 스레드 하나에서 출발해 스레드를 만들고 → `run()` 함정을 피하고 → 기다리고 → 같은 변수를 함께 바꾸다 망가지고 → 동기화로 고친다
- 예시 데이터: STEP 1·2는 시리즈 데이터 민수 85(k1) · 서준 92(k2)를 출력하는 두 스레드. STEP 3·4는 점수와 무관한 공유 변수 `count`(스레드 2개가 각각 10000번 `count++`)
- 실행할 때마다 순서·값이 달라지는 예제는 여러 번 실행해 검증하고, 화면에는 고정한 예시 하나를 "실행 결과 예시"로 그린다

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "스레드" 제목. 스레드 = 코드를 실행하는 흐름. 지금까지는 메인 스레드 하나였다 |
| start | 1. 스레드 만들기 | 1 | `new Thread(() -> System.out.println("민수 85"))`, 서준도 같은 방식 → 둘 다 `start()` → 마지막에 `main 끝` 출력. 결과 예시 `민수 85 / main 끝 / 서준 92`. 출력 순서는 보장되지 않고, 메인 스레드는 기다리지 않는다. `.note`: `extends Thread`로 만드는 방식도 있다 |
| run-trap | 1-1. `run()` 함정 | 1 | 스레드 안에서 `Thread.currentThread().getName()` 출력. `start()`면 `Thread-0`, `run()`을 직접 부르면 `main` — 새 스레드 없이 그냥 메소드 호출 |
| join | 2. `sleep`과 `join` | 2 | 스레드가 `Thread.sleep(1000)` 뒤 `민수 85` 출력. `join` 없으면 `main 끝`이 먼저, `t.join()` 한 줄을 넣으면 `민수 85 → 채점 끝`. `sleep`·`join`은 체크 예외 `InterruptedException`을 던져 `main`에 `throws` (20편 연결) |
| race | 3. 경쟁 조건 | 3 | `static int count`를 두 스레드가 각각 10000번 `count++`, 둘 다 `join` 뒤 출력. 결과 예시 `13426` (실행할 때마다 다름, 20000보다 적음). `count++`는 읽기·더하기·쓰기 세 단계라 겹치면 값이 사라진다 |
| sync | 4. `synchronized` | 4 | `static synchronized void add() { count++; }`로 바꾸면 한 번에 한 스레드만 들어가 항상 `20000` |
| outro | 정리 | 5 | 목록 전체 → 나레이션에 맞춰 줄 강조. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "자바 입문 스물두 번째, 스레드"라는 주제를 바로 알고 싶다. 시리즈의 다음 편인지 알 수 있기 때문이다.
2. 시청자로서, 스레드가 코드를 실행하는 흐름이고 지금까지의 예제는 메인 스레드 하나로 돌았다는 것을 듣고 싶다. 새 개념이 기존 지식과 이어지기 때문이다.
3. 시청자로서, `new Thread`에 람다를 넘겨 스레드를 만드는 모습을 보고 싶다. 19편 람다가 어디에 쓰이는지 알 수 있기 때문이다.
4. 시청자로서, `start()`를 불러야 스레드가 실행된다는 것을 보고 싶다. 만들기만 해서는 실행되지 않는다는 것을 알 수 있기 때문이다.
5. 시청자로서, 세 줄의 출력 결과를 보고 출력 순서가 보장되지 않는다는 것을 듣고 싶다. 스레드 코드의 결과를 순서에 기대면 안 된다는 것을 알 수 있기 때문이다.
6. 시청자로서, `main 끝`이 중간에 나온 이유가 메인 스레드가 기다리지 않기 때문이라는 설명을 듣고 싶다. 스레드가 따로 돈다는 것을 실감할 수 있기 때문이다.
7. 시청자로서, `extends Thread`로 만드는 방식도 있다는 메모를 한 줄 보고 싶다. 다른 자료에서 그 방식을 만나도 알아볼 수 있기 때문이다.
8. 시청자로서, `start()`면 `Thread-0`, `run()`을 직접 부르면 `main`이 출력되는 비교를 보고 싶다. `run()`을 부르면 새 스레드가 생기지 않는다는 함정을 피할 수 있기 때문이다.
9. 시청자로서, 1초 쉬는 스레드를 기다리지 않으면 `main 끝`이 먼저 나오는 것을 보고 싶다. 기다림이 필요한 상황을 알 수 있기 때문이다.
10. 시청자로서, `t.join()` 한 줄을 넣으면 `민수 85` 뒤에 `채점 끝`이 나오는 것을 보고 싶다. 스레드가 끝날 때까지 기다리는 법을 알 수 있기 때문이다.
11. 시청자로서, `sleep`·`join`이 체크 예외 `InterruptedException`을 던져서 `main`에 `throws`를 붙인다는 것을 20편과 연결해 듣고 싶다. 왜 그 줄이 붙는지 이해할 수 있기 때문이다.
12. 시청자로서, 두 스레드가 같은 `count`를 10000번씩 더했는데 20000보다 적게 나오는 결과를 보고 싶다. 경쟁 조건이 실제로 일어난다는 것을 확인할 수 있기 때문이다.
13. 시청자로서, 결과가 실행할 때마다 다르다는 것을 듣고 싶다. 화면 숫자와 내 결과가 달라도 당황하지 않기 때문이다.
14. 시청자로서, `count++`가 읽기·더하기·쓰기 단계로 나뉘어 겹치면 값이 사라진다는 설명을 보고 싶다. 경쟁 조건이 왜 생기는지 이해할 수 있기 때문이다.
15. 시청자로서, 이 문제의 이름이 경쟁 조건(레이스 컨디션)이라는 것을 보고 싶다. 다른 자료에서 같은 말을 만나도 알아볼 수 있기 때문이다.
16. 시청자로서, `synchronized` 메소드로 바꾸면 항상 20000이 나오는 것을 보고 싶다. 경쟁 조건을 막는 법을 알 수 있기 때문이다.
17. 시청자로서, `synchronized`가 한 번에 한 스레드만 들어가게 한다는 설명을 듣고 싶다. 동기화가 무엇을 하는지 정확히 알 수 있기 때문이다.
18. 시청자로서, 정리 장면에서 여섯 가지 핵심을 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
19. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
20. 시청자로서, 모바일 화면에서 코드와 결과 상자가 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
21. 시청자로서, 화면에 나온 코드를 그대로 따라 쳐도 같은 종류의 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
22. 제작자로서, 순서·값이 매번 다른 예제도 빌드 중에 여러 번 실제로 실행해 검증하길 원한다. "실행한 결과로만 보여 준다"는 원칙을 스레드 편에서도 지키기 위해서다.
23. 제작자로서, 그런 예제의 화면 결과 상자는 빌드할 때마다 바뀌지 않는 고정 예시이길 원한다. 다시 빌드해도 `index.html`이 달라지지 않기 위해서다.
24. 제작자로서, 영상에 나온 예제 프로그램 전체가 "실행할 때마다 다름" 주석과 함께 예제 기록 파일로 남길 원한다. 시청자 질문에 같은 코드로 답할 수 있기 때문이다.
25. 제작자로서, 디자인·템포·자막 방식이 21편과 같길 원한다. 시리즈의 일관성을 지키기 위해서다.
26. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고 싶다. 시리즈 기록을 유지하기 위해서다.

## Implementation Decisions

- **새 영상 프로젝트**: `java-thread-shorts`. 21편(`java-file-io-shorts`)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(`J.load(speed=1.2)`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다. 파일 입출력 설정(`J.FILE`, 파일 내용 상자)은 쓰지 않는다.
- **상단 바 브랜드**: `자바 입문 <em>스레드</em> 정리`. 진행 표시 5칸: start·run-trap → 1, join → 2, race → 3, sync → 4, outro → 5.
- **용어** (GLOSSARY, 기획 단계에서 등록함): 스레드, 메인 스레드, 경쟁 조건, 동기화. 기존 용어 람다식·체크 예외·throws를 그대로 쓴다.
  - "쓰레드", "데이터 레이스"는 쓰지 않는다
  - "동시에 실행"은 "동시에 실행되는 것처럼 번갈아"처럼 완화한다(코어가 여러 개면 실제로 동시에 돌 수 있음)
  - 경쟁 조건은 화면에 처음 한 번 "(레이스 컨디션)"을 덧붙인다
- **읽는 법**: 스레드, 메인 스레드, 스타트, 런, 슬립, 조인, 인터럽티드 익셉션, 싱크로나이즈드, 겟 네임.
- **장면별 기대 결과** (대조 기준)
  - start: 매 실행의 출력 줄 묶음이 `민수 85`, `서준 92`, `main 끝` (순서 무관). 화면 예시 `민수 85 / main 끝 / 서준 92`
  - run-trap: `start()` 쪽 `Thread-0`, `run()` 쪽 `main` (항상 같음 → 기존 `jcode`)
  - join: `join` 없는 버전 `main 끝` → `민수 85`, `join` 있는 버전 `민수 85` → `채점 끝`. 1초 `sleep` 때문에 사실상 고정이지만, 여러 번 실행해 매번 이 순서인지 확인한다
  - race: 매 실행 결과가 20000 이하이고, 한 번 이상 20000 미만. 화면 예시 `13426`
  - sync: 매 실행 정확히 `20000`
- **새 컴파일·실행 헬퍼** `jmulti(sid, lines, shown, ok, runs=20, mark=(), ...)` (`tools/javashorts.py`)
  - 예제를 `runs`번 컴파일·실행하고, 매번의 출력을 `ok(out)`로 검사한다. 하나라도 거짓이면(또는 컴파일 오류·실행 중 예외) 빌드를 멈춘다. "한 번 이상" 조건이 필요한 경우를 위해 `ok`는 전체 출력 목록을 받을 수도 있게 한다(구현 때 형태 결정: 예를 들어 `ok_each`·`ok_all` 둘로 나누기)
  - 화면 결과 상자에는 실제 출력이 아니라 고정 예시 `shown`을 그린다. 라벨은 "실행 결과 예시"(race는 "실행 결과 예시 · 매번 다름")
  - 컴파일은 한 번만 하고 실행만 반복해 빌드 시간을 줄인다
  - 예제 기록 파일에는 실행할 때마다 순서·값이 다르다는 주석과 함께 남긴다
  - `docs/java-helpers.md` 헬퍼 표에 추가한다
  - 헬퍼를 추가한 뒤 기존 자바 영상 두 편 이상을 다시 빌드해 `index.html`·`examples.txt`가 그대로인지(`git diff`) 확인한다
- **`main`의 `throws`**: join·race·sync 장면은 `J.MAIN_THROWS = "InterruptedException"`. start·run-trap은 `throws` 없이 컴파일되는지 확인한다(`join`을 쓰지 않으므로).
- **33자 제한**: `new Thread(() -> System.out.println("민수 85"))`처럼 긴 줄은 람다 몸체 앞에서 줄을 바꾼다. `Thread.currentThread().getName()`은 변수에 담거나 줄을 나눈다.
- **사실 표현 주의**
  - 출력 순서는 "보장되지 않는다"로 말하고, 화면 예시는 실제로 관찰된 순서로 그린다(관찰: 로컬 20회 모두 `민수 85 / main 끝 / 서준 92`)
  - 경쟁 조건 결과는 특정 숫자를 말하지 않는다("이만보다 적게, 실행할 때마다 달라요")
  - `run()` 직접 호출은 오류가 아니라 "그냥 메소드 호출"이라고 정확히 말한다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 실제로 컴파일·실행한 예제의 출력이 대본의 기대 조건을 만족하는지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 빌드 자체. 순서·값이 바뀌는 예제는 `jmulti`가 여러 번 실행해 조건을 검사하고, 항상 같은 예제는 기존 `jcode`가 대조한다.
- **대조 항목**
  - 여러 번 실행: start(줄 묶음), join 두 버전(순서), race(20000 이하 + 한 번 이상 미만)
  - 한 번 실행: run-trap(`Thread-0` / `main`), sync(`20000`, 여러 번 실행해도 됨)
  - 기대와 다르면 빌드를 멈춘다
- **헬퍼 회귀 확인**: `jmulti` 추가 후 기존 자바 영상 두 편 재빌드 결과에 `git diff`가 없어야 한다.
- **빌드 이후 검증** (`tools/verify-video.sh java-thread-shorts`)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(join 또는 race)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **수동 검토**: 나레이션 문장이 화면 결과와 맞는지 직접 확인한다(예: "main 끝이 먼저 나와요", "이만보다 적게", "항상 이만"). 자동 대조는 예제 결과까지만 하기 때문이다.
- **참고할 기존 사례**: 21편 빌드 스크립트와 정리 장면, 20편 체크 예외 장면, 19편 람다 장면.

## Out of Scope

- `ExecutorService`·스레드 풀, 가상 스레드, `CompletableFuture`
- `extends Thread` 방식의 코드(메모 한 줄만)
- `synchronized` 블록, `AtomicInteger`, `volatile`, `Lock`
- `wait`/`notify`, 데드락, 스레드 상태, 우선순위, 데몬 스레드
- `interrupt()`의 자세한 설명(`InterruptedException`은 `throws`로 넘기는 것까지만)
- 디자인·템포·제작 도구의 변경(`jmulti` 헬퍼 추가 제외)
