# 스펙: Next.js 1편 — 클로저 (자바와 비교)

Status: resolved

배경 자료: [closure-reading.md](closure-reading.md) · 기획 결정: [decisions.md](decisions.md)

## Problem Statement

이 채널의 시청자는 자바 입문 시리즈로 람다식과 사실상 final을 배웠지만, 자바스크립트·Next.js는 처음이다. Next.js(React) 코드를 읽기 시작하면 곧바로 **클로저**를 만나는데, 자바 감각으로 보면 이상한 일이 생긴다.

- 자바에서는 컴파일 오류인 코드(붙잡은 변수를 나중에 바꾸기)가 자바스크립트에서는 그냥 돌아가고, 바뀐 값이 보인다
- 함수가 끝났는데도 안쪽 함수가 바깥 변수를 계속 쓴다
- 반복문에서 만든 함수가 모두 같은 값(마지막 값)을 내놓는다
- React 버튼을 누르고 3초 뒤에 본 값이 화면 숫자와 다르다(스냅샷)
- Next.js 서버 액션이 붙잡은 변수가 브라우저까지 오간다는 것을 모른다

이 차이를 "자바에서는 왜 막았나"와 함께, 실제로 실행한 결과로 3분 이하 세로 쇼츠 한 편에 정확히 보여 줄 영상이 필요하다. 이 영상은 새 **Next.js 시리즈의 1편**이다.

## Solution

새 시리즈 첫 영상 "Next.js 1편: 클로저"를 기존 영상과 같은 디자인·제작 방식으로 만든다.

- 영상 규격: 1080×1920, 약 2분 30초, 1.2배 템포(TTS `ko-KR-SunHiNeural`, rate `+34%`)
- 흐름: 자바스크립트 클로저를 보여 주고 → 같은 코드를 자바와 나란히 비교하고 → 자바가 막은 이유와 우회법 → 반복문 함정 → 실무(React 스냅샷, Next.js 서버 액션)에서 다시 만난다
- 예시 데이터: 영상 전체를 **카운터(`count`)** 로 통일(STEP 1·3·5-1). STEP 2의 `x`, STEP 4의 반복 변수만 짧은 별도 예제
- 두 언어 구분: 자바스크립트 = 파랑(`--blue`), 자바 = 초록(`--green`)

| id | 장면 | 진행 표시 | 내용 |
|---|---|---|---|
| hook | 도입 | — | `.hook` + 150px "클로저" 제목. "같은 코드인데 자바스크립트는 2, 자바는 컴파일 오류?" |
| counter | 1. 클로저란 | 1 | JS `makeCounter()`가 `let count = 0`을 두고 `() => ++count`를 돌려준다. `c1(), c1(), c2()` → `1 2 1`. 함수가 끝나도 `count`가 살아 있고, `c1`·`c2`는 각자의 `count`를 가진다. `.note`: `() => x`는 자바의 `() -> x` |
| capture | 2. 변수를 붙잡는다 | 2 | 위아래 비교: JS `let x = 1; f = () => x; x = 2; f()` → `2` / 자바 같은 코드 → 컴파일 오류(사실상 final). 자바스크립트는 변수 자체를 붙잡는다 |
| why | 3. 자바는 왜? | 3 | JLS가 든 이유: 계속 바뀌는 지역 변수를 붙잡으면 동시성 문제. 자바 `makeCounter`에서 `++count` → 컴파일 오류, `int[] count = {0}`으로 바꾸면 `1 2 1`. `.note`: 실무는 `AtomicInteger` — 22편 스레드 참고 |
| loop | 4. 반복문 함정 | 4 | 위아래 비교: JS `var` → `3,3,3`, `let` → `0,1,2` / 자바 일반 `for`의 `i`를 람다에서 쓰면 컴파일 오류, 향상된 `for` 변수는 가능 |
| snapshot | 5. React 스냅샷 | 5 | `+5` 버튼: `setNumber(number + 5)` 후 3초 뒤 `alert(number)` → 화면은 5인데 알림은 `0`. 그 렌더링의 값을 붙잡은 클로저라서. 해결: 업데이터 `c => c + 1` (실행 없음) |
| action | 5. 서버 액션 | 5 | 서버 컴포넌트 안의 `"use server"` 함수가 `version`을 붙잡는다. 붙잡은 변수는 브라우저로 갔다가 서버로 돌아온다 → Next.js가 자동 암호화 → `.warn` "암호화만 믿고 비밀값을 넣지 말 것" (실행 없음) |
| outro | 정리 | — | 목록 전체 → 나레이션에 맞춰 줄 강조. 👍 구독 · 좋아요 |

## User Stories

1. 시청자로서, 첫 화면에서 "Next.js 1편, 클로저"라는 주제를 바로 알고 싶다. 새 시리즈가 시작됐다는 것을 알 수 있기 때문이다.
2. 시청자로서, 도입에서 "같은 코드인데 자바스크립트는 2, 자바는 컴파일 오류"라는 질문을 듣고 싶다. 끝까지 볼 이유가 생기기 때문이다.
3. 시청자로서, 클로저가 "함수와, 그 함수가 만들어진 곳의 바깥 변수를 묶은 것"이라는 정의를 한 문장으로 보고 싶다. 이후 장면을 이 정의로 해석할 수 있기 때문이다.
4. 시청자로서, `makeCounter()`가 끝난 뒤에도 `c1()`이 1, 2를 세는 것을 보고 싶다. 바깥 함수가 끝나도 붙잡은 변수가 살아 있다는 것을 실감할 수 있기 때문이다.
5. 시청자로서, `c2()`가 다시 1부터 시작하는 것을 보고 싶다. 클로저마다 자기 변수를 따로 가진다는 것을 알 수 있기 때문이다.
6. 시청자로서, `() => x`가 자바의 `() -> x`와 같은 모양이라는 메모를 보고 싶다. 처음 보는 자바스크립트 문법을 아는 것에 대응시킬 수 있기 때문이다.
7. 시청자로서, `let`·`const`가 무엇인지 화면 메모로 짧게 보고 싶다. 자바스크립트를 몰라도 코드를 따라갈 수 있기 때문이다.
8. 시청자로서, 붙잡은 뒤 `x = 2`로 바꾸면 자바스크립트는 `2`를 내놓는 것을 보고 싶다. 자바스크립트가 값이 아니라 변수 자체를 붙잡는다는 것을 알 수 있기 때문이다.
9. 시청자로서, 같은 코드를 자바로 쓰면 컴파일 오류가 나는 것을 바로 아래에서 보고 싶다. 두 언어의 차이가 한눈에 보이기 때문이다.
10. 시청자로서, 자바 오류의 이유가 "사실상 final"이라는 것을 19편과 연결해 듣고 싶다. 이미 배운 규칙이 여기서 나온다는 것을 알 수 있기 때문이다.
11. 시청자로서, 자바스크립트는 파랑, 자바는 초록으로 항상 구분되길 원한다. 두 코드가 나란히 나와도 헷갈리지 않기 때문이다.
12. 시청자로서, 자바가 이 제한을 둔 이유가 공식 문서(JLS)에 "동시성 문제"라고 적혀 있다는 것을 듣고 싶다. 제한이 임의가 아니라는 것을 알 수 있기 때문이다.
13. 시청자로서, 자바로 카운터를 옮기면 `++count`에서 컴파일 오류가 나는 것을 보고 싶다. 자바스크립트 카운터를 그대로 옮길 수 없다는 것을 알 수 있기 때문이다.
14. 시청자로서, `int[] count = {0}`으로 바꾸면 자바도 `1 2 1`을 내는 것을 보고 싶다. 변수가 아니라 가리키는 내용을 바꾸는 우회법을 알 수 있기 때문이다.
15. 시청자로서, 실무에서는 `AtomicInteger`를 쓴다는 메모를 22편 스레드와 연결해 보고 싶다. 배열 우회가 정답이 아니라는 것을 알 수 있기 때문이다.
16. 시청자로서, 반복문에서 `var`로 만든 함수 세 개가 모두 `3`을 내놓는 것을 보고 싶다. 자바스크립트의 고전적인 함정을 피할 수 있기 때문이다.
17. 시청자로서, `let`으로 바꾸면 `0,1,2`가 나오는 것을 보고 싶다. 반복마다 새 변수가 생긴다는 해결법을 알 수 있기 때문이다.
18. 시청자로서, 자바는 일반 `for`의 `i`를 람다에서 아예 못 쓰고, 향상된 `for`는 쓸 수 있다는 것을 보고 싶다. 자바는 틀릴 수 있는 쪽을 컴파일러가 막는다는 것을 알 수 있기 때문이다.
19. 시청자로서, React 버튼을 누르고 3초 뒤 알림이 `0`인 예제를 보고 싶다. Next.js 화면 코드에서 클로저가 실제로 문제를 만드는 모습을 볼 수 있기 때문이다.
20. 시청자로서, 그 이유가 "그 렌더링의 스냅샷을 붙잡았기 때문"이라는 설명을 듣고 싶다. 앞에서 배운 클로저로 React 동작을 설명할 수 있기 때문이다.
21. 시청자로서, 업데이터 함수 `c => c + 1`이 해결법이라는 것을 보고 싶다. 실무에서 바로 쓸 수 있기 때문이다.
22. 시청자로서, Next.js 서버 액션도 클로저라서 바깥 변수를 붙잡는다는 것을 보고 싶다. Next.js에만 있는 클로저 동작을 알 수 있기 때문이다.
23. 시청자로서, 붙잡은 변수가 브라우저까지 갔다가 서버로 돌아온다는 것을 보고 싶다. 서버 코드라고 안심하면 안 된다는 것을 알 수 있기 때문이다.
24. 시청자로서, Next.js가 그 값을 자동으로 암호화하지만 암호화만 믿고 비밀값을 넣으면 안 된다는 경고를 보고 싶다. 보안 실수를 피할 수 있기 때문이다.
25. 시청자로서, 정리 장면에서 핵심을 한 화면에 보고, 나레이션에 맞춰 강조되는 줄을 따라가고 싶다. 복습하기 쉽기 때문이다.
26. 시청자로서, 모든 대사가 단어 단위로 맞춰진 한국어 자막으로 나오길 원한다. 소리 없이 봐도 이해할 수 있기 때문이다.
27. 시청자로서, 위아래로 쌓인 비교 장면도 모바일에서 읽히는 크기이길 원한다. 쇼츠는 휴대폰으로 보기 때문이다.
28. 시청자로서, 화면의 자바스크립트·자바 코드를 그대로 따라 쳐도 같은 결과가 나오길 원한다. 영상을 믿고 따라 할 수 있기 때문이다.
29. 제작자로서, 자바스크립트 예제도 빌드 중에 실제로 실행해 대본의 기대 결과와 대조하길 원한다. "실행한 결과로만 보여 준다"는 원칙을 새 언어에서도 지키기 위해서다.
30. 제작자로서, 실행할 수 없는 React·Next.js 코드는 실행 없이 보여 주되 33자 제한과 하이라이트는 똑같이 적용받길 원한다. 화면 규칙이 장면마다 달라지지 않기 위해서다.
31. 제작자로서, 자바스크립트 예제도 예제 기록 파일에 남기를 원한다. 시청자 질문에 같은 코드로 답할 수 있기 때문이다.
32. 제작자로서, 헬퍼를 추가해도 기존 자바 영상의 빌드 결과가 바뀌지 않길 원한다. 공용 모듈 수정이 다른 영상을 망가뜨리지 않기 위해서다.
33. 제작자로서, 디자인·템포·자막 방식이 자바 시리즈와 같길 원한다. 채널의 일관성을 지키기 위해서다.
34. 제작자로서, 업로드 후 README 영상 목록에 행을 추가하고 싶다. 시리즈 기록을 유지하기 위해서다.

## Implementation Decisions

- **새 영상 프로젝트**: `nextjs-closure-shorts`. 가장 최근 자바 영상(22편 스레드)의 음성 생성 스크립트와 빌드 스크립트를 복사해 만든다(`J.load(speed=1.2)`, TTS `+34%`). 디자인 토큰·글꼴·화면 구성·모션은 바꾸지 않는다.
- **상단 바 브랜드**: `Next.js <em>클로저</em> 정리`. 진행 표시 5칸: counter → 1, capture → 2, why → 3, loop → 4, snapshot·action → 5. outro는 칸 없음(22편과 같게).
- **용어** (GLOSSARY, 기획 단계에서 등록함): 클로저, 붙잡다, 스냅샷. 기존 용어 람다식·사실상 final·원자적 연산·스레드 안전을 그대로 쓴다.
  - "붙잡다"는 화면에 처음 한 번 "(캡처)"를 덧붙인다
  - "값을 복사한다"는 JLS 원문 표현이 아니므로 단정하지 않는다. 자바는 "바뀌지 않는 변수만 붙잡을 수 있다"까지만 말한다
- **읽는 법**: 넥스트 제이에스, 자바스크립트, 바 / 렛 / 콘스트, 유즈 서버, 유즈 스테이트, 아토믹 인티저, 인트 배열. TTS로 들어 보고 어색한 것만 고친다.
- **장면별 기대 결과** (대조 기준)
  - counter: JS 출력 `1 2 1`
  - capture: JS 출력 `2` / 자바 컴파일 오류 문구에 `effectively final`
  - why: 자바 `++count` 버전 컴파일 오류 문구에 `effectively final` / `int[]` 버전 출력 `1 2 1`
  - loop: JS `var` 버전 `3,3,3`, `let` 버전 `0,1,2` / 자바 일반 `for` 버전 컴파일 오류 문구에 `effectively final`, 향상된 `for` 버전 출력 `0 1 2`(형식은 구현 때 결정, 실제 실행값으로)
  - snapshot·action: 실행하지 않는다
- **공용 모듈 확장** (`javashorts` — 자바 영상 공용 빌드 모듈)
  - **자바스크립트 실행·대조 헬퍼**: `node`로 예제를 실행하고 출력이 `expect`와 같아야 한다. 다르거나 실행 중 예외가 나면 빌드를 멈춘다. 결과 상자는 실제 출력으로 그리고, 예제 기록 파일에 자바스크립트 예제로 구분해 남긴다. 자바 헬퍼(`jcode`)와 같은 모양의 인자(`sid, lines, expect, mark, sm`)를 받는다
  - **보여 주기 전용 헬퍼**: 실행 없이 코드 블록만 그린다. 33자 제한·하이라이트·`mark`는 똑같이 적용한다. 예제 기록 파일에 "실행하지 않음(React·Next.js 코드)" 주석과 함께 남긴다
  - **하이라이터 키워드 추가**: `let`, `const`, `var`, `function`, `return`, `async`, `await`, `export`, `default`, `throw`, `new`, `if` 등 자바스크립트 키워드와 `=>`를 하이라이트한다. 자바 키워드 목록은 그대로 둔다(추가만). `"use server"`는 문자열(초록)로 그대로 둔다
  - `docs/java-helpers.md` 헬퍼 표에 두 헬퍼를 추가한다
  - 추가 뒤 기존 자바 영상 두 편 이상을 다시 빌드해 `index.html`·`examples.txt`가 그대로인지(`git diff`) 확인한다. 키워드 추가가 기존 자바 코드의 색을 바꾸는 경우(예: 자바 코드에 쓰인 `var`)가 있으면 그 영향도 여기서 드러난다
- **비교 장면 레이아웃** (capture, loop): `.vs` 2열은 33자 코드가 들어가지 않으므로 **위아래로 쌓는다**. 위 카드 자바스크립트, 아래 카드 자바. 코드는 `sm`(34px). 카드마다 라벨("JavaScript"/"Java")과 결과 상자(출력 / 컴파일 오류)를 붙인다. 라벨 색은 영상 전용 CSS에서 자바스크립트 `--blue`, 자바 `--green`으로 정한다(디자인 토큰은 그대로).
- **자바 예제 설정**: 함수형 인터페이스(`Supplier`, `IntSupplier` 등)를 쓰므로 `J.IMPORTS`에 `java.util.function.*`. `makeCounter`는 `members=`로 `Main` 안의 `static` 메소드로 넣는다.
- **33자 제한**: JS `makeCounter`는 `function makeCounter() {` / `let count = 0;` / `return () => ++count;`로 나눈다. 서버 액션 코드는 공식 예제를 줄여 `publishVersion` → `version`, `getLatestVersion()` → `getVersion()`, `throw` 문구는 짧은 한글 또는 생략(`...`)으로 바꾼다. React 예제는 `onClick` 핸들러 몸체만 보여 준다.
- **사실 표현 주의** (나레이션은 공식 문서 범위 안에서만)
  - 클로저 정의는 MDN 정의를 풀어 쓴다
  - 자바의 제한 이유는 JLS §15.27.2 "동시성 문제"만 말한다
  - 서버 액션: 붙잡은 변수가 클라이언트로 보내졌다가 돌아온다 / Next.js가 자동 암호화한다 / 암호화에만 의존하는 것은 권장하지 않는다 — 이 세 가지만 말한다. 키 생성 방식·환경 변수는 말하지 않는다
  - React: "상태는 스냅샷처럼 동작한다"(react.dev 표현)로 말한다

## Testing Decisions

- **좋은 테스트의 기준**: 시청자가 화면에서 보는 결과를 검사한다. 실제로 실행·컴파일한 예제의 출력·오류가 대본의 기대 결과와 같은지 본다. 빌드 스크립트 내부 구조나 HTML 마크업은 검사하지 않는다.
- **테스트 지점은 하나**: 빌드 자체. 자바 예제는 기존 `jcode`·`jce`가, 자바스크립트 예제는 새 실행·대조 헬퍼가 대조하고, 기대와 다르면 빌드를 멈춘다.
- **대조 항목**
  - 자바스크립트 실행: counter(`1 2 1`), capture(`2`), loop(`3,3,3` / `0,1,2`)
  - 자바 컴파일 오류: capture, why(`++count`), loop(일반 `for`)
  - 자바 실행: why(`int[]` → `1 2 1`), loop(향상된 `for`)
  - 실행 없음: snapshot, action — 대신 수동 검토 대상
- **헬퍼 회귀 확인**: 헬퍼·키워드 추가 후 기존 자바 영상 두 편 재빌드 결과에 `git diff`가 없어야 한다.
- **빌드 이후 검증** (`tools/verify-video.sh nextjs-closure-shorts`)
  - HyperFrames check: 오류 0건, 레이아웃 겹침·넘침 없음. `line_unread` 경고는 허용한다
  - snapshot: 모든 장면을 확인하고, 가장 빽빽한 장면(capture 또는 loop의 위아래 비교)을 390px 폭으로 줄여 모바일 가독성을 확인한다
  - 자막: 대사 중 자막 없는 시간이 0초인지 확인한다
  - 렌더링 후 ffprobe: 1080×1920, 오디오 트랙 존재
- **수동 검토**: 나레이션 문장이 화면 결과와 맞는지("이, 그대로 출력돼요", "세 개 모두 삼") 확인한다. snapshot·action 장면은 나레이션이 [closure-reading.md](closure-reading.md) 5·6절의 공식 문서 문장 범위 안인지 확인한다.
- **참고할 기존 사례**: 22편 빌드 스크립트·정리 장면, 19편 람다 영상의 사실상 final 장면(컴파일 오류 표시), `jce`·`cterm` 컴파일 오류 상자.

## Out of Scope

- 자바스크립트 `this`, 화살표 함수와 일반 함수의 차이, 호이스팅
- 자바 지역 클래스·익명 클래스(람다식만 보여 준다)
- 서버 액션 암호화 키 설정(`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`), 셀프 호스팅, `taint` API
- `useEffect` 의존성 배열의 자세한 설명(업데이터 함수 해결법까지만)
- React·Next.js 코드의 실제 실행(Next.js 프로젝트 생성 없음)
- 디자인·템포·제작 도구의 변경(두 헬퍼·키워드 추가·영상 전용 CSS 제외)
