STEP 1 · 클로저란

함수 + 바깥 변수

함수가 끝나도 붙잡은(캡처) 변수는 살아 있다

JavaScript1 2 1
function makeCounter() {
let count = 0;
return () => ++count;
}
const c1 = makeCounter();
const c2 = makeCounter();
console.log(c1(), c1(), c2());
() => x = 자바의 () -> x
let · const = 변수 선언
c1·c2는 각자의 count
makeCounter()를 부를 때마다 새로 생김
STEP 2 · 변수를 붙잡는다

값이 아니라 변수

자바스크립트는 바뀐 값까지 본다

JavaScript2
let x = 1;
const f = () => x;
x = 2;
console.log(f());
Java컴파일 오류
int x = 1;
Supplier<Integer> f = () -> x;
x = 2;
System.out.println(f.get());
… must be final or effectively final
자바는 "클로저" 대신 람다식의 캡처
사실상 final만 캡처 · 19편 람다식 참고
STEP 3 · 자바는 왜?

바뀌는 변수는 금지

동시성 문제를 막으려고 (자바 언어 명세)

Java · int++count → 컴파일 오류
static IntSupplier
makeCounter() {
int count = 0;
return () -> ++count;
}
Java · int 배열c1, c1, c2 → 1 2 1
static IntSupplier
makeCounter() {
int[] count = {0};
return () -> ++count[0];
}
배열을 가리키는 변수는 그대로
실무에서는 AtomicInteger · 22편 스레드 참고
STEP 4 · 반복문 함정

모두 3이 나온다?

var는 하나를 함께 · let은 반복마다 새로

JavaScriptvar → 3 3 3let → 0 1 2
const a = [];
for (var i = 0; i < 3; i++)
a.push(() => console.log(i));
a.forEach(f => f());
Java일반 for → 컴파일 오류향상된 for → 0 1 2
// list: IntSupplier 리스트
for (int i = 0; i < 3; i++)
list.add(() -> i);
for (int n : new int[]{0, 1, 2})
list.add(() -> n);

STEP 5 · 업데이터 함수

세 번 더해도 1?

붙잡은 값 대신 함수를 넘긴다

붙잡은 값→ 1
// 클릭 한 번에 +3?
setNumber(number + 1);
setNumber(number + 1);
setNumber(number + 1);
업데이터 함수→ 3
// n = 바로 전 값
setNumber(n => n + 1);
setNumber(n => n + 1);
setNumber(n => n + 1);
업데이터는 다음 렌더링 값을 계산
붙잡은 number는 그대로 → 알림은 여전히 0

넥스트 제이에스, 클로저!
같은 코드인데, 자바스크립트는 이를 출력하고,
자바는 컴파일 오류가 나요.
이 차이가 바로 클로저예요.
자바와 비교하면서 정리해 드릴게요.
클로저는 함수와,
그 함수가 만들어진 곳의
바깥 변수를 묶은 거예요.
메이크 카운터 안에서
렛으로 카운트를 만들고,
카운트를 하나 올리는 함수를 돌려줘요.
화살표 모양은 자바의 람다식과 같아요.
메이크 카운터는 이미 끝났는데,
씨 원을 부르면 일,
또 부르면 이가 나와요.
안쪽 함수가 카운트를 붙잡고 있거든요.
씨 투는 새로 만든 카운터라서,
다시 일부터 세요.
자바스크립트 클로저는 값이
아니라 변수 자체를 붙잡아요.
엑스가 일일 때 함수를 만들고,
엑스를 이로 바꾼 뒤 부르면,
바뀐 값 이가 나와요.
같은 코드를 자바 람다식으로
쓰면 컴파일 오류예요.
자바에서는 이걸 보통
클로저라고 부르지 않고,
람다식의 캡처라고 해요.
그리고 사실상 파이널인
변수만 캡처할 수 있거든요.
자바는 왜 막았을까요?
자바 언어 명세는,
계속 바뀌는 지역 변수를 붙잡으면
동시성 문제가 생기기 쉽다고 설명해요.
그래서 카운터를 그대로 옮기면,
플러스 플러스 카운트에서
컴파일 오류가 나요.
인트 배열에 담으면,
배열을 가리키는 변수는 바뀌지 않아서, 일, 이,
일이 나와요.
실무에서는 아토믹 인티저를 써요.
반복문에는 함정이 있어요.
바로 만든 함수 세 개는
모두 삼을 출력해요.
바 변수는 하나뿐이라서,
반복이 끝난 뒤의 값을 함께 보거든요.
렛으로 바꾸면 반복마다 새 변수가 생겨서, 영, 일,
이가 나와요.
자바는 일반 포문의 아이를
람다식에서 쓰면 컴파일 오류예요.
향상된 포문의 변수는 반복마다
새 변수라서 쓸 수 있어요.
넥스트 제이에스 화면은 리액트 컴포넌트라서,
클로저를 자주 만나요.
플러스 오 버튼을 누르고,
삼 초 뒤에 넘버를 알림으로 띄우면,
화면은 오인데 알림은 영이에요.
리액트 상태는 스냅샷처럼 동작해서,
핸들러가 그 렌더링의 값을 붙잡고 있거든요.
그래서 붙잡은 값으로는 이전
값을 이어서 계산할 수 없어요.
넘버 더하기 일을 세 번 불러도,
세 번 모두 같은 영을 붙잡고 있어서,
결과는 일이에요.
넘버 대신 업데이터 함수를 넘기면,
리액트가 바로 전 값을 넣어 줘서,
결과는 삼이에요.
다만 이미 붙잡은 넘버는 그대로라서,
알림은 여전히 영이에요.

페이지 안에서 유즈 서버 함수를 만들면,
바깥의 버전 변수를 붙잡아요.

액션을 부를 때 서버로 돌아와요.
그래서 넥스트 제이에스가

비밀값은 붙잡지 마세요.
정리할게요.
클로저는 함수와 바깥 변수의 묶음이에요.
자바스크립트는 변수 자체를 붙잡아요.
자바는 사실상 파이널만,
동시성 문제 때문이에요.
반복문에서는 렛을 쓰세요.

서버 액션의 값은 브라우저를 오가요.
