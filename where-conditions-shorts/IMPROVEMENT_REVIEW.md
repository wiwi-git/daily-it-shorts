# WHERE 쇼츠 개선 검토서

대상: `where-conditions-shorts`  
검토일: 2026-10-29  
목적: 기존 디자인을 유지하면서 SQL 설명의 정확성, 쇼츠 전달력, 화면과 나레이션의 연결을 개선한다.

## 검토 결과

- 영상은 13장면, 총 153.66초(약 2분 34초)다.
- 상품 6개의 예제 데이터를 SQLite에서 실행해 확인했으며, 비교·BETWEEN·AND·OR·괄호·IN·NOT IN·LIKE의 표시 결과는 모두 일치했다. MySQL 실행 검증은 하지 않았다.
- `script.json`과 `vo.json`의 장면별 대본은 일치한다.
- 소스, 음성 타이밍, 저장된 장면 스냅샷과 검사 기록을 확인했다.
- 저장된 검사 기록은 오류 0건이지만 구조 및 일부 자막 읽기 시간 경고가 있다.
- 이번 `npm run check` 재실행은 npm 캐시 디렉터리 쓰기 권한 오류로 완료하지 못했다.
- 최종 MP4와 실제 음성 청취 품질은 확인하지 않았다.
- 이 문서는 개선 제안이며, 영상 소스는 수정하지 않았다.

## 우선순위 높은 개선

### 1. LIKE 인덱스 설명의 단정 완화

위치: `build.py`의 `like2` 장면(약 130행), `script.json`의 `like2`.

현재 화면은 `'SQL%'`를 “인덱스 활용 ✓”, `'%펜'`을 “인덱스 활용 ✗”로 표시한다. 이는 인덱스 사용 여부를 지나치게 단정한다.

수정 제안:

- “일반적인 B-tree 인덱스 기준”이라는 전제를 붙인다.
- `'SQL%'`: “접두어 고정 → 범위 검색에 유리”
- `'%펜'`: “앞부분 미정 → 범위 검색에 불리”
- 데이터가 많으면 무조건 느려진다는 표현보다 “검색 비용이 커질 수 있음”으로 표현한다.
- 성능은 인덱스 구성과 실행 계획에 따라 달라진다는 점을 고려한다.

완료 기준: 화면과 나레이션 모두 인덱스 사용을 무조건 보장하거나 불가능하다고 단정하지 않는다.

### 2. 검색 의도를 바꾸는 조언 수정

위치: `script.json`의 `like2`, `build.py`의 `like2`.

“가능하면 SQL 퍼센트처럼 앞부분을 고정하세요”는 검색 의미를 바꿀 수 있다. `'%펜'`과 `'SQL%'`는 같은 검색의 성능 비교가 아니라 서로 다른 상품을 찾는 조건이다.

수정 제안: “접두어 검색으로 충분한 경우에는 앞부분을 고정한 패턴을 쓰세요.”

완료 기준: 성능을 위해 필요한 검색 의미를 바꾸도록 안내하지 않는다.

### 3. 본문 애니메이션을 설명 시점에 연결

위치: `build.py`의 `enter()`(약 311행), `word_time()`(약 28행), 각 장면의 타임라인.

현재 본문 요소는 일정한 간격으로 등장하고 코드 줄은 별도의 순서로 등장한다. 정리 장면 외에는 설명 단어와 강조 시점을 직접 연결하지 않는다.

수정 제안:

- AND: 첫 조건 강조 → 두 번째 조건 강조 → 두 조건에 모두 맞는 상품 표시.
- OR: 조건별 통과 상품 표시 → 합쳐진 결과 표시.
- 괄호: 괄호 없는 식의 AND 묶음 강조 → 잘못 포함된 SQL 문제집 강조 → 괄호 추가 → 수정된 결과 표시.
- LIKE: 패턴 설명 시 `%`와 `_` 강조 → 상품명에서 대응하는 글자 강조.
- 기존 단어 타이밍과 `word_time()`을 활용한다.

완료 기준: 핵심 조건·결과가 해당 설명 시점에 등장하거나 강조되며, 자식 코드 줄이 부모 코드 블록보다 먼저 애니메이션되어 보이지 않는 상태로 소모되지 않는다.

### 4. 핵심 주제로 분량 집중

위치: `script.json`, `build.py`의 `scenes`, `PROG`, 정리 목록.

요청한 비교·AND/OR·IN·LIKE 외에도 BETWEEN·NOT IN·인덱스·NULL 설명이 포함되어 있다. 길이 자체가 오류는 아니지만 입문자가 기억해야 할 개념이 많다.

수정 제안:

- 비교 → AND/OR와 괄호 → IN → LIKE 순서를 중심으로 구성한다.
- 인덱스 성능 설명을 후속 영상으로 분리하는 것을 우선 검토한다.
- BETWEEN·NULL은 핵심 학습 목표에 필요한지 판단해 축소하거나 분리한다.
- 분량을 줄일 때 나레이션 속도를 더 높이기보다 문장과 장면을 줄인다.

완료 기준: 도입에서 약속한 학습 목표, 본문, 진행 표시, 마지막 정리가 일치한다.

## 전달력과 가독성 개선

### 5. 도입을 실제 질문으로 시작

위치: `script.json`의 `hook`, `build.py`의 `hook`.

현재 약 8초의 도입은 키워드 나열과 “한 번에 정리” 안내다.

수정 제안: “책이면서 만 원 미만인 상품만 찾으려면?” 같은 문제와 간단한 결과를 먼저 보여준 뒤 WHERE 설명으로 이어간다.

완료 기준: 첫 수초 안에 시청자가 해결할 문제와 배울 이유를 알 수 있다.

### 6. 원본 데이터에서 필터링되는 과정 표현

위치: `build.py`의 `intro`, `and`, `or`, `paren`.

원본 6행은 초반에만 나오고, 뒤에서는 결과만 제시한다. 시청자가 상품의 가격과 카테고리를 기억해야 한다.

수정 제안: 필요한 장면에서 원본 일부를 다시 보여주고, 통과 행에 체크 표시를 하거나 제외 행을 흐리게 한다. 색 외에 기호·라벨도 함께 사용한다.

완료 기준: 원본 데이터와 조건만 보고 왜 해당 결과가 나왔는지 화면에서 추적할 수 있다.

### 7. 휴대폰 기준 코드·표 확대

위치: `build.py`의 `.code`, `.tbl`, `.scene` CSS(약 245~272행).

1080px 영상의 코드 42px·표 40px은 390px 폭에서 약 15px·14px로 축소된다. 저장된 스냅샷에서는 여러 장면의 본문 아래에 넓은 빈 공간이 있다.

수정 제안:

- 핵심 조건과 결과를 확대한다.
- 설명에 쓰지 않는 `id` 열은 제거하거나 축소한다.
- 모든 장면에 같은 크기를 강제하기보다 정보량에 맞게 조절한다.
- 본문과 자막, 쇼츠 UI 안전 영역을 함께 확인한다.

완료 기준: 가장 빽빽한 괄호 장면과 원본 표를 390px 폭으로 확인해 조건·상품명·가격을 쉽게 읽을 수 있다.

### 8. 자막을 의미 단위로 분할

위치: `build.py`의 `split_caption()` 및 `caption_chunks()`(약 147~193행).

저장된 검사에는 일부 자막의 읽기 시간이 짧다는 경고가 있다. “펜이거나 1만 8천 원 / 이상인…”처럼 조건 중간이 끊기는 부분도 있다.

수정 제안:

- 금액과 비교 표현을 하나의 의미 단위로 묶는다.
- 읽기 시간이 부족하면 대본을 간결하게 다듬는다.
- 기존 TTS 단어 경계 동기화는 유지한다.
- 표시용 자막과 발음용 대본을 분리할 경우, `앤드 → AND`, `이즈 널 → IS NULL` 등의 대응을 명시해 동기화가 깨지지 않도록 한다.

완료 기준: 대사 중 자막 공백 없이 동기화되고, 짧은 자막이 빠르게 연속 교체되거나 조건 중간이 부자연스럽게 끊기지 않는다.

## 내용 보완

### 9. NULL 장면에 실제 사례와 결과 추가

위치: `build.py`의 `P` 데이터와 `null` 장면.

현재 상품 데이터에는 NULL이 없어서 `IS NULL`이 무엇을 찾아내는지 결과로 확인할 수 없다.

수정 제안: 장면을 유지한다면 별도 사례임을 명시해 NULL이 있는 행과 조회 결과를 보여준다. 공통 상품 데이터를 변경한다면 IN·NOT IN 등 모든 예제 결과도 다시 검증한다.

완료 기준: `= NULL`이 참이 되지 않는 이유와 `IS NULL`로 찾는 실제 결과를 구분해 볼 수 있다.

### 10. NOT IN의 NULL 예외 안내

위치: `script.json` 및 `build.py`의 `in` 장면.

현재 예제는 정확하지만 “목록에 없으면 통과”라는 일반화는 NULL에서 혼동을 줄 수 있다. 비교 대상이 NULL인 경우와 목록 안에 NULL이 들어간 경우를 고려해야 한다.

수정 제안: 입문 영상의 밀도를 고려해 “NULL은 별도 처리가 필요”라는 메모를 넣거나, NULL 심화 영상으로 연결한다.

완료 기준: NOT IN을 모든 값에 대한 단순한 반대 조건으로 오해하게 만들지 않는다.

### 11. BETWEEN의 두 경계 모두 예시로 보여주기

위치: `build.py`의 `between` 장면.

현재 3,000원 상품은 있지만 10,000원 상품은 없다. 설명은 정확하나 양 끝 포함 중 한쪽만 결과로 보여준다.

수정 제안: 장면을 유지한다면 두 경계값을 표시하는 보조 그림을 쓰거나, 예제 데이터를 조정한 뒤 전체 쿼리를 재검증한다.

완료 기준: 하한과 상한 모두 포함됨을 화면으로 확인할 수 있다.

### 12. 마무리를 실전 조합으로 정리

위치: `script.json`의 `outro`, `build.py`의 `EXEC`와 `outro`.

“이것만 알면 WHERE는 충분합니다”는 범위가 넓은 표현이다.

수정 제안:

- “이제 기본 필터 조건을 조합할 수 있습니다”로 바꾼다.
- `category IN ('book', 'pen') AND price >= 10000` 같은 조합을 마지막 실전 예제로 검토한다.
- 도입에서 던진 문제를 마지막에 해결하는 구조로 연결한다.

완료 기준: 마지막 화면에서 시청자가 실제로 작성할 수 있게 된 조건이 드러난다.

## 제작 파일의 재현성 개선

### 13. 쿼리와 결과 자동 대조

위치: `build.py`의 `P`, `rows()`, 각 장면의 결과 ID 목록.

현재 데이터와 결과 목록은 각각 하드코딩되어 있다. 이번 결과는 맞지만 데이터 변경 시 불일치가 생길 수 있다.

수정 제안: 공통 데이터로 쿼리를 실행해 결과를 생성하거나, 빌드 전 기대 결과와 실행 결과를 대조한다. 화면의 생략된 WHERE 구문은 검증할 때 전체 SELECT 문으로 조립한다.

완료 기준: 조건 또는 상품 데이터를 수정했을 때 잘못된 결과가 그대로 영상에 들어가지 않는다.

### 14. 새 환경의 음성 생성 준비

위치: `gen_vo.py`와 Python 의존성 설정.

`gen_vo.py`는 `assets/vo`가 이미 있다고 가정한다. Python 패키지 버전을 명시하는 파일도 해당 프로젝트에서 확인되지 않았다.

수정 제안:

- 생성 전 `assets/vo` 디렉터리를 만든다.
- `edge-tts` 등 Python 의존성과 실행 방법을 기록한다.
- `ffmpeg`, `ffprobe` 설치 여부를 사전 점검한다.
- 프로젝트 폴더 외부에서 실행해도 경로가 안정적으로 해석되도록 스크립트 위치 기준 경로를 사용한다.

완료 기준: 새 환경에서도 문서화된 순서로 음성·HTML을 재생성할 수 있다.

## 권장 작업 순서와 검증

1. LIKE 설명과 검색 의도 관련 문구를 먼저 수정한다.
2. 영상에 남길 학습 범위를 정하고 대본·정리·진행 표시를 함께 맞춘다.
3. 대본 변경분의 음성과 단어 타이밍을 재생성한다.
4. 핵심 장면을 나레이션 단어 시점에 연결한다.
5. 자막 분할과 모바일 가독성을 조정한다.
6. 모든 예제 쿼리와 화면 결과를 다시 대조한다. MySQL 전용 설명은 MySQL 문서 또는 실제 실행으로 확인한다.
7. `npm run check`를 실행하고, 모든 장면 및 전환 시점의 스냅샷을 확인한다.
8. 최종 MP4를 렌더링해 음성·자막·화면을 함께 재생하고, `ffprobe`로 1080×1920 및 오디오 트랙을 확인한다.

수정할 때는 생성물인 `index.html`만 직접 고치지 말고 원본인 `build.py`와 `script.json`에 반영한다. 기존 색상·글꼴·브랜드 디자인과 TTS 단어 경계 동기화를 유지한다. 커밋·푸시는 별도 요청이 있을 때 진행한다.
